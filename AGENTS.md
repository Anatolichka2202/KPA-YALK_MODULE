# Правила работы агента

## 1. Стартовый контекст

Перед работой читать строго в таком порядке:

1. `README.md`;
2. `PROJECT_MEMORY.md`;
3. `docs/INDEX.md`;
4. документы, явно относящиеся к текущей задаче.

Не обходить весь `docs/`.
Не читать весь репозиторий "на всякий случай".

Цель документационной системы — уменьшать необходимый контекст.

---

## 2. Четыре границы

Всегда различать:

```text
РЕПОЗИТОРИЙ
    ↓
ПРОДУКТ: MilTechStation
    ↓
ПОСТАВКА: КТМА
    ↓
ТЕКУЩАЯ ЗАДАЧА/ОБЪЕКТ: УБСИ
```

Нельзя автоматически переносить решение уровня КТМА в общий
MilTechStation.

Нельзя автоматически переносить решение УБСИ на другие изделия КТМА.

Если задача явно не относится к другому изделию, его документацию
не читать и не использовать.

---

## 3. Текущий объект

Текущий объект поставки КТМА — УБСИ.

Работа по УБСИ ведётся до закрытия его текущего объёма:

- исходные требования;
- рабочая трактовка требований;
- испытания;
- оборудование;
- протоколы;
- реализация;
- операторский интерфейс;
- регистрация;
- отчётность;
- подтверждение на реальном стенде.

После явного решения о закрытии УБСИ текущий объект меняется.

До этого момента знания о других изделиях являются opt-in.

---

## 4. Каноническая документация

Единственная точка входа:

`docs/INDEX.md`

Каноническими считаются документы, достижимые из этого индекса.

Во время миграции в `docs/` могут временно оставаться старые файлы.
Если документа нет в новом `docs/INDEX.md`, не считать его текущей
истиной без специальной необходимости.

Один факт должен иметь одного владельца.

В других документах вместо копирования ставить ссылку.

---

## 5. Где разрешено создавать документацию

Проектные документы разрешено создавать только в:

- `docs/`;
- `plans/`.

Исключения в корне:

- `README.md`;
- `AGENTS.md`;
- `PROJECT_MEMORY.md`.

Запрещено создавать документационные файлы рядом с кодом:

```text
orbita/README.md
stand/README.md
registrar/README.md
plugin_x/README.md
notes.md
TODO.md
design.md
```

Если компоненту нужна краткая документация, она размещается в
`docs/reference/components/`.

---

## 6. PROJECT_MEMORY.md

`PROJECT_MEMORY.md` — часто обновляемая рабочая память.

В ней должны оставаться только сведения, которые полезно знать почти
при любой текущей работе:

- текущий объект;
- текущий этап;
- подтверждённые решения;
- важные запреты;
- подтверждённые особенности живого стенда;
- актуальные открытые блокеры;
- ссылки на исследования и референсные программы.

`PROJECT_MEMORY.md` не является:

- журналом всех экспериментов;
- копией ТУ;
- копией протокольной документации;
- архивом старых решений.

Опровергнутая информация удаляется или заменяется актуальным выводом.

---

## 7. Исследования

Подробные исследования хранятся в:

`docs/research/`

Там могут находиться:

- разбор референсных программ;
- результаты экспериментов;
- захваты;
- гипотезы;
- сравнение реализаций;
- доказательства решений.

Исследование не является канонической истиной само по себе.

После подтверждения результата:

- технический вывод переносится в соответствующий канонический документ;
- практически важный вывод при необходимости попадает в
  `PROJECT_MEMORY.md`;
- исследование остаётся источником доказательства.

Опровергнутую гипотезу не переносить в каноническую документацию.

---

## 8. Планы

Рабочие планы находятся только в:

`plans/`

При выполнении плана агент обязан обновлять тот же файл плана после
каждого завершённого логического этапа.

План должен показывать:

- цель;
- этапы;
- выполненное;
- оставшееся;
- новые факты;
- изменённые документы;
- изменённый код.

После завершения:

- устойчивое знание переносится в `docs/`;
- краткий актуальный вывод при необходимости переносится в
  `PROJECT_MEMORY.md`;
- план переносится в `plans/done/`.

План не имеет приоритета над канонической документацией.

---

## 9. Исполняемые данные — не документация

Файлы вроде:

- `data/scenarios/*.yaml`;
- `data/catalog/*.yaml`;
- `data/profiles/*.yaml`;
- адресных `.txt/.csv`;
- конфигураций, которые читает программа,

остаются рядом с системой, которая их использует.

Но нормативное обоснование не должно существовать только в комментарии
YAML/CSV.

Исполняемый файл отвечает:

> Что программа должна выполнить?

Документация отвечает:

> Почему именно это правильно и откуда это следует?

---

## 10. Obsidian

`docs/` является Obsidian vault.

Правила:

1. Начинать навигацию с `docs/INDEX.md`.
2. Использовать обычные относительные Markdown-ссылки.
3. Не создавать orphan-документы.
4. Новый документ обязан появиться в соответствующем индексе.
5. При перемещении документа исправлять ссылки.
6. Изображения и схемы складывать в `docs/assets/`.
7. Первичные документы складывать в `docs/sources/`.
8. Graph View использовать для навигации, а не как замену структуре.
9. Не создавать заметку, если существующий документ уже является
   владельцем этого знания.
10. Не коммитить персональное состояние окон Obsidian.

---

## 11. Источники истины

Для требования к изделию:

1. исходный нормативный документ;
2. каноническая рабочая выжимка;
3. реализация.

Для фактического поведения оборудования/протокола:

1. подтверждённый живой стенд и референсная программа;
2. каноническое описание протокола;
3. текущий код;
4. исторические реализации.

Старый код или старая заметка не доказывают текущее поведение стенда.

Не возвращать в документацию уже опровергнутые гипотезы.

---

## 12. Дизайн интерфейса

Старые прототипы интерфейса не являются источником требований.

Новый дизайн формируется заново на основе:

- фактического операторского процесса;
- требований испытаний;
- текущего production-кода;
- требований безопасности;
- реального состава данных.

Старые дизайн-прототипы не использовать как канон.

---

## 12.1. Сборка и развёртывание

Перед любой задачей, содержащей:

```text
build
compile
package
deploy
copy to stand
move to another PC
SSH
SCP
```

обязательно прочитать:

```text
docs/product/build.md
docs/delivery/deployment.md
```

Для работы с физическим стендом также:

```text
docs/delivery/stand.md
```

Жёсткие запреты:

1. Не выбирать новый toolchain, если существует рабочий Qt Creator Kit.
2. Не устанавливать новый Qt/compiler/build system без прямой задачи.
3. Не создавать новые случайные build directories вместо исправления
   существующей сборки.
4. Не переносить build tree на стенд.
5. Не устанавливать Qt/CMake/compiler на стенд.
6. Не создавать P2P/ad-hoc/SMB/FTP/VPN/temporary HTTP infrastructure для
   обычного deployment.
7. Для переноса использовать документированный SSH/SCP flow.
8. Не менять сетевые адреса, маршруты и firewall без задачи именно на сеть.
9. Перед удалённой операцией проверять hostname стенда.
10. Если документированный deployment сломан — диагностировать его, а не
    проектировать новый транспорт.

Цель:

> сборка и перенос должны быть рутинной операцией, а не исследовательской
> задачей каждый раз.

## 13. Главное правило

Документация должна уменьшать объём контекста, необходимого для решения
задачи.

Если из-за нового документа для понимания одного вопроса приходится
читать больше файлов, структура стала хуже.
