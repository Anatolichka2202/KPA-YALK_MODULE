# MilTechStation V1 — проектный runtime станции

**Статус документа:** согласованная рабочая спецификация.

**Граница:** этот документ описывает продуктовый уровень MilTechStation.
Он не задаёт методику, карту каналов, команды или verdict конкретного
изделия. Такие факты остаются в документации поставки и текущей задачи.

**Трекер:** [task.md](../task.md). Атомарные задачи и их статусы находятся в
`_specs/miltechstation-v1/tasks/`; это единственный источник истины о
прогрессе задач. `task.md` — только сводка для человека.

## Problem Statement

Станция уже умеет исполнять часть проверок, но её возможности разнесены между
сценариями, delivery-кодом и отдельными экранными путями. Инженер не может
доказуемо собрать новый проект проверки из поддерживаемых ресурсов, выполнить
его тем же безопасным runtime, сохранить полный фактический след запуска и
затем корректно повторить отдельный производственный узел без потери истории.

В результате нельзя считать наличие кода для одного изделия готовностью
универсальной станции. Нужен единый продуктовый путь: проект задаёт состав,
workflow задаёт контекст, сценарий обращается к логическим ресурсам, runtime
выполняет проверку, Evidence фиксирует факт, а оператор видит только доступные
ему действия и достоверный статус.

## Solution

MilTechStation V1 строится вокруг `Project → Workflow → Scenario → Resource →
Capability → Device plugin → Evidence → Result`.

Проектный пакет описывает конкретную поставку без добавления её предметных
терминов в общий runtime. Одинаковый runtime обслуживает свободные,
формальные и производственные запуски. Производственный пользователь работает
с пятью пакетами проверки: `FULL`, `POWER`, `YALK`, `YTP`, `YVP`; формальный
ТУ-run остаётся отдельным workflow. После `FULL` можно повторить только
неудачный узел: оба запуска сохраняются, а текущий статус изделия считается по
последней принятой проверке соответствующего узла.

Нормальные условия и климатические условия `+`/`−` являются отдельными
запусками с явным контекстом среды. Свободный режим и минимальная админка
работают через те же project/resource/safety boundaries и не получают прямой
доступ к транспортам приборов.

## User Stories

1. Как инженер проекта, я хочу описать проект, его изделия, оборудование и workflows в пакете, чтобы не создавать отдельное приложение для каждой поставки.
2. Как инженер проекта, я хочу валидировать пакет до физического запуска, чтобы ошибка конфигурации не стала опасным воздействием.
3. Как автор сценария, я хочу обращаться к логическому ресурсу и capability, чтобы не зависеть от IP-адреса, COM-порта или модели прибора.
4. Как интегратор оборудования, я хочу подключать новый transport или vendor SDK через plugin, чтобы предметные процедуры не знали его wire-протокол.
5. Как интегратор существующей программы, я хочу запускать её как внешний процесс через общий runtime, чтобы не переписывать работающий стенд без необходимости.
6. Как разработчик, я хочу, чтобы core не содержал названий конкретной поставки или изделия, чтобы следующий проект не наследовал чужую методику.
7. Как оператор, я хочу выбрать разрешённый workflow проекта, чтобы случайно не запустить engineering-сценарий вместо формальной проверки.
8. Как оператор, я хочу видеть readiness требуемого оборудования до старта, чтобы не получать ложный verdict изделия из-за отсутствующего прибора.
9. Как оператор, я хочу безопасно остановить run, чтобы runtime выполнил cleanup и сохранил причину незавершённости.
10. Как оператор, я хочу продолжить работу после подтверждённого восстановления оборудования, чтобы не повторять уже известные и безопасно сохранённые действия без причины.
11. Как инженер по безопасности, я хочу, чтобы конкурентные Free, ТУ и Production runs не владели одним ресурсом одновременно, чтобы исключить конфликтующие воздействия.
12. Как инженер по безопасности, я хочу видеть состояния ресурса READY, ACTIVE, SAFE, ERROR и INDETERMINATE, чтобы timeout не маскировался под готовность.
13. Как инженер по качеству, я хочу получить неизменяемый run context с проектом, workflow, конфигурацией, оператором, изделием и средой, чтобы результат можно было проследить.
14. Как инженер по качеству, я хочу видеть команды, подтверждения, измерения, ошибки и safety-действия в Evidence, чтобы отличить дефект изделия от ошибки стенда.
15. Как инженер, я хочу привязать raw telemetry, waveform и stdout/stderr к Evidence метаданными, чтобы диагностические данные не терялись и не засоряли общую модель измерений.
16. Как производственный оператор, я хочу запустить `FULL`, `POWER`, `YALK`, `YTP` или `YVP`, чтобы проверить изделие нужным объёмом без перекомпиляции программы.
17. Как производственный оператор, я хочу повторить только отказавший узел, чтобы, например, перепроверить отсоединившийся магазин без стирания истории предыдущего запуска.
18. Как руководитель производства, я хочу, чтобы текущий статус изделия вычислялся по последней принятой проверке каждого узла, а не по случайному старому run.
19. Как инженер, я хочу составить новый совместимый production workflow, сменить binding или выполнить свободную проверку с собственным допуском без изменения кода.
20. Как администратор станции, я хочу видеть проекты, оборудование, connections, resources и диагностику, чтобы подготовить рабочее место без скрытых настроек.
21. Как оператор климатического испытания, я хочу запускать проверку отдельно в normal, `+` или `−` условиях, чтобы контекст среды был частью факта запуска.
22. Как разработчик поставки, я хочу создать специализированный экран поверх общего runtime, чтобы не переносить предметную логику в основное окно станции.
23. Как ответственный за выпуск, я хочу воспроизвести установленный runtime package и прогнать его smoke-тест, чтобы выпуск не зависел от рабочей директории разработчика.
24. Как аудитор, я хочу, чтобы published scenario и его конфигурационная identity сохранялись с run, чтобы результат нельзя было незаметно переписать изменением YAML.
25. Как команда разработки, мы хотим иметь явный файловый трекер с атомарными задачами и доказательствами, чтобы прогресс не зависел от истории чата.

## Implementation Decisions

- `Project` является композиционным корнем. Он ссылается на equipment profile,
  supported DUT types, workflows, screens, reports и scripts; не создаёт
  отдельный Scenario Engine.
- `Workflow` определяет policy запуска: fixed или dynamic scenario,
  registration policy, environment, report и reference workflow. Семантика
  названия workflow принадлежит проекту, а не core.
- Общий runtime не получает KTMA-, UBSI-, YALK-, YTP-, YVP- или PPB-specific
  ветвлений. Они принадлежат delivery/project/task слоям.
- Физический путь всегда проходит через logical resource, capability и device
  plugin. HMI, сценарий, script и connector не обходят эту границу напрямую.
- Project package, scenario и profile имеют версию/identity, фиксируемую с
  run. Published configuration не меняется in-place.
- Free, ТУ и Production используют общий Scenario Engine и общий run contract.
  Отдельный `FreeModeEngine` не создаётся.
- Производственная модель V1 использует `FULL`, `POWER`, `YALK`, `YTP`, `YVP`.
  Конкретный формальный ТУ-run не подменяется этими пакетами.
- Повтор узла создаёт новый immutable run. История сохраняется; текущий
  агрегированный статус изделия использует последнюю принятую проверку
  соответствующего узла.
- Климат `+`/`−` не является post-climate shortcut: это отдельные workflow
  runs с явно зафиксированными условиями. Нормативные setpoint'ы не
  придумываются общим продуктовым кодом.
- Для V1 не требуется полноценный персональный login/RBAC. Оператор фиксируется
  в run, а публикация конфигурации защищается средствами ОС.
- Состояние ресурса и recovery являются общими механизмами. После timeout
  состояние, которое нельзя доказать, становится `INDETERMINATE`; это не
  verdict изделия.
- Каждый физически значимый путь получает назначенные closure gates:
  contract/integration tests, bench verification при применимости и проверку
  сохранённого Evidence.

## Testing Decisions

- Тесты проверяют внешнее поведение: загрузку и валидацию пакета, разрешение
  workflow, выбор logical resource, запуск/отмену процесса, сохранение и
  повторное отображение run/Evidence, блокировку конфликтующих runs и
  классификацию технической ошибки. Не проверяются приватные детали классов.
- Наиболее высокий доступный seam — `Project package → workflow → Scenario
  Engine → Resource/capability → fake plugin → RunStore/Evidence`.
- Для hardware-impacting путей mock-тест не заменяет живую пробу. Такая проба
  фиксирует команду, фактическое измерение, criterion, verdict и cleanup.
- Перед `CLOSED` обязателен зелёный текущий CI. Локальный CTest нужен как
  быстрый gate, но не заменяет CI или bench verification.
- Existing prior art: project-definition, run-store-context, component-profile,
  component-runtime, execution-runtime, execution-scenario, station-session,
  resource-routing и sample-bridge tests. Новый код должен расширять эти seams,
  а не создавать parallel runtime.

## Критерии приёмки

- [ ] **К1.** Project package валидируется, содержит project identity,
  equipment profile и workflows; некорректный пакет не начинает физический run.
- [ ] **К2.** Fixed, dynamic, free, ТУ и production workflow исполняются через
  один Scenario Engine и сохраняют project/workflow/configuration identity.
- [ ] **К3.** Сценарий выбирает именованный logical resource и capability;
  неоднозначная или несовместимая привязка останавливает запуск до воздействия.
- [ ] **К4.** Поддерживаемый component/plugin или внешний process можно
  включить в workflow без внесения delivery-терминов в station core.
- [ ] **К5.** Перед запуском оператор получает readiness требуемых ресурсов и
  project-driven выбор доступного workflow.
- [ ] **К6.** Одновременные пересекающиеся Free/ТУ/Production runs блокируются;
  timeout переводит ресурс в доказуемое состояние или `INDETERMINATE`, а
  recovery не выдаёт это за успешный run.
- [ ] **К7.** Один законченный generic run сохраняет и повторно отображает
  immutable context, command/ack/error/safety events, measurements, verdict и
  ссылки на raw artifacts.
- [ ] **К8.** Production V1 поддерживает `FULL`, `POWER`, `YALK`, `YTP`, `YVP`;
  повтор узла сохраняет оба run и корректно пересчитывает текущий статус DUT.
- [ ] **К9.** Free и минимальный Admin V1 создают/выбирают совместимую
  конфигурацию через общий resource/safety boundary, без перекомпиляции и без
  прямого transport access.
- [ ] **К10.** Normal, climate `+` и climate `−` оформлены как отдельные
  workflows/runs с явным environment context; неизвестные setpoint'ы не
  генерируются общим кодом.
- [ ] **К11.** Установленный runtime package проходит smoke-test вне дерева
  сборки; current CI зелёный; физически значимые delivery paths имеют
  требуемые bench/Evidence gates.

## Out of Scope

- Конкретные ТУ, каналы, команды, IP-адреса и методики УБСИ или другого
  изделия.
- Полноценная Fleet/СУС, MES, web dashboard и hard-real-time HIL executor.
- Полный Studio с graph canvas и завершённый YAML/IR editor.
- Mandatory calibration enforcement и полноценный RBAC.
- Реализация PPB как отдельного приложения; PPB остаётся последующим
  project-level proof.
- Само по себе устранение текущих delivery-тестов или стендовых проблем УБСИ.

## Further Notes

- Состояние реализации и тестов не хранится в этой спецификации: его источники
  истины — task-файлы и рабочий план. Спецификация не объявляет
  MilTechStation готовой к выпуску.
- Детальный статус задач, их зависимости и критерии находятся в task-файлах.
  Документы `docs/` остаются владельцами стабильных продуктовых фактов, а
  `plans/` — рабочих планов.
