# Референс ИСД и проверка сети

Дата: 26.08.2026. Это извлечённые факты из Delphi, а не утверждённая карта
кроссировки УБСИ.

## Протокол ИСД

Исходник [Unit1.pas](../docs/по%20ктма/03_Референсные_программы/02_Delphi_управление_ИСД/Unit1.pas)
использует HTTP GET без отдельного API:

```text
http://<ISD>/type=1num=<N>val=<CODE>work=<0|1>
http://<ISD>/type=2num=<N>val=<0|1>
http://<ISD>/type=3num=<N>val=<0|1>
http://<ISD>/type=4num=1
```

- `type=1` — аналоговый канал: код `val`, включение `work`;
- `type=2` — переключаемый канал, в коде названный `ISDONK` / `ISDOFFK`;
- `type=3` — переключаемый канал, в коде названный `ISDONBUS` / `ISDOFFBUS`;
- `type=4num=1` — общий сброс ИСД.

Это прямо соответствует реализации плагина `orbita.isd_http`: `analog`,
`switch` с типом 2/3 и `reset`.

## Извлечённые номера

В [OrbitaAll.pas](../docs/по%20ктма/03_Референсные_программы/01_Delphi_проверка_КТМА/0.0.0/OrbitaAll.pas)
есть последовательности референсного испытания. Например, для первых четырёх
трактов используются пары `type=2: 5,6,7,8` и `type=3: 1,2,3,4`; далее —
`type=2: 13,14,29,30,32,37,41` и `type=3: 32…43`.

Также там есть массивы:

```text
isdch    = 1, 5, 9, 13, 17, 21, 25, 29
Metkadch = 76, 77, 78, 79, 80, 81, 82, 83
```

Они относятся к конкретной старой схеме проверки, поэтому нельзя записывать
их как `sensor_load_350ma`, `yalk_analog` и т.п. без сверки с А.1 и реальным
кабелем. Но это готовый список кандидатов для стендовой проверки.

## Разрешённый IP-конфликт

Проверка 26.08.2026 сделала безопасный HTTP GET на `.101`. Устройство вернуло
`komanda ne vypolnena` и пример URL `http://192.168.0.99/type=1num=2val=3work=1`.
Это точный формат референсной Delphi-программы; поэтому текущий ИСД
**подтверждённо** находится на `192.168.0.101`.

`Periphery1.ini` со значением `ISDip=192.168.0.132` относится к старой
установке. Его не используем в профиле. Ошибочную привязку `.101` к
Ethernet-адаптеру УБСИ удалили: кандидат на адаптер — `.115` с MAC
`00-35-65-03-74-06`, но подтверждение через UDP `1001/1101` пока не получено.
До сверки схемы А.1 нельзя выполнять даже общий `type=4num=1`: это команда
сброса, меняющая физическое состояние ИСД.

## Доступ к стенду

Проверка на ПЭВМ `DESKTOP-5EO9J5A` подтвердила: Windows 11, пользователь
`Azerty`, `sshd` работает и слушает TCP/22. Однако с рабочей станции ARP для
`192.168.0.50` возвращает MAC `78-44-76-A1-28-04`, тогда как Ethernet ПЭВМ
имеет MAC `00-E0-4B-61-03-6F`. Следовательно, Ethernet-адрес `.50` конфликтует
с другим устройством либо находится в другом L2-сегменте; HTTP на нём отвечает
`Boa/0.94.14rc21`, а не Windows.

Исторически SSH проверялся через DHCP-адрес Wi-Fi, но этот адрес больше не
используется. Текущая команда имеет обязательный явный адрес:

```powershell
$standSshAddress = '<текущий SSH-адрес DESKTOP-5EO9J5A>'
.\scripts\stand_remote.ps1 -Action Status -UserName Azerty -StandAddress $standSshAddress
```

Скрипт допускает продолжение только если удалённая машина вернула имя
`DESKTOP-5EO9J5A`. Перед развёртыванием по проводной сети нужно устранить
конфликт `.50`, а не менять профиль оборудования на случайный DHCP-адрес.
