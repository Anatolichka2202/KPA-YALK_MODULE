# Фактическая архитектура проекта

Документ описывает код, который действительно существует в `master`. Целевая
архитектура отделена от уже реализованной части.

## Что работает сейчас

Путь телеметрии:

```text
E20-10
  → E2010Device
  → ISampleSource
  → очередь отсчётов
  → BitstreamRecoverer
  → FrameDecoderM16
  → ChannelRegistry / Snapshot
  → OrbitaDesktop: таблицы, графики, статистика
```

`liborbita` является библиотекой протокола. Её публичная граница находится в
`orbita/include/orbita.h`. Она принимает нормализованные адреса каналов и
возвращает сырые телеметрические коды. Qt, SQLite, VISA и сценарии внутрь
библиотеки не входят.

`ISampleSource` — используемая внутренняя граница источника отсчётов. Сейчас у
неё одна реализация — `E2010Device`. Старый `DeviceInterface` существует в
исходниках, но текущим конвейером не используется.

SQLite `parameters.db` открывает `MetadataService` в UI-слое. База даёт имена,
категории, адреса и допуски, но не участвует в декодировании сигнала.

`OrbitaDesktop` непосредственно создаёт `orbita::Orbita`, пытается открыть
E20-10 и при ошибке переходит в режим без устройства. В приложении есть режимы
сбора, детального просмотра, конфигурации, БД и простой сценарий.

Текущий сценарий поддерживает только:

- `CMD` — текстовую инструкцию оператору;
- `CHECK` — сравнение одного телеметрического кода с диапазоном.

Это ещё не движок стендовых испытаний.

Каталог `drivers` содержит сохранённые Windows-бинарники производителей. Это не
система плагинов и не готовые Linux-драйверы.

## Чего в коде пока нет

- плагина Ethernet/UDP для физического опросчика RS-485;
- VISA-адаптера В7-78/1;
- адаптера Я2М-66М;
- адаптера МБ26.20;
- проверенного адаптера ИСД;
- общего диспетчера лабораторного оборудования;
- движка карт испытаний с воздействиями, выдержками и измерениями;
- расчёта результата по ячейке и блоку;
- отчёта испытания;
- импорта цифровых данных приложения 2.

## Целевая структура следующего этапа

```text
OrbitaDesktop
  ├─ Мониторинг
  │    └─ TelemetryService → liborbita
  └─ Испытания
       └─ TestEngine (без Qt и ОС)
            ├─ TelemetryService
            ├─ EquipmentManager
            │    ├─ UbsiEthernetUdpAdapter
            │    ├─ VisaVoltmeterAdapter
            │    ├─ WattmeterAdapter
            │    ├─ Mb2620Adapter
            │    ├─ IsdStimulusAdapter
            │    └─ Mock-адаптеры
            ├─ каталог объектов и видов испытаний
            ├─ правила ОК/НЕ ОК
            └─ результаты и отчёт
```

Первой вертикальной реализацией должен стать УБСИ № 7:

1. проверить доступность Ethernet-адаптера и занятость UDP-портов;
2. пассивно записать исходящие пакеты, затем в отдельной проверке подтвердить
   безопасную команду выбора режима;
3. подтвердить варианты UDP-пакетов на реальных данных;
4. связать прямые данные ячеек с телеметрическими параметрами приложения 1;
5. показать графики;
6. реализовать один подтверждённый вид испытания и итог `ОК/НЕ ОК`;
7. только после этого подключать автоматическое управление ИСД и VISA.

### Первый сквозной сценарий УБСИ

Операторский путь должен быть таким:

```text
УБСИ № 7 → вид испытания → состав ЯП-П/ЯТП/ЯВП-8/ЯЛК-96
    → готовность АЦП, «Орбиты» и нужных плагинов
    → запуск → синхронные графики
    → результаты параметров → ячеек → блока
```

Для УБСИ ваттметр Я2М-66М не входит в обязательный состав готовности. В7-78/1,
ИСД и МБ26.20 требуются только теми видами испытаний, где они явно указаны.

Сначала реализуется отдельная `Проверка связи и чтения`. Она подтверждает, что
каналы «Орбиты» обновляются, адаптер отвечает и пакеты имеют ожидаемый формат.
Её результат — `СТЕНД ГОТОВ/НЕ ГОТОВ`, а не приёмочный результат изделия.

Первый настоящий `ОК/НЕ ОК` для УБСИ добавляется только после переноса из ТУ
одного подтверждённого набора воздействий, формул и допусков. Для него движок:

1. выбирает параметры УБСИ из приложения 1;
2. включает только необходимые плагины;
3. выполняет воздействие и выдержку;
4. одновременно сохраняет телеметрию «Орбита», прямые данные ячеек и эталонное
   измерение, если оно предусмотрено;
5. строит графики из одной временной шкалы;
6. рассчитывает результаты параметров и сворачивает их до ячейки и блока;
7. сохраняет версию карты испытания, конфигурацию стенда и исходные записи.
