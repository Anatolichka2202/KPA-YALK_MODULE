# Данные MilTechStation

Этот документ описывает модель данных на уровне продукта.

Здесь нет конкретных IP-адресов, УБСИ, номеров ТУ или конкретных моделей
приборов.

Точная раскладка данных поставки КТМА:

[../delivery/data.md](../delivery/data.md)

---

# Главное разделение

MilTechStation работает минимум с четырьмя разными типами данных:

```text
1. КАТАЛОГ
   что система умеет измерять и как найти параметр

2. СЦЕНАРИЙ / КОНФИГУРАЦИЯ
   что именно надо выполнить

3. RUN
   что действительно произошло в одном запуске

4. ЖИЗНЕННЫЙ ЦИКЛ ИЗДЕЛИЯ
   какое изделие, какой состав, какой этап и какие запуски к нему относятся
```

Эти слои нельзя смешивать в одну "главную базу".

---

# Каталог

Каталог описывает устойчивые технические метаданные:

- типы объектов;
- группы параметров;
- адреса / locator;
- единицы;
- источники данных;
- преобразования;
- связи параметров с физическими источниками;
- подтверждённость конкретной привязки.

Каталог отвечает:

> Что это за параметр и откуда его получать?

Он не отвечает:

> Что произошло в прогоне вчера в 14:35?

---

# Сценарий

Сценарий задаёт последовательность испытания:

```text
шаг
  ↓
procedure
  ↓
required capabilities
  ↓
arguments
```

Сценарий — исполняемая конфигурация.

Он не является журналом результата.

---

# Run

Один run — неизменяемый факт конкретного выполнения.

В run должны сохраняться:

- уникальный `run_id`;
- идентификатор и версия сценария;
- версия каталога;
- версия профиля;
- идентификатор/серийный номер объекта;
- время начала и окончания;
- итог запуска;
- дерево выполненных шагов;
- измерения;
- события.

`run_id` является техническим ключом связи подробного измерительного
результата с другими слоями системы.

---

# Measurement

Измерение хранит как минимум:

```text
что измеряли
эталон / заданное
фактическое
нижний предел
верхний предел
единицу
локальный verdict
сообщение
дополнительные attributes
```

`attributes` позволяют сохранить специфические детали конкретной
процедуры, не превращая общую модель RunStore в модель одного изделия.

---

# Сырые артефакты

Помимо структурированного run система может сохранять отдельные
диагностические артефакты:

- телеметрию;
- сырые пакеты;
- CSV;
- HTML.

Они дополняют RunStore, но не должны заменять структурированный результат.

---

# Жизненный цикл изделия

Жизненный цикл отвечает уже не за отдельное измерение, а за вопросы:

```text
какое изделие?
какой состав?
какая ячейка была установлена?
когда её заменили?
какой этап выполнялся?
какой run относится к этой попытке?
```

Подробные измерения при этом не должны копироваться во вторую базу.

Связь выполняется через `run_id`.

---

# Документ — представление, а не источник результата

HTML/CSV/PDF — это представление уже сохранённых данных.

Канонический измерительный результат не должен существовать только внутри
HTML-файла.

Документ можно пересоздать из структурированных данных, если его формат
меняется.

---

# Граница ответственности

```text
продукт
  определяет общую модель

поставка
  определяет конкретные базы, каталоги и документы

текущий объект
  добавляет свои task-specific поля и правила
```

Не переносить поля УБСИ в общий RunStore, если они могут жить в
`MeasurementResult.attributes` или task-specific модели.
