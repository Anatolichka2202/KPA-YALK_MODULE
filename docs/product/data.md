# Данные MilTechStation

Этот документ описывает модель данных на уровне продукта.

Здесь нет конкретных IP-адресов, УБСИ, номеров ТУ или конкретных моделей приборов.

Точная раскладка данных поставки КТМА:

[../delivery/data.md](../delivery/data.md)

---

# Главное разделение

MilTechStation работает как минимум с шестью различными слоями данных:

```text
1. PROJECT
   что представляет собой конкретный проект станции/проверки

2. КАТАЛОГ
   что система умеет измерять и как найти параметр

3. WORKFLOW / SCENARIO / CONFIGURATION
   в каком контексте и что именно надо выполнить

4. RUN / EVIDENCE
   что действительно произошло в одном запуске

5. ЖИЗНЕННЫЙ ЦИКЛ ИЗДЕЛИЯ
   какое изделие, какой состав, какой этап и какие run к нему относятся

6. DOCUMENT VIEW
   как сохранённый результат показывается человеку/заказчику
```

Эти слои нельзя смешивать в одну "главную базу".

---

# Project

Project — композиционный корень конфигурации конкретной станции или проверки.

Он хранит или ссылается на:

- версию project package;
- equipment profile;
- поддерживаемые DUT types;
- workflows;
- screens;
- reports;
- scripts.

Формат текущего package описан в [Project package](../reference/components/project-package.md).

Project не является журналом результатов.

---

# Каталог

Каталог описывает устойчивые технические метаданные:

- типы объектов;
- группы параметров;
- адреса / locator;
- единицы;
- источники данных;
- преобразования;
- связи параметров с физическими источниками;
- подтверждённость конкретной привязки.

Каталог отвечает:

> Что это за параметр и откуда его получать?

Он не отвечает:

> Что произошло в прогоне вчера в 14:35?

---

# Workflow и Scenario

Workflow задаёт контекст запуска:

- сценарий или разрешение динамического сценария;
- registration policy;
- environment descriptor;
- report reference;
- reference workflow.

Scenario задаёт исполняемую последовательность проверки:

```text
step
  ↓
procedure
  ↓
resource + capability
  ↓
arguments / execution policy
```

Workflow и Scenario являются исполняемой конфигурацией, а не журналом результата.

---

# Run

Один run — неизменяемый факт конкретного выполнения.

Run Context должен постепенно включить:

```text
run_id
project_id / project_version
workflow_id
scenario_id / scenario_version
catalog_version
station/profile version
DUT type / id / serial
operator
environment
started_at / finished_at
```

Текущий `ScenarioRunResult` уже хранит часть этого контекста. Остальные поля мигрируются без создания отдельного task-specific RunStore.

`run_id` является техническим ключом связи подробного результата с другими слоями системы.

---

# Evidence

Evidence — первичная структурированная запись того, что происходило во время run.

Минимальные классы событий целевой модели:

```text
COMMAND
COMMAND_ACK
MEASUREMENT
STATE
ENVIRONMENT
OPERATOR_ACTION
ERROR
SAFETY
VERDICT
```

Event envelope должен содержать достаточно данных для упорядочивания и трассировки:

```text
sequence
timestamp
monotonic time
run_id
source/resource
capability/operation
data
quality
```

Команда оборудования и её результат должны записываться на общей границе оборудования, а не вручную в каждой предметной процедуре.

Высокочастотные waveform/HIL данные не обязаны храниться как отдельный general event на каждый sample: для них допускается отдельный stream/artifact с Evidence metadata/reference.

---

# Measurement

Измерение хранит как минимум:

```text
что измеряли
эталон / заданное
фактическое
нижний предел
верхний предел
единицу
локальный verdict
сообщение
дополнительные attributes
```

`attributes` позволяют сохранить специфические детали конкретной процедуры, не превращая общую модель RunStore в модель одного изделия.

В дальнейшем measurement evidence также должен однозначно указывать resource/device и quality измерения.

---

# Сырые артефакты

Помимо структурированного run система может сохранять отдельные диагностические артефакты:

- телеметрию;
- сырые пакеты;
- waveform;
- CSV;
- process stdout/stderr;
- вложения.

Они дополняют Evidence/RunStore, но не должны заменять структурированный результат.

---

# Жизненный цикл изделия

Жизненный цикл отвечает не за отдельное измерение, а за вопросы:

```text
какое изделие?
какой состав?
какая ячейка была установлена?
когда её заменили?
какой этап выполнялся?
какой run относится к этой попытке?
```

Подробные измерения при этом не должны копироваться во вторую базу.

Связь выполняется через `run_id`.

Free workflow может вообще не иметь lifecycle record. Формальный workflow может прикрепить run к существующему объекту, а production workflow может потребовать зарегистрированный DUT. Эта политика принадлежит Workflow, а не Scenario Engine.

---

# Документ — представление, а не источник результата

HTML/CSV/PDF — представление уже сохранённых данных.

Канонический измерительный результат не должен существовать только внутри HTML-файла.

Документ можно пересоздать из структурированных данных, если его формат меняется.

---

# Граница ответственности

```text
продукт
  определяет общую модель Project / Workflow / Run / Evidence

поставка
  определяет конкретные packages, базы, каталоги и документы

текущий объект
  добавляет свои task-specific поля и правила
```

Не переносить поля конкретного изделия в общий RunStore, если они могут жить в `MeasurementResult.attributes`, Evidence data или task-specific lifecycle model.
