# УБСИ — текущий объект работ

## Статус

УБСИ является текущим объектом работ поставки КТМА.

Пока работа по УБСИ не закрыта, именно этот объект определяет основной
рабочий контекст проекта.

---

## Что должно быть закрыто по УБСИ

Работа считается не только написанием алгоритма проверки.

Для объекта необходимо согласовать и закрыть весь путь:

```text
исходные данные
    ↓
требования
    ↓
рабочая трактовка требований
    ↓
физическая методика
    ↓
оборудование и протоколы
    ↓
программная реализация
    ↓
операторский процесс
    ↓
выполнение на живом стенде
    ↓
регистрация результатов
    ↓
итоговый документ
```

---

## Канонические блоки УБСИ

Для текущего объекта владельцы знаний разделены так:

```text
task/ubsi/
├── overview.md       что представляет собой объект
├── tu.md             выжимка исходных требований
├── tu-work.md        рабочая трактовка и покрытие
├── testing.md        физическая реализация испытаний
├── operator.md       рабочий процесс оператора и HMI
├── production-data.md production lifecycle и snapshot состава
└── yvp.md            актуальный commissioning ЯВП
```

Этот файл является точкой входа и не должен дублировать детали этих документов.

---

## Исходные данные

Первичные документы должны храниться отдельно от нашей трактовки:

```text
docs/sources/ktma/ubsi/
```

Исходный нормативный документ отвечает:

> Что требует первоисточник?

Рабочая документация отвечает:

> Как именно мы понимаем, реализуем и доказываем это требование?

Эти два слоя нельзя смешивать.

---

## Исследования

Разбор:

- референсных программ;
- старого ПО;
- сетевого трафика;
- работы оборудования;
- живого стенда;

должен находиться в:

```text
docs/research/
```

В канон переносится только подтверждённый итог исследования.

Опровергнутые гипотезы не переносятся.

---

## Интерфейс оператора

Каноническое описание находится в:

[ubsi/operator.md](ubsi/operator.md)

Старые UI-прототипы и переходный `docs/operator-ui-new-dis.md` не являются источниками требований.

Операторский интерфейс строится на основе:

- фактической последовательности испытания;
- текущего production-кода и сценариев;
- требований ТУ;
- реального оборудования;
- требований безопасной работы;
- необходимых оператору данных.

Документ `operator.md` отдельно фиксирует текущее покрытие и известные расхождения между согласованным HMI и реализацией.

---

## Граница текущей задачи

Решения УБСИ не должны без проверки становиться:

- общими правилами КТМА;
- общими API MilTechStation;
- требованиями к другим изделиям.

Если найденное решение действительно общее, оно сознательно переносится
на более высокий уровень документации.

---

## После закрытия УБСИ

После явного решения о закрытии текущего объекта:

1. финальное состояние фиксируется в канонической документации;
2. оперативные детали убираются из `PROJECT_MEMORY.md`;
3. текущий объект меняется;
4. агент начинает работать с документацией следующего объекта.

До этого момента другие изделия являются opt-in контекстом.
