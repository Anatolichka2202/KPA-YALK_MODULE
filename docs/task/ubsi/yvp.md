# Подтверждённый физический тракт 11.09.2026

Стенд собран в следующем виде:

```text
Rigol DG-1022Z CH1
  ↓
вывод «З» кабеля ЯВП 8-2
  ↓
ЯВП-8
  ↓
адаптер КТМА
  ↓
ROKT / UDP
```

Для текущей сборки:

```text
«З» = линия заряда; подключена к CH1 Rigol
«Н» = не используется
АКИП-1160/6 = не является источником сигнального воздействия ЯВП
```

Кабельная сборка ЯВП:

```text
ИСД X5 → ЯВП 8-1 X2
ЯВП 8-1 X1 → ЯВП-8 X1
ЯВП 8-1 X3 DB-9F ↔ ЯВП 8-2 X6 DB-9M

ИСД X6 → ЯВП 8-2 X5
ЯВП 8-2 X1 → ЯВП-8 X2
ЯВП 8-2 X2 → ЯВП-8 X3
```

Rigol физически подключён и теперь включён в профиль стенда для `probe`.
Активные команды генератора намеренно заблокированы через
`device.active_commands_confirmed: false`: на текущем commissioning оператор вручную выставляет 1 В, а программное `set_sine(amplitude_vpp=...)` нельзя разрешать до подтверждения, что это значение должно трактоваться именно как Vpp, а не peak/RMS.

# Что подтверждено по ROKT

Для адаптера КТМА подтверждены две 128-байтные команды ROKT:

```text
ROKT 0A 01 00 <cell>
    вход в режим ЯВП

ROKT 0A 03 <channel-1> <cell>
    выбор одного канала ЯВП
```

Физический канал: `1..8`. В wire-поле передаётся `0..7`.

В коде это реализовано через:

```text
UlkUdpTransport::startYvpRokt()
UlkUdpTransport::startYvpChannelRokt()

plugin operations:
start_yvp_probe
start_yvp_channel_probe
```

# Что больше не считается текущим трактом

Старая гипотеза:

```text
ЯВП → обычный поток ЯЛК → адреса 88..96
```

не используется для активной production-проверки ЯВП.

Также больше нельзя считать корректной старую модель коммутации:

```text
yvp_input = base + offset
yvp_gain  = base + offset
```

По фактической кабельной схеме физический вход ЯВП выбирается парой линий ИСД, а коэффициент усиления задаётся комбинацией `КУ1..КУ4`. Поэтому старые `yvp_input` / `yvp_gain` оставлены в профиле только как несовместимость/placeholder и не должны активироваться до снятия точных HTTP `type/num`.

Старый `yvp_fast` catalog binding остаётся `confirmed: false` как исторический/commissioning-кандидат и не должен разрешать воздействие или приёмочный verdict.

# Что пока НЕ подтверждено

После команд ЯВП адаптер выдаёт UDP-трафик, но для текущего репозитория ещё не подтверждены:

```text
размер и структура полезного кадра ЯВП
назначение полей
масштабирование raw → физическая величина
связь raw-данных с коэффициентом усиления/АЧХ
HTTP type/num для физической коммутации входов ЯВП
код КУ1..КУ4 для 0,25 / 0,5 / 1 / 2 / 4 / 8 / 32 мВ/пКл
точная программная трактовка заданных 1 В генератора
полный acceptance criterion
```

Поэтому текущая процедура `ubsi.yvp` делает только то, что можно доказать:

```text
1. отправляет ROKT 0A 03 для каналов 1..8;
2. после каждой команды ждёт свежий UDP-трафик;
3. сохраняет в события run статистику принятых кадров;
4. не включает генератор автоматически;
5. не переключает неподтверждённые маршруты ИСД;
6. завершает шаг как INCOMPLETE, а не как НОРМА/НЕ НОРМА.
```

Отсутствие трафика после конкретной команды является технической ошибкой стенда/тракта, а не автоматически браком изделия.

# Production flow текущего commissioning

Standalone `data/scenarios/ubsi_production_yvp.yaml`:

```text
питание УБСИ
  ↓
проверка доступности Rigol по VISA
  ↓
оператор: CH1, 1 В, OUTPUT по текущей ручной методике
  ↓
yvp.enter_mode       (ROKT 0A 01)
  ↓
ubsi.yvp             (ROKT 0A 03, каналы 1..8)
  ↓
yvp.safe_cleanup
  ↓
отключение питания
```

Проверка доступности Rigol не означает разрешение автоматического OUTPUT: активные команды генератора пока заблокированы профилем.

# Raw probe для закрытия декодера

В release есть:

```text
orbita_yvp_rokt_probe.exe
```

Запуск на текущем стенде по умолчанию:

```powershell
.\orbita_yvp_rokt_probe.exe
```

Явные параметры:

```powershell
.\orbita_yvp_rokt_probe.exe 192.168.0.115 192.168.0.50 1113 1 1000 C:\Orbita\yvp-capture
```

Порядок аргументов:

```text
adapter_ip
local_ip
port
cell
capture_ms
output_directory
```

Probe отправляет `0A 01`, затем последовательно `0A 03` для каналов 1..8, печатает наблюдаемые размеры кадров/первые байты и сохраняет raw-записи. Он не управляет генератором и ИСД и не пытается угадывать декодер.

# Следующие шаги

1. Получить живой capture `0A 01` и каждого `0A 03` при собранном тракте и контролируемом сигнале Rigol.
2. По capture доказательно определить frame layout ЯВП.
3. Снять штатную коммутацию ИСД и получить точные HTTP `type/num` для входов и КУ.
4. Реализовать явные операции `select_yvp_input` / `select_yvp_gain`; не возвращаться к `base+offset`.
5. После подтверждения единицы амплитуды разрешить автоматический `set_sine` / `output` Rigol.
6. Только после этого возвращать коэффициенты усиления, АЧХ, затухание и приёмочный verdict.

До закрытия этих пунктов автоматический `НОРМА` по ЯВП запрещён.
