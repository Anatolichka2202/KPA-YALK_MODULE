# УБСИ — операторский интерфейс

Этот документ является каноническим владельцем операторского процесса и требований к HMI для текущего объекта УБСИ.

Он отвечает на вопрос:

> Что должен видеть и делать оператор, и как UI отображает уже существующий backend-сценарий?

Связанные владельцы знаний:

- [tu.md](tu.md) — что требует исходный нормативный документ;
- [tu-work.md](tu-work.md) — как требования закрываются стендом;
- [testing.md](testing.md) — физическая методика;
- [production-data.md](production-data.md) — production lifecycle и snapshot состава;
- [yvp.md](yvp.md) — актуальный commissioning ЯВП.

Старые UI-прототипы и `docs/operator-ui-new-dis.md` не являются источником требований. Они могут использоваться только как исторические/рабочие материалы до финальной очистки.

---

# 1. Основной принцип

Испытание выполняется в одном постоянном рабочем окне.

Оператор не должен переходить по отдельным wizard-страницам для каждого шага. В течение run сохраняется общий shell:

```text
слева     маршрут / этапы
центр     визуализация текущего этапа
снизу     прогресс / время / ключевая телеметрия
```

Центральная область меняется по текущему `ScenarioEngine::RunEvent`, а не запускает отдельный второй сценарный движок.

Подготовка оборудования является первым состоянием этого же workspace, а не отдельным приложением или отдельным мастером.

---

# 2. Визуальный стиль

Источник стиля — текущий промышленный dark UI проекта.

Обязательные свойства:

- тёмно-синий / графитовый промышленный интерфейс;
- без перехода на светлую тему;
- без декоративных dashboard-элементов, не помогающих текущей операции;
- без постоянного глобального журнала и лишних status-bars в испытательном окне;
- данные текущего испытания важнее административной информации;
- карточки/иконки применяются для выбора понятного оператору действия, а не технические dropdown-списки backend-кодов.

---

# 3. Верхнеуровневая навигация

Основные режимы:

```text
Главная
├── Производство
├── ТУ
└── Администрирование
```

Production и ТУ используют один runtime-компонент отображения измерений, но разный операторский контекст.

---

# 4. Производственный маршрут

Канонический операторский маршрут полной проверки:

```text
Главная
  ↓
Производство
  ↓
производственная сессия
  ↓
Подготовка
  ↓
Питание
  ↓
ЯЛК-96
  ↓
ЯТП
  ↓
ЯВП-8
  ↓
Завершение
```

Это UI-группировка. Она не заменяет и не сокращает узлы backend-сценария.

Текущий `data/scenarios/ubsi_production_full.yaml` выполняет `readiness`, `supply_range`, блок ЯЛК, блок ЯТП, commissioning-блок ЯВП и `power_off`. UI должен отображать эти узлы внутри маршрута, не придумывая альтернативных scenario ID.

---

# 5. Видимые production scopes

Оператору доступны:

```text
полная УБСИ
ЯЛК-96
ЯТП
ЯВП-8
```

Не показывать как отдельный пользовательский scope:

```text
Питание
ЯП-П
```

Питание является частью соответствующих процедур и полной проверки.

ЯП-П является частью обязательного четырёхкомпонентного состава УБСИ. Backend `FullUbsi` помечает затронутыми `YALK-96`, `YTP`, `YVP`, `YP-P`, а пакет `PowerConsumption` — `YP-P`.

При этом сам full scenario сейчас не содержит отдельного узла с именем `YP-P`. До отдельного подтверждения нельзя автоматически утверждать, что `supply_range` полностью закрывает все требования к ЯП-П. Это зарегистрированная несостыковка, а не основание показывать отдельную кнопку ЯП-П.

---

# 6. Оператор и изделия

Производственная сессия должна работать с ФИО оператора.

Табельный/персональный номер в этот экран не входит.

УБСИ и серийные номера его ячеек регистрируются в административном контуре и берутся из `registrar.db`. Испытательное окно не должно превращаться в дублирующую форму регистрации состава.

Целевая модель сессии — выбрать несколько уже зарегистрированных УБСИ и последовательно выполнить выбранную проверку для каждого из них под одной операторской сессией.

История операторских связок может хранить:

```text
timestamp
operator
serial
scenario
status
run_id
```

Текущая реализация `runs/operator_sessions.csv` является рабочим механизмом, но не заменяет production ledger и `runs.db` как источник результатов испытаний.

---

# 7. Подготовка оборудования

Открытие production/TU не должно само по себе опрашивать, переключать или армировать оборудование.

Проверка начинается только после явного действия оператора в состоянии `Подготовка`.

Проверяется только оборудование, требуемое выбранным сценарием через `requiredCapabilities`.

Это означает, что текущий commissioning-сценарий ЯВП требует доступности `signal.generator` / Rigol, но доступность прибора не означает разрешение автоматических активных команд генератора.

Legacy Orbita/E20 не входит в readiness УБСИ и не должен автоматически открываться из production/TU УБСИ.

Ошибка оборудования отображается как ошибка стенда/тракта и не превращается в `НЕ НОРМА` изделия.

---

# 8. Питание

UI питания должен показывать фактический ход процедуры, а не отдельный верхнеуровневый тест.

Для полной проверки отображаются:

```text
24 В
27 В
35 В
19 В / 5 минут
возврат 27 В
37 В / 1 минута
возврат 27 В
```

На экране нужны как минимум:

- текущая уставка;
- измеренное/фактическое состояние, которое предоставляет backend;
- ток потребления;
- текущая точка последовательности;
- итог текущего шага.

Критерий изделия по общему току:

```text
Iобщ <= 0.4 А
```

`0.6 А` — защитный current limit стенда, а не критерий годности.

---

# 9. ЯЛК-96

В левой части рабочего пространства оператор должен видеть текущий внутренний этап ЯЛК:

```text
инициализация потока
калибровка 97 / 99
исходное состояние
80 аналоговых каналов
контактные сигналы
перегрузка ±12 В
эталон 6.2 В
безопасное завершение
```

## Аналоговые каналы

Основное представление — один обзор 80 рабочих каналов.

Источник данных — события backend, включая:

```text
ulk_address
command_v
v7_v
yalk_v
value_samples
background_mean
background_min
background_max
```

Абсолютная шкала канала — `0...6.2 В`. Малые колебания показываются отдельным усиленным диапазоном, а не подменяют абсолютную шкалу.

В7 показывается отдельно как физический независимый эталон воздействия ИСД. Он не является источником 80 столбцов ЯЛК.

## Контактные сигналы

Отдельно показывать цифровое состояние `0/1` и текущую точку воздействия.

Текущие точки:

```text
0.0 В
0.9 В
2.5 В
```

## Перегрузка

Оператор должен видеть:

- какой физический канал сейчас перегружается;
- полярность `+12/-12 В`;
- состояние остальных наблюдаемых каналов относительно baseline;
- превышение критерия `abs(delta_code) <= 2`.

Одних трёх текстовых значений `канал / полярность / delta` недостаточно для финального HMI полной 88-канальной процедуры.

# 10. ЯТП

UI ЯТП показывает:

- текущий канал;
- подтверждённое оператором сопротивление;
- измеренное сопротивление;
- серию `value_samples` текущего канала;
- обзор 30 каналов на абсолютной шкале `0...240 Ом`;
- усиленный диапазон min/max для малых отклонений;
- последовательность точек Р4831 `0 / 120 / 240 Ом`.

Р4831 остаётся ручным.

UI не должен создавать второй собственный диалог подтверждения. `operator.manual_input / confirm_value` остаётся единственным backend-контрактом операторского подтверждения Р4831.

---

# 11. ЯВП-8

## Подтверждённый текущий физический тракт

```text
Rigol DG-1022Z CH1
  ↓
вывод «З» кабеля ЯВП 8-2
  ↓
ЯВП-8
  ↓
адаптер КТМА
  ↓
ROKT / UDP
```

Для текущего commissioning:

- Rigol физически подключён и должен быть доступен по VISA;
- оператор вручную выставляет `1 В` и `OUTPUT` по текущей методике;
- автоматические `set_sine/output` запрещены профилем, пока не подтверждена трактовка амплитуды `Vpp/peak/RMS`;
- неподтверждённые маршруты ИСД автоматически не переключаются.

Подтверждённый transport:

```text
ROKT 0A 01 00 <cell>
ROKT 0A 03 <channel-1> <cell>
```

Физические каналы: `1..8`.

Пока payload ЯВП не декодирован и acceptance criterion не закрыт, UI должен честно показывать commissioning/transport status и итог `INCOMPLETE` от backend.

Нельзя:

- выдавать наличие UDP-трафика за измерительный результат ЯВП;
- разрешать автоматический OUTPUT Rigol до подтверждения единицы амплитуды;
- использовать старую гипотезу `88..96` как доказанную карту результата;
- показывать `НОРМА`, если backend не может доказать acceptance.

Комиссионное ручное действие оператора с Rigol должно отображаться как инструкция сценария, а не как произвольная кнопка прямого управления генератором в графическом UI.

---

# 12. Режим ТУ

ТУ использует те же read-only графики и тот же `RunEvent` mapping.

В графических страницах ТУ не должно быть произвольных прямых кнопок управления ИСД, источником, генератором или транспортом. Воздействия и коммутация остаются scenario-driven.

Текущие подтверждённые ручные действия оператора:

1. ЯТП — установка Р4831 через существующий backend modal `operator.manual_input`;
2. ЯВП commissioning — ручная установка `Rigol CH1 = 1 В, OUTPUT` по инструкции сценария, пока автоматические active commands запрещены.

Это не разрешает создавать отдельную ручную панель управления Rigol в TestPage.

---

# 13. Время и прогресс

Достоверным является фактически прошедшее время run.

Текущая реализация вычисляет `Общая длительность` и `Осталось` как экстраполяцию из процента прогресса. Эта оценка не является утверждённым требованием HMI и не должна считаться канонической.

Пока отдельное правило расчёта оставшегося времени не согласовано:

- показывать elapsed time можно;
- приблизительные total/remaining должны быть либо явно вторичными, либо убраны;
- нельзя выдавать progress-based экстраполяцию за расчётную длительность процедуры.

---

# 14. Завершение

Финальное состояние остаётся в том же workspace.

Оно должно показывать фактический backend verdict, а не локально вычисленный UI-итог.

Минимум:

- итог run;
- статус основных блоков;
- факт safe cleanup / power off, если эти события доступны;
- `run_id` / связь с отчётом;
- переход к следующему изделию производственной сессии или возврат к выбору.

Для текущего ручного commissioning ЯВП отдельно требуется закрыть вопрос безопасного завершения ручного `Rigol OUTPUT`: сценарии имеют `yvp.safe_cleanup`, но текущий cleanup не содержит автоматической команды генератора, поскольку active commands запрещены. Нельзя считать этот вопрос закрытым только наличием общего safe-stop UI.

# 16. Обязательные несостыковки к закрытию

До объявления операторского ТЗ закрытым необходимо:

1. ЯП-П: доказательно связать требования ЯП-П с существующим power/full flow либо добавить недостающую backend-процедуру. Не решать это только текстом UI.
2. Production session: проверить и довести модель явного выбора нескольких зарегистрированных УБСИ в очередь одной сессии.
3. Перегрузка ЯЛК: вернуть оператору обзор состояния остальных каналов относительно baseline во время прохода 1..88.
4. Время: убрать статус «утверждённого» с progress-based `≈ total / remaining` и зафиксировать окончательное правило отображения.
5. ЯВП: по живому capture определить payload, физическую величину и acceptance criterion; до этого сохранять `INCOMPLETE`.
6. ЯВП manual Rigol: зафиксировать явный безопасный порядок отключения/снятия ручного OUTPUT после commissioning run; текущий `yvp.safe_cleanup` не управляет генератором.
7. Завершение: довести финальное состояние рабочего окна до принятого минимального набора данных без отдельного wizard/result application.

Эти пункты отслеживаются в `plans/active/ubsi-operator-ui.md`.
