# УБСИ — заморозка интерфейса

Статус: **FROZEN / перенос в Qt**

Этот документ фиксирует окончательное визуальное решение для текущего цикла работ. Он не открывает новый этап проектирования интерфейса.

## 1. Правило остановки

После этой фиксации изменение уже принятого экрана допускается только если обнаружено хотя бы одно из следующего:

1. отображаются фактически неверные данные;
2. нарушена методика или безопасность;
3. элемент нельзя корректно связать с реальной моделью данных;
4. интерфейс не помещается или становится нечитаемым на обязательном разрешении;
5. действие оператора невозможно выполнить или оно неоднозначно;
6. реализация расходится с этим документом или утверждённой спецификацией;
7. владелец интерфейса явно изменил требование.

Не являются основанием для изменения:

- «можно сделать ещё красивее»;
- «здесь осталось место»;
- «давайте добавим ещё одну карточку/график/статистику»;
- «так обычно делают»;
- «агенту кажется логичнее»;
- желание унифицировать экраны, которые по смыслу различаются;
- локальная переделка соседнего экрана;
- желание владельца интерфейса «ещё чуть-чуть допилить», если нет причины из списка выше.

Если возникает только эстетическая идея без дефекта, она записывается в отложенные идеи и **не выполняется в этом цикле**.

## 2. Источники визуального решения

В текущем цикле есть два интерактивных прототипа. Их роли зафиксированы и не должны смешиваться произвольно.

### 2.1. Основной прототип

Основой для переносимого интерфейса является **web-прототип v1.3**.

Из него берутся:

- общий каркас рабочего окна;
- производственная сессия;
- Подготовка;
- Питание;
- ЯЛК — аналоговые каналы;
- ЯЛК — контактные сигналы;
- ЯТП;
- ЯВП;
- Завершение;
- общая нижняя телеметрическая область;
- цветовая семантика;
- поведение active / pinned / hover / zoom;
- состояния ошибки стенда и остановки.

### 2.2. Исключение: перегрузка ЯЛК

Для экрана **«ЯЛК-96 — перегрузка ±12 В»** визуальным образцом является **web-прототип v0.5**.

Это осознанное исключение из более раннего решения рисовать только `Δcode` относительно нуля.

Главная плоскость перегрузки должна показывать для всех 88 физических каналов:

- исходное состояние `baseline` как постоянную полупрозрачную тень/фон;
- текущий или последний свежий снимок как основной столбец;
- перегружаемый канал отдельным синим выделением;
- остальные 87 каналов одновременно;
- канал с нарушением критерия — красным.

При этом нормативная проверка **не меняется**:

```text
abs(current_code - baseline_code) <= 2
```

То есть визуально оператор сравнивает baseline и current, а решение о годности всё равно принимается по `delta_code`.

В верхнем контексте показываются:

- полярность `+12 В / -12 В`;
- перегружаемый канал `1..88`;
- номер воздействия `1..176`;
- фаза/выдержка;
- максимальный `|Δcode|` остальных наблюдаемых каналов;
- текущий результат.

В подсказке канала допустимо показывать:

```text
baseline_code
current_code
delta_code
verdict
```

Не добавлять второй большой график `Δcode`, heatmap, отдельный график одного канала или ещё одну конкурирующую плоскость.

Оранжевый warning для перегрузки **не вычисляется**, пока отдельно не утверждено его правило. В частности, не использовать самодельный порог `75 %` допуска.

## 3. Постоянный каркас Production

После запуска прогона геометрически постоянны:

1. верхняя строка: `← Сессия | УБСИ | Производство · <объём> | оператор | Остановить`;
2. левая колонка текущей процедуры;
3. центральная рабочая область;
4. нижняя телеметрическая область.

Меняется содержимое левой и центральной областей, но не их геометрическое положение.

Левая колонка показывает **только текущую процедуру**.

Примеры:

- Питание — точки питания/выдержки;
- ЯЛК — инициализация, калибровка, исходное состояние, аналоги, контакты, перегрузка, эталон, завершение;
- ЯТП — поток, калибровка, точки Р4831, завершение;
- ЯВП — текущая структура матрицы ЯВП.

Глобальное дерево `Подготовка → Питание → ЯЛК → ЯТП → ЯВП → Завершение` не является постоянным содержимым левой колонки во время run.

## 4. Нижняя область

Нижняя область постоянна по геометрии и должна быть достаточно высокой, чтобы график общего тока УБСИ был хорошо читаем.

Она содержит:

- фактическое прошедшее время;
- живой график общего тока УБСИ;
- ход текущей процедуры в реальных единицах: канал/точка/воздействие/выдержка.

Не показывать ETA, если оно не является гарантированным временем методики.

## 5. Production session

Используется компоновка v1.3:

- слева — зарегистрированные УБСИ;
- по центру — очередь текущей сессии;
- справа — параметры сессии.

Реестр и очередь — разные сущности.

На всю сессию едины:

- оператор;
- производственный этап;
- объём проверки.

Одно изделие не может присутствовать в очереди дважды. Между изделиями очередь можно редактировать, во время активного run — нет.

## 6. Подготовка

Вход в Подготовку сам по себе не обращается к оборудованию.

Проверка стенда начинается только после явного действия `Проверить оборудование`.

`Начать испытание` виден, но недоступен, пока требуемое оборудование не готово.

## 7. ЯЛК — аналоговые каналы

- одна общая плоскость всех 80 рабочих каналов;
- все каналы обновляются из общего свежего состояния, а не только текущий;
- текущий backend-канал только выделяется;
- выбранный оператором канал не меняет выполнение;
- min/max видимы;
- по умолчанию используется увеличенный рабочий диапазон вокруг точки;
- доступен возврат к полной физической шкале `0...6,2 В`;
- hover показывает подробности, click фиксирует просматриваемый канал;
- zoom/pan не останавливают live update.

## 8. ЯЛК — контактные сигналы

Распределение рабочей высоты:

```text
примерно 70 % — аналоговый обзор 80 каналов
примерно 30 % — цифровые состояния
```

Цифровая часть не должна занимать половину экрана.

Точки:

```text
0,0 В
0,9 В
2,5 В
```

## 9. ЯТП

- одна плоскость 30 каналов;
- точки `0 / 120 / 240 Ом`;
- Р4831 — единственное обязательное ручное действие;
- используется backend-modal подтверждения, второй собственный диалог UI не создаётся;
- после подтверждения переходы автоматические;
- абсолютная шкала `0...240 Ом` и увеличенный рабочий диапазон доступны как режимы просмотра;
- критерий и итог берутся из backend, UI не изобретает их.

## 10. ЯВП

Используется представление v1.3.

Главная область — общая плоскость 8 каналов, а не большой график одного текущего канала.

Для текущей точки отображаются подтверждённые backend-данные:

- канал;
- заданный коэффициент;
- рассчитанный коэффициент;
- частота;
- данные В7, если они опубликованы backend;
- состояние acceptance.

Для матрицы используются текущие production параметры:

```text
8 каналов
7 коэффициентов: 0.25, 0.5, 1, 2, 4, 8, 32 мВ/пКл
7 частот
```

UI не выдаёт `НОРМА`, если backend ещё не применил приёмочный критерий.

## 11. Завершение Production

Финальный экран может быть плотнее live-экранов и показывать предметную производственную статистику.

Допустимы:

- общий verdict;
- verdict по выполненным блокам;
- краткие причины отклонений;
- предметная статистика по проверкам;
- производственный этап;
- run id;
- системный контекст;
- необязательный комментарий испытателя.

Не добавлять декоративные KPI, круговые проценты и статистику без производственного смысла.

## 12. ТУ

ТУ использует те же измерительные компоненты, но отдельную оболочку.

Перед запуском:

- выбирается оператор;
- выбирается **только зарегистрированное** УБСИ;
- выполняется полный нормативный маршрут;
- ручной ввод произвольного SN не используется;
- проверка оборудования запускается отдельным явным действием.

Во время run слева отображаются нормативные пункты ТУ, без технических `init/calibration/cleanup` как отдельных пунктов.

`НЕ НОРМА` отдельного пункта не прерывает ТУ; run продолжается до конца, если нет ошибки стенда/безопасности/hard-stop backend.

Production-only warning в ТУ не показывается.

## 13. Цветовая семантика

```text
зелёный   = подтверждённая НОРМА / успешное завершение
красный   = НЕ НОРМА изделия
оранжевый = только утверждённое production-only визуальное предупреждение
синий     = active / current
серый     = ещё не выполнено / inactive
```

Ошибка стенда может использовать сильный красный системный overlay, но не размещается как verdict изделия.

Нормальные отдельные измерительные столбцы не обязаны становиться зелёными; зелёный не должен превращать график в однотонный ковёр.

## 14. Разрешение

Эталон: `1920×1080`.

Обязательная рабочая нижняя граница: `1600×900`.

В испытательном workspace нет прокрутки страницы. Zoom/pan разрешены внутри графиков.

## 15. Перенос в Qt

Qt/C++ воспроизводит утверждённое поведение и геометрию. Перенос **не является новой стадией проектирования**.

Если в Qt хочется добавить элемент, которого нет в этом документе, утверждённом прототипе или контракте данных, элемент не добавляется.

Проверка завершённости переноса выполняется сравнением состояний с прототипом, а не субъективным ощущением «стало красивее».

## 16. Последний предохранитель

Если владелец интерфейса после этой фиксации предлагает эстетическую переделку без конкретного дефекта, сначала нужно проверить её по разделу 1.

Если причина не подходит ни под один разрешённый пункт, правильное действие — **не менять интерфейс и напомнить, что текущий цикл дизайна закрыт**.
