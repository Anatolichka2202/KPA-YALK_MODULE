# MilTechStation — контракт Desktop Core, редакция 0.1

Дата: 23.11.2026. Владелец: backend/platform. Потребитель: отдельная команда HMI.
Статус: реализован первый контрактный слой; API пока не заморожен до совместных контрактных тестов.

## Границы ответственности

| Модуль | Отвечает | Не отвечает |
|---|---|---|
| StationSession / ScenarioEngine | Оборудование, ресурсы, сценарии, остановка, события, исходные результаты | Отрисовка и навигация |
| Поставка | Физические протоколы, методики, подготовка, критерии, жизненный цикл изделия | Общее рабочее место |
| Desktop Core | Идентичность проекта, типизированные read-model, доступность workflow и предварительная проверка команд | Вызов прибора, управление безопасностью, сохранение отчётов |
| Desktop Application Service (следующий этап) | Асинхронные команды, интеграция с StationSession, подписки, персистентность, политики запуска | Qt-виджеты |
| HMI | Компоновка, визуализация состояний, пользовательские действия | Прямые аппаратные команды и трактовка допусков |
| Отдельный ТУ executable (план) | Один фиксированный workflow и ограниченная операторская среда | Произвольные инженерные операции |

Уже созданные исходники:
- station/include/orbita_stand/desktop_core.h
- station/src/desktop_core.cpp
- station/tools/station_project_inspect.cpp
- station/tests/desktop_core_test.cpp

Desktop Core не содержит QWidget и не является вторым сценарным движком.

## Поток данных

    Project YAML + StandProfile -> DesktopCore -> DesktopSnapshot
    Приборы -> StationSession -> ParameterRepository / RunEvent
            -> application service -> RuntimeObservation -> DesktopCore
            -> Qt adapter (queued) -> QAbstractItemModel -> HMI

Приложение собирает согласованный runtime-снимок в потоке владельца. Атомарное свойство StationSession::busy() само по себе не делает чтение изменяемого профиля или реестра потокобезопасным. Qt-модели обновляются в GUI-потоке, а QWidget никогда не вызывает оборудование.

### Смысл данных

- Отсутствие значения не заменяется нулём: значение передаётся через optional.
- Fresh / Stale / Disconnected / Invalid / UnknownUnit / UnitMismatch — независимые состояния.
- Строить график можно только по конечному, свежему значению с подтверждённой совпадающей единицей.
- Статус Simulated передаёт runtime, а не слово в имени профиля.
- Компонент Ready требует реального наблюдения с отметкой времени; enabled в YAML не является доказательством готовности.
- Признак activeOutputsDeclaredConfirmed — только декларация из профиля, не право подавать напряжение.
- RunVerdict относится к сценарию. Статусы КТМА NORM/NOT_NORM/STAND_ERROR преобразует адаптер самой поставки.

Номер схемы DesktopSnapshot: 1. Изменение значения поля требует отдельного решения и тестов.

## Командный контракт

DesktopCore::check(CommandRequest, RuntimeObservation) принимает только типизированные намерения.

| Команда | Предварительные условия |
|---|---|
| StartWorkflow | Workflow существует, входит в сборку, включён поставкой, есть зарегистрированный обработчик, runtime настроен и готов, нет другого запуска/остановки/аварии, подтверждены нужные регистрация и среда |
| RequestStop | Есть активная операция; остановка разрешена также при неисправности |
| CreateScenarioDraft | Только инженерная сборка, явный допуск на редактирование, разрешённый workflow, станция не занята |

Строковое operator_action из YAML не считается полномочием. DesktopPolicy.supportedActions — явный список реализованных приложением обработчиков. Произвольный invoke(capability,operation,args) не предоставляется HMI.

ВАЖНО: check() — только предварительный пропуск для UI. Это **не** авторизация и **не** физическая блокировка. Исполнитель команд ещё раз проверяет условия на момент исполнения и действует исключительно через StationSession, политики конкретной поставки, leases и подтверждённую безопасную последовательность. Вызов реального оборудования в Desktop Core отсутствует.

### Полная инженерная сборка

Предоставляет явно разрешённые workflow, инженерные сценарии и мониторинг. Редактирование не означает разрешения на активные выходы. Управление оборудованием получит собственные строгие сервисные контракты.

### Отдельная сборка ТУ (ещё не реализована)

В момент создания ядра задаётся один существующий tuWorkflowId. Остальные workflow скрыты, редактирование сценариев недоступно, симуляция по умолчанию не допускается к исполнению. Сборка использует те же StationSession, ScenarioEngine и RunStore, но иной набор API и экранов. ТУ-сборка пока является архитектурной целью: действующий MilTechStation.exe связан с КТМА.

## Безопасный инструментарий

Новый CMake target: station_project_inspect. Он использует загрузчики реального проекта и профиля и выдаёт JSON-контракт. Не загружает драйверы, не опрашивает приборы, не включает выходы.

Примеры запуска в каталоге пакета:

    station_project_inspect.exe projects/reference_device/project.yaml --edition engineering --handler station.generic --allow-edit
    station_project_inspect.exe projects/ktma/project.yaml --edition tu --workflow tu_normal --handler ktma.tu

Вывод содержит schema, edition, project, profile, workflows, components, причины недоступности. По определению в режиме инспекции runtime_state равен unconfigured, а launchable = false даже при указанном --handler; флаг описывает поддерживаемый обработчик, не включает исполнение.

Ошибки проекта дают ненулевой exit code и JSON в stderr. Команду можно применять перед сборкой поставки; она не подтверждает физическую готовность стенда.

## Передача команде HMI

Использовать как входной контракт:
- DesktopSnapshot: проект/поставка, edition, runtimeState, workflows, components.
- WorkflowView: стабильный ID, действие, launchable и причина отказа.
- ComponentView: состояние, диагностика, optional observedAt.
- ParameterView: optional measured value, источник, единица, качество, graphAllowed.
- CommandRequest и Decision: намерение и результат предварительной проверки.

Нельзя ссылаться на индексы массива workflow как на идентификаторы, вызывать физическое оборудование из виджета или считать отсутствие данных исправным нулём.

Утверждение API производится после совместного контракта HMI и backend; до этого изменение структур допустимо с обновлением тестов.

## Приёмка текущего слоя

CTest stand.desktop_core проверяет отсутствие фиктивной готовности, запрет неподтверждённого запуска, фильтрацию workflow ТУ, запрет редактирования, остановку при busy/fault и корректность измерений (нулевое, отсутствующее, просроченное, нечисловое, несовпадение единиц).

Это проверка программного контракта, а не стендовая приёмка и не визуальная приёмка HMI.

Не редактировать apps/ui_preview и docs/ui в backend-ветке без согласования с интерфейсной командой.
