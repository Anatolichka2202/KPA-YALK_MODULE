# Отчётность

Отчётность разделена по уровню ответственности и не смешивает измерения с
жизненным циклом изделия.

## 1. Отчёт запуска стенда

HTML/CSV из `report_writer` содержит сценарий, версию каталога и профиля,
события, raw/decoded значения, единицы, допуски, график и итог запуска.
`run_id` — ключ для поиска полной записи в `runs.db`.

## 2. Отчёт ячейки и этапа

Регистратор добавляет к `run_id` тип ячейки, SN, этап и попытку. В таблице
должны быть: пункт ТУ, требование, фактическое значение, допуск,
`НОРМА/НЕ НОРМА`, средство измерения, оборудование, идентификатор запуска и
статус `НЕ ПРОВЕРЕНО`.

## 3. Журнал КТМА

Финальный документ показывает изделие, состав, все SN (включая снятые), причины
замен, четыре этапа каждой активной ячейки, ссылки на прогоны и итог
`КТМА НОРМА / НЕ НОРМА / НЕПОЛНАЯ`.

## Правила ТУ

`НОРМА` ставится только при наличии фактического измерения и подтверждённой
карты. Непроверенный пункт не превращается в ноль и не скрывается: он выводится
отдельной строкой с причиной (`оснастка отсутствует`, `методика не определена`,
`производственный контроль`). Ручной ввод разрешён только с оператором,
временем, заданием и фактическим значением.

Для УБСИ текущий отчёт по ТУ содержит ЯЛК, ЯТП, питание и служебные шаги;
непокрытые требования (например, изоляция, ток канала, нагрузка 350/450 мА и
ЯВП-8) явно остаются `НЕ ПРОВЕРЕНО`. Производственная ведомость дополняет
результат поканальными значениями и отклонениями.

## Трассировка

```text
пункт ТУ → scenario step → MeasurementResult → run_id
         → stage_attempt_id → registrar.db → журнал КТМА
```

Это позволяет отделить «конкретный прогон не прошёл» от «требование ещё не
покрыто стендом».
