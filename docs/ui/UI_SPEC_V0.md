# MilTechStation · UI Specification 0.1

**Статус:** проект интерфейса, не утверждённая эксплуатационная документация.  
**Дата:** 23.11.2026  
**Область:** только интерфейс и проектирование интерфейсного API.  
**Технологический baseline:** C++17, Qt 6.8 Widgets.  
**Прототип:** apps/ui_preview/ (самостоятельное приложение, без оборудования).

## 1. Решения, согласованные для UI

1. Полная MilTechStation — универсальная инженерная среда.
2. Состав интерфейса зависит от пакета поставки, типа изделия, оборудования и разрешённых пользовательских функций.
3. Гибридная компоновка: стабильная навигация и страницы + настраиваемые док-панели в инженерной рабочей области.
4. Конечные проверки по ТУ выполняются **отдельными приложениями (ТУ-сборками)**, которые поставляются вместе с полной MilTechStation в рамках конкретной поставки.
5. ТУ-приложение не превращается в режим свободной инженерной работы. У него иной, пошаговый операторский поток.
6. На этом этапе не меняются драйверы, протоколы, сценарии, проверки, runtime и логика безопасной остановки.

## 2. Внешний вид

**Направление:** Industrial Precision — тёмный HMI, нейтральные поверхности, высокочитаемые текст/таблицы, акценты только для действия или статуса. Без декоративных приборных рамок и ложной «активности» на пустых графиках.

### Геометрия (проектные значения)

- Верхняя панель: ориентировочно 68–76 px, постоянная идентификация поставки и явная отметка режима имитации.
- Боковая навигация: 210 px в первоначальном прототипе; сокращение в компактный режим — отдельная UX-задача.
- Системный низ: краткий статус приложения/стенда без дублирования основного содержимого.
- Шаг сетки: 4 px; базовый вертикальный ритм 8/12/16/24 px.
- Основной текст: 13–14 px, подписи параметров 13–16 px, главные измеренные значения от 20 px; адаптация к DPI и физическому экрану обязательна до выпуска.
- Условная минимальная геометрия прототипа: 1120×720; целевой инженерный экран тестируется на 1366×768, 1600×900 и 1920×1080; HiDPI — отдельно.
- Важные действия с оборудованием не размещать в тесном меню или за иконкой без подписи.

## 3. Информационная архитектура

### Полная программа

| Screen ID | Заголовок | Основная информация | Основные взаимодействия |
|---|---|---|---|
| overview | Обзор | поставка, изделие, готовность, текущий запуск, события | открыть актуальное рабочее место |
| workspace | Рабочая область | тренды, параметры, мнемосхемы, диагностические панели | dock/undock, presets, выделение параметров |
| equipment | Оборудование | список ресурсов, роли, подключения, диагностические признаки | открыть подробности и разрешённое управление |
| scenarios | Сценарии | библиотека, версии, редактор, валидация | только инженерные операции; исполнение по отдельному разрешённому контракту |
| results | Результаты | история запусков, значения, технические события, документы | поиск/фильтрация/экспорт |

Навигация компактная и постоянная. Контент определяется поставкой. Отсутствие функциональности в поставке ≠ неисправность; отсутствие обязательного физического компонента ≠ скрыть компонент.

### Самостоятельная ТУ-сборка

| Screen ID | Шаг | Что обязательно видно |
|---|---|---|
| tu.prepare | Подготовка | изделие/серийный номер, однозначная версия методики, условия, готовность компонентов, блокировки |
| tu.run | Испытание | текущий пункт, объяснение действия оператора, фактические измерения, допуски, статус шага, журнал |
| tu.result | Результат | раздельные статусы изделия и исполнения, причина прерывания/ошибки, протокол и источник результата |

В ТУ-приложении нет произвольных команд по строковому capability/operation, редактирования YAML/HTML и механизма изменения критериев «на лету». Подтверждения оператора должны иметь ясную формулировку; запуск и опасные действия остаются заблокированными до действительной готовности.

### Отдельные исполняемые файлы

Концепция поставки:

- Полная программа: MilTechStation.exe (существующий исполняемый файл).
- ТУ-приложение: отдельный executable на каждую определённую конфигурацию/семейство ТУ (условное имя MilTechStation-TU-UBSI.exe).
- Общие UI-библиотеки и платформенные компоненты — переиспользуемые, без копирования методик в UI.
- Версия и состав каждой ТУ-сборки должны быть однозначно связаны с пакетом, методикой и артефактом релиза.

**Важно:** отдельных TU executable в этом коммите ещё нет. Существующий project.yaml содержит маршруты вида tu_normal, а пакетный скрипт пока упаковывает один MilTechStation.exe. Разделение здесь — будущая архитектурная граница, не реализованный факт.

## 4. Гибридное рабочее место

### Постоянная оболочка

- Header: MilTechStation, название поставки, изделие/сессия, обобщённый статус, корректная отметка SIMULATOR/DEMO.
- Navigation: пять верхнеуровневых разделов; отсутствие дополнительной иерархии по умолчанию.
- Main: переключаемые страницы; в workspace — центр для осциллограмм/мнемосхем.
- Context: контекстная панель по запросу или при выделении элемента, **не обязательна**.
- Events: журнал/инциденты может быть закреплён снизу или во вкладке.
- Никакие системные события, блокировки и критические предупреждения не зависят от видимости контекстной панели.

### Док-панели

Использовать стабильные objectName (например, uiPreview.parameters, uiPreview.events). Сохранение layout из QMainWindow::saveState(version), восстановление через restoreState(version); опционально QSettings, ключ <project_id>/<layout_version>/<operator_preset>. Профиль проекта и пользовательский layout — разные источники конфигурации.

Нужно ограничить невалидные компоновки: команда «Вернуть исходную компоновку», восстановление исчезнувших панелей, проверка границ мониторов. Нельзя закрыть последнее доступное место для критического статуса оборудования.

В прототипе реализовано сохранение позиций двух панелей по id поставки через QSettings. Переход на production должен добавить миграцию пресетов, восстановление по умолчанию и multi-monitor QA.

## 5. Контракт отображения по поставке (предложение, не runtime API)

**Новый UI manifest** описывает *представления*, но не физическую безопасность:

\`\`\`yaml
ui_schema: 1
identity:
  title: "КТМА"
  dut_label: "УБСИ"
shell:
  sections: [overview, workspace, equipment, scenarios, results]
workspace:
  default_preset: diagnostics
  panels: [parameters, events, measurements]
views:
  - id: parameters
    type: parameter_table
    source: parameter_catalog
  - id: events
    type: event_log
    source: station_events
\`\`\`

Этот YAML **иллюстративный**: его нет в существующем project loader, он не должен трактоваться как запущенная функция. В runtime уже есть ProjectDefinition::screenPaths для опциональных UI-ассетов; семантику, права и валидацию UI manifest придётся согласовать отдельным проектным решением.

Не включать в декларативную UI-модель: реальные напряжения, адреса, маршрут коммутации, хардкод конкретного протокола, скрытое разрешение на активные выходы или операторские права.

## 6. Состояния и правила визуализации

### Объекты / компоненты

| Machine state (предложено) | Видимый текст | Правило |
|---|---|---|
| unknown | Не опрошен | по умолчанию, до первой подтверждённой диагностики |
| disconnected | Нет связи | когда получен явный достоверный признак отсутствия связи |
| initializing | Подготовка | идёт операция подготовки |
| ready | Готов | подтверждена готовность в допустимом контексте |
| busy | Занят | активная операция |
| warning | Требует внимания | есть диагностическое ограничение |
| error | Ошибка стенда | есть подтверждённая ошибка оборудования |
| simulated | Имитация | данные из симулятора, не физическое измерение |

«Не получено значение» не превращать в 0; просроченное значение не отображать как текущее. Для критичных параметров нужны timestamp и quality/source в контекстном слое.

### Итоги сценария

В проектном API сценариев уже есть RunVerdict {NotRun, Ok, Fail, Incomplete, Error, Aborted}. В HMI нужны явные подписи:
- NotRun — Не выполнялось;
- Ok — Норма (по результатам выполненной методики);
- Fail — Несоответствие изделия;
- Incomplete — Не завершено;
- Error — Ошибка выполнения/стенда (конкретизируется из evidence);
- Aborted — Прервано.

**Не применять напрямую это отображение для любых других подсистем.** В КТМА для производства присутствуют отдельные доменные статусы NORM/NOT_NORM/STAND_ERROR/INCOMPLETE/STOPPED. Преобразование должно принадлежать adapter/presentation, а не произвольному QLabel.

### Критичные взаимодействия

- «Остановить выполнение» — запрос к механизму управления сценарием; НЕ маркировать как аппаратную аварийную остановку.
- Блокировки запуска отображаются как явные причины, а не просто disabled button без объяснения.
- Не перекрывать статус результата всплывающим success-toast, если сохранение отчёта не подтвердилось.
- Чужой/неподтверждённый проект не получает оборудование из КТМА по умолчанию.

## 7. Будущий Presentation API (предложение)

Существующие точки интеграции:
- ProjectDefinition / WorkflowDefinition: идентичность пакета, каталог workflows, operatorAction и политика регистрации;
- StationSession: конфигурация, busy(), runWorkflow(), requestStop(), safeStopAll(), equipment(), parameters();
- RunEvent, ScenarioRunResult, EvidenceEvent, MeasurementResult: источник событий/измерений/итогов;
- QWidget/Qt model-view — слой представления, без доступа к физическим драйверам.

Предлагаемая граница, **пока без реализации**:

\`\`\`cpp
struct UiStationSnapshot {
    QString projectId;
    QString projectTitle;
    QString dutType;
    QString serial;
    UiRuntimeState stationState;
    QList<UiEquipmentSummary> equipment;
    QList<UiParameterSample> parameters;
    QList<UiWorkflowSummary> workflows;
    UiRunSummary activeRun;
};

class IStationPresentationSource {
public:
    virtual ~IStationPresentationSource() = default;
    virtual UiStationSnapshot snapshot() const = 0;
};
\`\`\`

UI выбирает страницы и виджеты **по презентационным типам**, а не через касты к KtmaMainWindow. Внешний адаптер переводит runtime DTO в безопасные для GUI обновления. Если источник работает в другом потоке, Qt-модель обновляется исключительно в потоке GUI через queued signals/slots.

Для команд предлагается отдельный IUiCommandDispatcher с проверкой возможности и причины недоступности. Он не должен автоматически пробрасывать строковые capability/operation из любого клика. Никаких команд в ui_preview нет.

## 8. Роли и права

Роль влияет на доступ к функции, но не скрывает аварийное состояние и не меняет содержание измерения. Все UI-ограничения повторно проверяются в сервисной/доменной логике при будущей интеграции.

| Действие | Оператор ТУ | Инженер | Администратор |
|---|---|---|---|
| Смотреть состояние и результат | Да | Да | Да |
| Выполнять фиксированную ТУ-процедуру | По разрешённой сборке | По регламенту | По регламенту |
| Произвольное изменение шагов ТУ | Нет | Нет в ТУ-сборке | Нет в ТУ-сборке |
| Редактировать инженерный сценарий | Нет | При наличии права | При наличии права |
| Изменять конфигурацию оборудования | Нет | По допуску | По допуску |

Это матрица UX-намерений, не утверждение о реализованном RBAC в текущем desktop.

## 9. Тест-критерии для дизайна

1. KTMA и reference_device визуально отличаются данными поставки, но имеют одинаковые структурные правила.
2. У reference_device отсутствуют специфические действия КТМА.
3. В ТУ-приложении нет панели прямого ручного управления оборудованием.
4. Если нет канала данных, UI показывает «Нет данных», а не 0 или «Норма».
5. Состояние симуляции/демо нельзя спутать с фактическим подключением.
6. Док-панель перемещается, закрывается, восстанавливается и не переносится в layout другой поставки.
7. Клавиатурный обход есть; selected, hover и focus визуально различимы.
8. Нет принудительного требования экрана 1920×1080; содержимое не обрезается на 1366×768.
9. Состояния отказа стенда, отказа изделия, остановки и неполного выполнения не сливаются.
10. На этом UI-этапе НЕ должно появиться новых вызовов драйверов/протоколов или автоматических действий с напряжением/генераторами.

## 10. Открытые вопросы, требующие UX-проверки

- Плотность инженерных таблиц на реальных экранах стенда и в реальном освещении.
- Сколько панелей одновременно использует инженер (2/4/6+) и на скольких мониторах.
- Нужно ли показывать одновременно два экземпляра одного типа прибора и сравнение источников.
- Роль схем физических соединений: обзор оборудования или отдельная интерактивная мнемосхема.
- Формат подтверждения действий оператора на ТУ и отображение блокировок.
- Когнитивная нагрузка при длинной методике, прерываниях, повторных шагах.
- Система пользовательских пресетов и порядок восстановления после изменения поставки.

**Важное ограничение:** пока отсутствуют интервью/наблюдения реальных операторов и измерения времени выполнения задач; приведённые решения — проектные гипотезы, не результаты UX-тестов.
