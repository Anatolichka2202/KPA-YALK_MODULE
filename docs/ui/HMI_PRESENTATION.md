# MilTechStation · HMI-представления (UI design + prototype)

**Дата:** 23.11.2026  
**Статус:** реализованный UI-only редактор / viewer, контракт будущей интеграции. Реальная телеметрия и команды не подключены.

## 1. Назначение

HMI-представление — отдельный **конфигурируемый экран**, включающий компоненты визуализации для конкретной поставки/изделия. Это не системный shell, не просто график и не синоним маршрута ТУ.

Пример объекта:

- `КТМА / УБСИ → Экран HMI №1`
- Поле напряжения, поле тока, дискретный статус, шкала, тренд и контекстная подпись.
- Каждый компонент имеет устойчивый ID, геометрию, подпись, единицу и **ключ источника данных**.
- Поставке позволено включать несколько HMI-представлений; в текущем прототипе — два на вариант поставки, переключаемые в редакторе и рабочей области.

**Целевое разделение:**

| Слой | Ответственность |
|---|---|
| UI shell | выбор поставки, навигация, окна, рабочее пространство |
| HMI document | декларативная композиция элементов, привязки, размеры и оформление |
| HMI renderer | рисует виджет по модели данных; различает missing/invalid/stale/simulated/live |
| Presentation data source | преобразует реальные источники в типизированные read-only данные с качеством и временем |
| Command dispatcher | отдельно проверяет полномочия, блокировки и возможность реальной операции |
| Runtime | владеет оборудованием, протоколами, сценарием, безопасностью и записью результатов |

Схема **не** даёт право выполнять команду. Наличие control/widget также не подтверждает доступность физического устройства.

## 2. Реализовано в UI Preview 0.4

Файлы:
- `apps/ui_preview/hmi_presentation.h/.cpp` — `HmiDocument`, `HmiCanvas`, `HmiDesignerPage`, `HmiReadOnlyPanel`.
- `apps/ui_preview/hmi/ktma.json` — демонстрационный экран КТМА.
- `apps/ui_preview/hmi/reference_device.json` — независимый экран эталонного имитатора.
- `apps/ui_preview/manifests/ktma.json` и `reference.json` — включение экрана `hmi` и виджета `hmi`.

В полной MilTechStation появляется раздел **HMI-представления**; в **Рабочей области** — его read-only отображение на общем `HmiDocument`. Изменения конструктора немедленно отражаются в viewer.

### Библиотека элементов (6 видов)

| Вид | UX-поведение и визуализация | Данные |
|---|---|---|
| `label` | постоянная подпись / обозначение | не требует binding |
| `numeric` | число с единицей, исходное состояние «—» | read-only key |
| `status` | дискретное/перечислимое состояние текстом | read-only key |
| `bar` | горизонтальная шкала | read-only key; в production нужны диапазон и физическая размерность |
| `trend` | график отсчётов, пустое состояние | массив/поток значений; production timestamps обязательны |
| `command` | визуальное место управляющего элемента | **всегда заблокирован** в прототипе |

Редактор позволяет:
- создавать, дублировать, переименовывать и удалять отдельные HMI-экраны;
- синхронно выбирать HMI-экран в редакторе и инженерной рабочей области;
- сохранять и загружать целый набор HMI-экранов с проверкой принадлежности поставке;
- выбирать демонстрационный ключ данных из списка и видеть предупреждение о несовместимом типе;
- добавлять элемент из палитры;
- выделять и перетаскивать его по полотну `960 × 540`, с привязкой к сетке 20 px;
- править заголовок, ключ привязки, единицу, координаты и размер;
- удалять элементы;
- переключать редактор, просмотр без данных и синтетический предпросмотр;
- экспортировать и импортировать HMI JSON через диалог файлов.

Файл проекта HMI содержит `schema=1`, `format=miltech.ui.hmi.preview`, `delivery_id`, размер полотна и массив элементов. Применяется валидация разрешённых типов, уникальности ID, размера и границ, принадлежности поставке; при ошибке импорт не меняет предыдущий документ.

Ограничение: это **черновик UI, не эксплуатационная мнемосхема**. Редактор не создаёт physical wiring map, не знает фактической мощности/тока приборов и не исполняет никакие команды.

## 3. Правила проектного UX

- Базовый экран не должен изображать физический объект в состоянии «ВКЛ», если это неизвестно.
- Режим `Предпросмотр · без данных` показывает «—», «Неизвестно», «Нет данных» для динамических полей.
- Режим `Предпросмотр · синтетика` использует **только** явно указанные `ui.demo.*` ключи и маркируется как UI DEMO.
- Ключ, введённый вручную, не превращается автоматически в существующее измерение.
- Никакого зелёного цвета «Норма» без исполнения и оценки реальной методики.
- Командные элементы отображают явную блокировку; будущая интерактивность возможна лишь через отдельный API и контроль полномочий.
- Для корректных HMI нужный статус должен быть на экране, а не только в журнале.
- Геометрия фиксирована логическими координатами; scroll/zoom/responsive QA следует проработать отдельно. Нельзя гарантировать читаемость на сенсорных экранах по одной offscreen-сборке.

## 4. Целевой API привязок (НЕ реализован)

Презентационная модель не должна знать конкретный тип железа:

```cpp
enum class HmiQuality { Missing, Invalid, Stale, Simulated, Valid };

struct HmiSample {
    QString key;
    QVariant value;
    QString unit;
    HmiQuality quality;
    QDateTime measuredAtUtc;
    QString sourceResource;
    QString sourceCapability;
};
```

Каждому HMI-виджету требуется контракт данных (тип/единицы, диапазон, формат, актуальность). Привязка к `IParameterSource` / `ParameterRepository` или другой существующей подсистеме должна идти через отдельный адаптер **только чтения**, передающий обновления Qt-моделям в GUI-потоке. При потере источника — `stale` либо `missing` согласно подтверждённой политике; нельзя продолжать показывать устаревшее значение как актуальное.

**Для активных команд нужен отдельный контракт:**
- роль и разрешённое действие в конкретной поставке;
- предусловия, ресурс, блокировки и опасность операции;
- явное действие пользователя и подтверждение, когда требуется;
- раздельные `requested`, `acknowledged`, `verified`, `failed`;
- аудит вызова и отказа;
- никогда не инициировать при загрузке экрана, автопредпросмотре или изменении компоновки.

## 5. Что предстоит после UI-only

1. Публикация, версионирование и миграции наборов HMI-страниц.
2. Grid/canvas редактор с копированием, multi-select, выравниванием, слоями и undo/redo.
3. Реестр визуальных компонентов, в том числе специализированных приборных виджетов по capability.
4. Источники/привязки из реального каталога, а не ввод ID вручную.
5. Визуальная валидация несоответствия типа, единиц, диапазонов и устаревания.
6. HMI-мнемосхемы электрических/сетевых связей на основе подтверждённых файлов поставки.
7. Правила наследования и включения HMI в ограниченный TU executable.
8. UX тесты с аппаратной и симуляционной моделью, multi-monitor/HiDPI и доступностью.

## 6. Проверка

Отдельная CI-сборка `MilTechStationUiPreview` должна:
- находить `HmiDesignerPage` и `HmiReadOnlyPanel` в полной станции;
- проверять, что редактор и HMI-док отсутствуют в операторском ТУ;
- добавлять элемент и проверять синхронность между document и viewer;
- проверять режим без данных и синтетический предпросмотр;
- проверять JSON roundtrip и отказ импорта документа другой поставки;
- проверять границы перетаскивания.

Рендеринг HMI-представления в offscreen CI **не** доказывает его эргономику. Нужна визуальная приёмка на реальных мониторах.
