# MilTechStation · UI Component Catalog 0.2

**Статус:** рабочая версия каталога Qt Widgets UI, не документация к физическому оборудованию.  
**Дата:** 23.11.2026  
**Реализация:** `apps/ui_preview/components.h`, `components.cpp`, `theme.qss`.

## Назначение и граница

Здесь описаны **визуальные компоненты**, их интерфейсное поведение и источники данных. Компонент не хранит протокол прибора, не отправляет команды и не присваивает вывод «НОРМА» без доменного результата.

Дизайн-система общая для полной программы и ТУ-сборок, но их компоновки независимы.

### Имена для автоматизации

- `ui.variantSelector`: переключение демонстрационной поставки.
- `ui.workspaceHost`: локальный хост инженерных док-панелей.
- `uiPreview.parameters` / `uiPreview.events`: стабильные dock IDs.
- `ui.parameters`, `ui.parameterSearch`, `ui.parameterTable`: таблица и поиск.
- `ui.trendCanvas`, `ui.waveformSelector`, `ui.syntheticToggle`: графики.
- `ui.equipmentOverview`, `ui.equipmentList`: браузер оборудования.

**Не использовать эти objectName как контракт управления оборудованием.** Они предназначены исключительно для UI-тестов/автоматизации.

## 1. Таблица параметров

Колонки первого прототипа: ПАРАМЕТР, ЗНАЧЕНИЕ, ЕД., ИСТОЧНИК, КАЧЕСТВО. Фильтрация — по имени и коду параметра. Данные существуют только в `ParameterFixture`. Нет имитации реального времени: в тестовых fixtures отсутствует подтверждённый timestamp измерения.

### Обязательное поведение для следующей интеграции

- Различать `missing`, `stale`, `invalid`, `simulated`, `valid`.
- У показываемого значения — нормализованная единица, происхождение, timestamp и признак качества.
- Нулевое значение *не является* заменой отсутствующего измерения.
- Производственный список может быть многострочным, фильтруемым и сортируемым без перенаправления исходной телеметрии через GUI.
- Контекстный просмотр источника должен раскрывать физический ресурс / capability только после разрешения конфигурации.
- Для огромного количества каналов необходимы QAbstractItemModel/delegate и измерение стоимости обновлений; **не** обновлять каждую ячейку 100 раз в секунду без профилирования.

## 2. Тренд и синтетическая пила

Две визуализации:
- Плавный сигнал (математический пример).
- Счётчик 0…1023 (три синтетических пилообразных периода).

Это **не тест ЯФК, не эхо RS-485 и не доказательство прохождения данных через Орбиту**. Пила служит только проверкой рендера, шагов шкалы и удобства визуального контроля формы. В реальной поставке ЯФК источник, значения, длительность, сброс, достоверность, сравнение TX/RX и критерий заключения определяет методика/драйвер, а не картинка.

### Следующий UX-контракт для графиков

- Оси с единицами и явно указанным временем/номером отсчёта.
- Показ качества сигнала, сбросов/разрывов и интервалов без данных.
- Синхронизация нескольких источников без искусственного совпадения timestamps.
- Выбор канала и диапазона с доступным управлением клавиатурой.
- Снимок графика при сохранении результата с указанием происхождения данных.
- Производственный график не рисуется по UI-фикстурам.

## 3. Логическая схема

Текущая цепочка `Источник → Коммутация → Изделие` для КТМА — композиционная иллюстрация **без утверждений о физической проводке и коммутационных состояниях**.

Нужны два отдельных режима в будущем:

1. **Логические ресурсы:** из `ProjectDefinition` и профиля оборудования.
2. **Физическая схема/маршрут:** только на основании подтверждённой документации конкретной поставки, с указанием достоверности, актуального состояния коммутации и источника.

Не рисовать зелёные «замкнутые цепи», пока нет реального readback оборудования.

## 4. Состояние приборов

Первичное состояние карточки всегда **НЕ ОПРОШЕН**, пока в presentation не получены верифицированные данные. Карточка показывает идентификатор, назначение, статус и *причину недоступности*, а не произвольную кнопку «Подключить». Для аппаратных команд потребуется отдельная модель разрешений и межблокировок.

Карточка конкретного устройства вправе предоставлять специфические controls только через UI-фабрику capability views после проверки поставки.

## 5. Журнал событий

Пока журнал пишет только намеренно отделённые события интерфейса с префиксом `UI ·`. Это не EvidenceEvent и не технический журнал стенда. Запись ограничена 100 UI-событиями.

Production log должен показывать time/source/severity/resource/context и корректный порядок событий, но **не** поглощать immutable evidence, необходимую для итогового протокола.

## 6. Правила вложенной док-компоновки

Главная рама включает Header + Navigation + Main + Footer. В разделе Workspace Main содержит свой QMainWindow и только он владеет док-панелями.

Почему это важно: инженер может вынести журнал на второй экран, не перенося вместе с ним навигацию и системный статус. Изменение docking state не должно быть частью изменения физического режима.

- При смене поставки layout сохраняется под `layouts/<project_id>/v2`.
- При смене раздела docking state сохраняется, панели скрываются вне workspace.
- `Исходная компоновка` восстанавливает стандартные области.
- В ТУ-сборке docks вообще отсутствуют.
- Миграция layout и работа с off-screen floating dock при изменении числа мониторов требуют ручной QA.

### Открытый риск

У Qt QDockWidget floating mode — отдельное окно; надо проверить поведение при скрытии родительского workspace, переходе на TU и смене экранов. Это нельзя считать закрытым только по результату offscreen-smoke.

## 7. Минимальная QA-матрица v0.2

| Проверка | Автоматически | Человек/визуальная проверка |
|---|---|---|
| Сборка Qt 6.8+ | CI | не требуется |
| КТМА ↔ reference ↔ TU, число экранов | smoke | проверить содержание |
| Сортировка/поиск таблицы | smoke: поиск | проверить читабельность колонок |
| Выбор формы тренда, отключение синтетики | smoke | проверить пилу и empty state |
| Изоляция TU от инженерных панелей | smoke | проверить навигацию |
| Dock restore/layout | частично | требуется drag/floating/multi-monitor |
| 1366×768 / 1600×900 | offscreen PNG | требуется анализ скриншотов на обрезание |
| Настоящая телеметрия/аппаратная безопасность | **не входит в UI-этап** | аппаратные испытания отдельным этапом |

### Первые UX-задачи для наблюдения

- Оператор видит блокировку ТУ и понимает причину без просмотра технических логов.
- Инженер отличает синтетическую пилу от физической телеметрии с первого взгляда.
- При 4+ приборах инженер находит неисправный компонент и источник параметра.
- Три синтетических периода пилы читаемы и при 1366×768, и в закреплённой док-компоновке.
- После изменения поставки не остаются чужие контекстные команды/вкладки.

**Ограничение:** интервью и наблюдения с операторами не проводились; UX-предположения нельзя объявлять подтверждёнными до тестирования.
