# MilTechStation · API & UX Research Log 0.1

**Дата:** 23.11.2026. Статус: начальный анализ источников + аудит API действующего кода.  
Ссылки ниже — первичные документы Qt, профильные HMI-стандарты и UX-источники; это не подтверждение, что проект уже удовлетворяет требованиям.

## 1. Исходная техническая среда

Проверено в исходниках KPA-YALK_MODULE:

- Основной desktop: Qt 6.8, C++17; QMainWindow/QStackedWidget/QDockWidget и QSS уже используются.
- apps/desktop/main.cpp запускает UniversalMainWindow и задаёт минимум 1600×900.
- UniversalMainWindow наследует KtmaMainWindow; KtmaMainWindow наследует MainWindow. Это несовместимо с целью полностью независимой UI-оболочки без технического долга.
- apps/desktop/resources/styles.qss, палитра main.cpp и локальные стили разных страниц конфликтуют концептуально: нет единственного места определения цветов и типографики.
- ProjectDefinition уже содержит id/title/version/workflows/dutTypes/screenPaths. Поля screenPaths есть, но декларативный UI manifest ещё не описан.
- StationSession — нейтральная точка владения оборудованием и жизненным циклом; его API runWorkflow(), invokeManual(), requestStop(), safeStopAll() нельзя вызывать из декоративного компонента.
- Существующие TU workflow (например, tu_normal) в projects/ktma/project.yaml и скрипт package_stand_win11.ps1 ещё ориентированы на одну основную программу, а не отдельный ТУ executable.

## 2. Исследование Qt API

### A. Компоновка: QMainWindow + QDockWidget — выбрано для v0

Документация:
- [QMainWindow Qt 6.8](https://doc.qt.io/qt-6.8/qmainwindow.html).
- [QDockWidget Qt 6.8](https://doc.qt.io/qt-6.8/qdockwidget.html).
- [QSettings Qt 6.8](https://doc.qt.io/qt-6.8/qsettings.html).

Подтверждено: QMainWindow поддерживает вложенные/вкладочные dock-области и saveState/restoreState. Для стабильного восстановления необходимо давать QDockWidget уникальные objectName. Длинные сложные dock layouts могут быть менее понятны операторам: это аргумент сохранять их **только в инженерном контуре**, а не в ТУ-приложении.

Практическое решение: QMainWindow — внешний shell; центральный QWidget — фиксированный header/rail/stack; docks только в engineering workspace. В прототипе уже есть пара док-панелей и сохранение по id поставки.

Риски/проверка: floating windows на двух мониторах, возврат в видимую область после смены дисплея, минимальные размеры графиков, быстрое восстановление первоначальной компоновки, стабильность objectName при обновлении версии.

### B. Навигация: QStackedWidget — выбрано для shell

[QStackedWidget Qt 6.8](https://doc.qt.io/qt-6.8/qstackedwidget.html). Он показывает одну страницу за раз, без необходимости одновременно создавать полноценные бизнес-модули. Смена верхнеуровневого экрана не должна запускать аппаратную операцию.

Риск: нельзя считать stack индексом для runtime workflow или хранить permissions в номерном порядке; понадобятся стабильные screen id и маршрутизатор.

### C. Таблицы: model/view — для production, не QTableWidget в высокочастотном мониторинге

[QAbstractItemModel Qt 6](https://doc.qt.io/qt-6/qabstractitemmodel.html),
[QStyledItemDelegate Qt 6.8](https://doc.qt.io/qt-6.8/qstyleditemdelegate.html).

Qt запрещает модифицировать model-related API из произвольного рабочего потока, если модель живёт в GUI thread. Для production: QAbstractTableModel/QTableView, компактные пачки изменений, отдельные роли для quality/stale/units/timestamps, delegates для индикации. В прототипе используется QTableWidget **только для статических UI-фикстур**.

Не делать каждое поступившее измерение отдельным emit+repaint без управления нагрузкой. Частоту обновления отображения определять профилированием, а не приравнивать к частоте телеметрии. Не терять исходные данные — интерфейсное прореживание отличается от записи первичного потока.

### D. Qt Widgets vs Qt Quick/QML

[Qt UI Technologies 6.8](https://doc.qt.io/qt-6.8/topics-ui.html),
[Qt Widgets 6.8](https://doc.qt.io/qt-6.8/qtwidgets-index.html).

Выбор v0: **Widgets**. Аргументы — существующая база, QCustomPlot, native dock behavior, отсутствие необходимости дублировать уже работающие интеграции. Qt Quick может быть полезен впоследствии для сложных схем и сенсорных панелей, но переход всей программы сейчас не обоснован исследованием. Qt допускает гибридную архитектуру; решения по конкретным view нужно принимать после UX-тестов и оценки нагрузки.

### E. Accessibility и горячие клавиши

[Qt Accessibility](https://doc.qt.io/qt-6/accessible.html),
[QWidget accessibleName](https://doc.qt.io/qt-6/qwidget.html).

Нужно именовать интерактивные элементы, различать hover/focus/selected, обеспечить keyboard navigation и не передавать смысл одним только цветом. В прототипе есть accessibleName на навигации, переключателе сборки, таблице и Alt+1…5. Полноценная проверка клавиатуры/скринридера ещё не проводилась.

## 3. UX и HMI: исследованные принципы

### ISA-101 / IEC 63303

Источники:
- [ISA-101 Series](https://www.isa.org/standards-and-publications/isa-standards/isa-101-standards).
- [IEC 63303:2024, официальный каталог](https://webstore.iec.ch/en/publication/66298).

Они описывают подход к системам HMI для автоматизации и жизненный цикл проектирования/эксплуатации. Для MilTechStation это **профессиональный ориентир**, не автоматически применимый сертификационный перечень: испытательная станция не во всём эквивалентна процессному диспетчерскому HMI. Полные платные стандарты здесь не анализировались, соответствие стандартам не заявляется.

Вывод для UI:
- сначала показывать отклонения и ограничения, затем вторичные декоративные показатели;
- системные статусы и контекст должны быть доступны во время выполнения операции;
- интерфейсные состояния и правила их появления нужно документировать, а не кодировать случайными цветами;
- экранная структура и документация должны переживать добавление следующей поставки.

### Usability heuristics для сложных инженерных систем

Источники:
- [NN/g: 10 usability heuristics](https://www.nngroup.com/articles/ten-usability-heuristics/).
- [NN/g: heuristics in complex applications](https://www.nngroup.com/articles/usability-heuristics-complex-applications/).
- [NN/g: error messages](https://www.nngroup.com/articles/error-message-guidelines/).

Применение к MilTechStation:
1. Видимость состояния системы: оператор различает **нет связи, не опрошено, запуск, ошибка, имитация**.
2. Узнавание вместо вспоминания: кнопка и выбранная методика подписаны, критичное состояние не скрыто в логах.
3. Предотвращение ошибок: нельзя перепутать изучение сигнала и фактическую команду питания.
4. Контроль пользователя: понятная остановка процедуры и причины невозможности запуска; отдельный механизм безопасной остановки.
5. Минимизация нагрузки: операторский ТУ-поток не показывает редакторы сценариев, HTML-шаблоны и отладочные команды.

### Контраст/цвет как измеримый критерий

Источники:
- [WCAG 2.2 — Contrast minimum](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum).
- [WCAG 2.2 — Use of color](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html).
- [WCAG 2.2 — Target size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum).

WCAG сформирован для web-контента; для нативного Qt desktop используем **измеримые UX-ориентиры**, а не заявляем формальную совместимость. Для обычных текстов целевой контраст >=4.5:1, для крупных >=3:1; проверять реальные соседние сочетания цветов и состояния disabled/focus. Целевые размеры кликабельных контролов и расстояния между ними тестировать под мышь, перчатки (если требуются), экранный DPI и реальные условия стенда.

Нельзя кодировать «НОРМА» только зелёным. На любом критичном индикаторе необходимы текст/форма/дополнительный сигнал.

## 4. Исследование потребностей и сценариев

Это **гипотезы на основании архитектуры ПО и пользовательского описания поставок**, не проведённое полевое исследование.

| Персона | Цель | Основной UX-риск | Предлагаемое исследование |
|---|---|---|---|
| Оператор ТУ | без ошибки провести изделие по методике | пропуск шага; неверный SN; ложный успех | 5–8 модераторских проходов на имитаторе, разбор ошибок |
| Инженер стенда | видеть сигналы и быстро локализовать неисправность | перегруженность окнами/непонятные источники | контекстное наблюдение, сценарии «нет данных»/«два прибора» |
| Разработчик сценариев | редактировать и отлаживать методики | смешение опубликованной и черновой версии | тест «найти, изменить, проверить, вернуться к исходной» |
| Ответственный за выпуск | получить подтверждённый протокол | путаница NOT_NORM / STAND_ERROR | проверка понятности формулировок на примерах |

Тестовые задачи, пригодные для следующего цикла:
- за 10–15 секунд определить, почему запуск недоступен (показатель-гипотеза, не гарантированный норматив);
- без подсказки отличить физическое значение от результата симулятора;
- открыть график нужного канала и закрепить журнал справа;
- сменить поставку и убедиться, что конфигурация оборудования не «унаследована» от предыдущей;
- различить «НЕ НОРМА» изделия, ошибку стенда и неполный протокол.

Успех измерять: процент правильных решений, количество ошибок, время выполнения, задержки на чтение, обращения к журналу и субъективную сложность после задачи. Не оптимизировать время ценой безопасности.

## 5. Контроль интерфейсных API при последующей интеграции

**В имеющемся runtime**:
- ProjectDefinition: project.h, включая fields workflows/screenPaths;
- StationSession: station_session.h (busy, configure, runWorkflow, invokeManual, requestStop, safeStopAll);
- ScenarioRunResult/RunVerdict/RunEvent/EvidenceEvent: scenario.h.

Возможный новый API (не реализован сейчас):

| Направление | Что передаётся | Предполагаемый потребитель |
|---|---|---|
| Delivery → UI | стабильный project id, предложенные страницы, views | ShellNavigationModel |
| Runtime → UI | снапшот готовности/ресурсов и diagnostic quality | StationPresentationModel |
| Measurements → UI | value/unit/timestamp/quality/source, без отсутствующих значений | ParameterTableModel / PlotSeriesModel |
| Scenario → UI | step tree, progress, evidence, final verdict | ScenarioProgressModel |
| UI → domain (позже) | типизированная разрешённая команда, контекст, причина отказа | UiCommandDispatcher |

Сам UI должен быть **потребителем** этих данных, но не владельцем StationSession, EquipmentRegistry, приборов и потоков сценария. Обновления модели, живущей в GUI thread, должны поступать через механизм, безопасный для Qt thread affinity.

## 6. Backlog исследования, по приоритетам

**P0 — до подключения к реальным устройствам**
- инвентаризация всех текущих окон и потоков работы КТМА;
- матрица состояний/источников и права на действия;
- детальное ТУ flow, сообщения блокировок, правило достоверности результатов;
- keyboard/focus, контрасты, читаемость на стендовом мониторе;
- отрицательные сценарии: отвал USB/Ethernet, отсутствие значения, прерывание, частичный результат.

**P1 — для рабочего инженерного UI**
- таблицы с большим числом каналов, фильтры/группировки, источники значений;
- сравнение нескольких приборов, пресеты dock-layout;
- стоимость repaint и latency на предполагаемой частоте телеметрии;
- поведение нескольких мониторов и смены DPI.

**P2 — до UI API freeze**
- декларативный manifest и версия схемы;
- сценарии миграции сохранённой компоновки между релизами;
- формальная карта UX-компонентов + номенклатура состояний;
- доступность/справка, локализация, темы освещённости.

## 7. Статус доказательств

- Проверено документами Qt: перечисленные классы и их основные функции.
- Проверено кодом MilTechStation: текущее Qt окружение, проектный runtime, наследование KTMA, workflows.
- Исследовательская гипотеза: новая IA, UI manifest, дизайн-токены, размерности, роли и структура отдельных TU executable.
- **Не проверено:** сборка нового прототипа на Qt 6.8, запуск GUI под Windows, интервью с операторами, соответствие IEC/ISA, аппаратное взаимодействие.

Исследование должно сопровождаться логом изменений: что подтверждено API, что UX-тестом, а что остаётся гипотезой.
