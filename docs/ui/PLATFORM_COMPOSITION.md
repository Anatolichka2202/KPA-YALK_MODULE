# MilTechStation · сборный UI, конфигуратор ТУ, администрирование

**Решение:** 23.11.2026. Статус: архитектурные требования и UI-прототип, backend реализации пока нет.

## 1. Основное требование: станция собирает HMI из компонентов

Полная MilTechStation — приложение-оболочка. Поставка предоставляет описания видимых экранов и доступных UI-панелей, оборудование, рабочие процессы и каталоги. Состав экранов **не прошивается** в один конкретный класс КТМА.

Два разных объекта, которые нельзя смешивать:

1. `ProjectDefinition` — существующий runtime-контракт пакета проекта: идентичность, сценарии, приборный профиль, каталог, пути UI assets.
2. `UiComposition` — **предлагаемый UI-контракт**: видимые разделы, группы навигации, модульные панели и их размещение.

В приложении-прототипе `apps/ui_preview/ui_composition.h/.cpp` уже реализован отдельный парсер UI-манифеста. В `apps/ui_preview/manifests/` содержатся **три изолированных UI-фикстуры**:

- `ktma.json` — полная станция, инженерная рабочая область с параметрами, событиями, трендом и топологией;
- `reference.json` — тот же каркас, другой набор UI-компонентов, **без** топологии;
- `tu_ubsi.json` — три обязательных операторских экрана без инженерных и сервисных инструментов.

Парсер проверяет версию схемы, известные screen/component IDs, дубликаты, обязательные страницы. Это **не** проверка аппаратной безопасности, прав доступа, методики ТУ и не загрузка production-пакета.

### Целевая композиция

```text
Delivery package (project.yaml)
  ├─ station hardware profile
  ├─ product / scenario catalog
  ├─ workflow definitions
  └─ UI manifest (versioned)
       ├─ navigation modules
       ├─ engineering panels
       ├─ equipment-specific views
       └─ default workspace layout
                    |
              UI Composition Engine
                    |
              Full Station Shell
```

UI-модуль регистрирует `screen_id`, фабрику виджета, тип модели представления, требования к данным и **идентификаторы разрешений**. Проект может включить модуль в композицию, но само наличие UI-модуля не даёт права вызывать оборудование. Для будущих нештатных (third-party) UI модулей потребуются версия ABI/API, контракт ресурсов и политика подписывания/загрузки — их пока нет.

## 2. Конфигуратор ТУ: что должна уметь станция

Это **функция конфигурационного ядра**, а не нарисованная кнопка «Экспорт».

Редактор и публикация сценариев частично уже представлены в `apps/desktop/scenario_visual_editor.*`. Существующие workflow лежат в `projects/<project>/workflows/*.yaml`. **Сейчас нет** подтверждённой операции «создать отдельный исполняемый ТУ-продукт» — скрипт `scripts/package_stand_win11.ps1` работает с `MilTechStation.exe`.

### Предполагаемый workflow конструктора

| Стадия | Ответственность конфигуратора |
|---|---|
| Создать проект ТУ | ID, наименование, изделие, версия, производственная поставка |
| Составить/выбрать методику | Пункты, условия, параметры, критерии, версия сценария |
| Назначить оборудование | Только валидированные capabilities, роли ресурсов, физические профили |
| Собрать операторский UI | Обязательные этапы Подготовка / Испытание / Результат + разрешённые представления |
| Проверить | Полнота методики, статическая проверка ресурсов, сценарии ошибок/остановки, симуляция |
| Зафиксировать | Immutable snapshot методики, ресурсов, UI-манифеста, отчётного шаблона и версии платформы |
| Сформировать релиз | Отдельный .exe с фиксированной идентичностью и зависимостями, ресурсами, проверкой целостности |
| Передать в поставку | Комплект приложения, библиотек, лицензируемых компонентов и документации, контрольная сумма |

### Минимальные сервисные контракты (проектирование, не существующий API)

```cpp
struct TuPackageSpec {
    std::string packageId;
    std::string version;
    std::string projectId;
    std::string workflowId;
    std::string scenarioRevision;
    std::string uiManifestRevision;
    // immutable references to catalog, equipment profile and report template
};

struct TuBuildDiagnostic {
    std::string code;
    std::string message;
    bool blocking = false;
};

class IDistributionConfigurator {
public:
    virtual ~IDistributionConfigurator() = default;
    virtual std::vector<TuBuildDiagnostic> validate(const TuPackageSpec&) = 0;
    virtual std::string buildPackage(const TuPackageSpec&) = 0;
};
```

Это **схема контракта**, без сборщика и не для немедленного включения в station-core. Сервис сборки должен воспроизводить конкретную версию ТУ и фиксировать происхождение результата.

Нужна не «компиляция нового Qt интерфейса из YAML», а **отдельный запускаемый host/launcher**, собранный с фиксированным пакетом и подключающий только те компоненты/функции, которые включены в релиз. Методика и проверки остаются в общей платформе; не клонировать исходники Qt окон для каждой новой ТУ.

Ограниченный HMI **не заменяет** авторизацию в доменном слое. Даже если скрыты редакторы и ручные команды, в ТУ-сборке должна быть аппаратная проверка допустимости действий.

### Прототип конструктора

Экран `ui.configurator` в полной станции умеет локально менять ID, название, версию, выбрать демонстрационную методику и включить/выключить опциональные UI-представления. Получается **предпросмотр JSON черновика** с полями `backend_validated=false` и `executable_built=false`. Кнопка формирования EXE **намеренно отключена**.

## 3. Административный функционал

Отдельный контур со своей навигацией в полной станции. Короткий путь из основной программы, без примешивания к операторскому проведению ТУ.

| Раздел | Функции |
|---|---|
| Станция | идентичность комплекса, активный профиль, версии, подключения, параметризация |
| Оборудование | состав, привязки, диагностика плагинов, источники, состояния ресурсов |
| Поставки | установленные пакеты, активация, версии, обновления и откат |
| Доступ и аудит | пользователи, роли, права на операции, журнал административных изменений |

Существующий `StationAdminDialog` **уже** показывает профиль, подключения, оборудование/ресурсы и диагностику в режиме чтения. Это реальная точка переиспользования. **Управления пользователями/ролями, установкой пакетов и аудитом административных изменений в нём нет**; эти требования относятся к будущему service/backend. UI-прототип `ui.administration` воспроизводит четыре раздела и явно помечает состояние «не подключено», не выдавая их за реализованные.

## 4. Границы безопасности и ответственности

- `UiComposition` отвечает за отображение. `ProjectDefinition` и `StationSession` определяют доступные ресурсы, операции и исполнение. Реальная авторизация потребует отдельного сервиса и проверки при каждом действии.
- `IDistributionConfigurator` отвечает за проверку и упаковку, не за рисование окна. Публикация ТУ не должна происходить только потому, что UI заполнен.
- Администрирование не выполняет скрытых команд активным выходам при открытии страницы.
- Установка/изменение профиля требует отдельной валидации и журналирования. Для опасных изменений — отказ, когда станция занята; политика и подтверждения определяются ядром.
- Изменение компоновки экрана не изменяет состояние аппаратуры.

## 5. Приёмка следующего этапа

1. Проект может включать и исключать разрешённые UI-модули декларативно, без изменений C++ кода основной оболочки.
2. Полная станция может содержать служебные разделы «Конфигуратор» и «Администрирование».
3. ТУ-сборка имеет только операторские экраны, и в её runtime запрещены все непредусмотренные действия независимо от UI.
4. Конфигуратор проверяет согласованность проектной конфигурации, формирует неизменяемый комплект, отдельный executable и подтверждаемый manifest релиза.
5. Администратор может диагностировать конфигурации и устанавливать/откатывать версии с аудитом, оператор не имеет таких прав.
6. Ошибки стенда и изделия, сохранение протоколов и безопасное завершение испытаний не теряют существующие инварианты.

## 6. Реализовано / ещё не реализовано

| Область | UI-прототип | Runtime |
|---|---|---|
| Декларативная навигация | реализовано на JSON-фикстурах | интеграции с project.yaml нет |
| Набор панелей по поставке | частично реализовано (в том числе опциональная схема) | нет регистра произвольных поставляемых виджетов |
| UI конструктора ТУ | редактируемый черновик + предпросмотр | нет валидатора сборки и упаковщика EXE |
| UI администрирования | четыре раздела, диагностические заглушки | у existing StationAdminDialog есть только read-only часть |
| Утверждение ТУ/контроль целостности | задокументировано | не реализовано |
| Авторизация и управление учётными записями | макет | не подключено |

**Текущая работа остаётся UI-only.** Состояние CI сообщается отдельно; макет не применяется к рабочим стендам.
