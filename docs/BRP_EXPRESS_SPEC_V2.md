# БРП · экспресс-приложение испытаний — функциональная спецификация

**Ревизия:** v0.2 · **26.11.2026** · утверждённый экспресс-объём для постановки задач  
**Репозиторий:** `Anatolichka2202/KPA-YALK_MODULE` · **ветка:** `tu_brp_minimal` (`9070d7784293dd2aee7dcd1bea2979bbe34acb6d` при сверке)  
**Источники кода:** текущая ветка, `rebuild/tu-minimal-clean`, отдельные реализованные приёмы из `master` (`ba99f5d9a2387add438749f575a5d380eed5e1a4`).  
**Статус:** рабочая спецификация для реализации в `tu_brp_minimal`. Публикация документа не подтверждает выполнение аппаратных испытаний.

> **Принцип проекта:** быстро получить функциональное приложение БРП на уже работающем C++/Qt коде. Разрешены локальные решения, жёстко заданные карты и временные подпорки. Никакого нового ядра, универсальной архитектуры, конфигуратора, отдельной службы или переноса методик УБСИ.
>
> **Полное отделение:** задачи `R-*`, `INT-*`, `UI-*` принадлежат **MilTechStation** и не являются ни родительскими, ни блокирующими задачами экспресс-БРП.

## 1. Problem Statement

Ветку `tu_brp_minimal` уже можно использовать для инструментальной диагностики БРП: приём/декодирование кадров «Орбиты», RS-485, ЯСМ с внешним тестом, операции АКИП/ИСД/В7, чтение конкретных M16-адресов и подготовка протокола существуют. Но основной маршрут испытания не соединяет большинство этих операций. Оператор вынужден пользоваться ручной диагностикой и отдельными процедурами. Нужно **сшить готовое** в одно быстро работающее ТУ-приложение, не теряя существующую ручную трассировку.

## 2. Solution

Оператор запускает приложение БРП, проверяет доступность оборудования, задаёт изделие и выполняет последовательный сценарий. Внутри сценария используются работающие аппаратные вызовы и проверки. Там, где воздействие подключено к ИСД, оно выполняется автоматически; иначе оператор получает ручное действие, после которого станция самостоятельно проверяет телеметрию.

В основной работе присутствуют **два способа эксплуатации**:

1. **Прогон ТУ** — строгая последовательность с результатами, повторами, сервисным принудительным ОК, диагностикой отказов и сохранением истории.
2. **Ручная трассировка/диагностика** — текущий инженерный экран сохраняется и может расширяться: M16, M8 как универсальная возможность декодера, графики, адресные профили, захват, действия ИСД, ЯСМ, тесты отдельных сигналов. **Он остаётся доступен в текущих инженерных сборках**; в будущем его можно исключить при сборке без удаления рабочего кода.

### 2.1 Отдельная кнопка «ББ ПР — выдать сигнал»

- Оператору нужна **явная активная команда выдачи сигнала ББ ПР**, а не только строка наблюдения `ББ ПР` в телеметрии.
- Кнопка доступна на инженерном/ручном экране; во время соответствующего шага основного прогона допускается использовать то же действие через имеющийся интерфейс шага. Не создавать отдельный экран ради кнопки.
- Нажатие инициирует **реальную, подтверждённую для стенда выдачу сигнала** через установленный способ управления; после действия виден статус исполнения и значение/состояние по соответствующему адресу M16, если поток активен.
- Не придумывать адрес ИСД, величину, направление сигнала, команду или физическую коммутацию: эти данные сверяются по фактической реализации/разводке. **По состоянию проверенного кода подтверждено только наблюдение ББ ПР на `M16P1A10B60C21T01`; механизма выдачи именно этого сигнала не найдено.** До подтверждения маршрута аппаратная выдача недоступна, причина видна оператору; тест не ставит ОК за одно нажатие кнопки.
- Для выданного воздействия есть штатное отключение/снятие по допустимой последовательности и запись в журнал; нельзя оставить сигнал включённым после ошибки или прекращения прогона.

### 2.2 Манчестер/ЯСМ и PURUMK

- Проверка **входит в объём проекта**, но имеет **более низкий приоритет**, чем основной M16/RS-485/ПОС/дискретный прогон.
- **PURUMK** — обозначенная пользователем внешняя программа, применяемая для формирования тестового сигнала Манчестер. В исследованных исходниках её API, путь к исполняемому файлу, формат запуска и способ управления не обнаружены. Нельзя выдавать непроверенные аргументы командной строки или обещать автоматический запуск.
- Первый рабочий сценарий при отсутствии подтверждённого API: интерфейс БРП показывает оператору действие «Запустить тестовый сигнал в PURUMK»; оператор запускает подготовленную проверку во внешней программе, БРП принимает данные через уже существующий тракт ЯСМ/«Орбита» и сравнивает с ожидаемым тестом, фиксируя результат. Если доказан способ безопасного автоматического управления PURUMK, можно добавить вызов из приложения **без переписывания приёмного тракта**.
- Используются уже имеющиеся загрузка `.bcfrm` / последовательности ожидаемых кодов и `YasmCheck`. Фактическая выдача PURUMK, успешный приём и сравнительный вердикт различаются в журнале.
- Отсутствие PURUMK не должно ломать сборку или проверки, не связанные с Манчестером. Соответствующий пункт показывает причину недоступности, не выдаёт фиктивную НОРМА.

### 2.3 Маршрут основного прогона

1. Подготовка изделия, выбор интерфейса и проверка готовности только требуемого оборудования.
2. Управление питанием БРП и подготовкой ИСД — **повторно используем готовые процедуры и драйверы**; численные требования УБСИ не переносим.
3. Интерфейсная проверка RS-485: известный счётчик `0…1023` и контроль последовательности; этот тракт уже существует.
4. Проверки свежести и устойчивости получения по выбранным M16-адресам (ПОС1–4; ПНА; ББ СУ, ББ ПР, Ептм; «Команда 1»; датчики перегрузок/угловых скоростей; Uск1–4; резервные адреса; «Контроль стирания»; «Исправность») — в пределах доступной адресной карты и утверждённой очереди.
5. ПОС1–ПОС4: несколько измерительных точек на каждый канал **по согласованной стендовой шкале ±6 В**, сравнение телеметрии с В7; использовать имеющуюся обработку и подтверждённые возможности ЯФК/ИСД.
6. Дискретные сигналы: управлять подключёнными входами через ИСД; для неподключённых к ИСД — действие оператора с автоматической проверкой кадра.
7. Действие «ББ ПР — выдать сигнал» доступно в указанном операторском контексте и проверяется по фактической команде и реакции, а не наличию метки в UI.
8. Обработка результатов, повторов и сбоев, безопасное снятие воздействия, итог и сохранённый протокол.
9. На следующем менее приоритетном срезе — проверка ЯСМ/Манчестер с PURUMK через существующий вход данных и при необходимости ручное действие оператора.

**Про диапазон ПОС:** опубликованный документ «НОВЫЙ_БРП_технические требования.pdf», п. 3.2.1.6.1, содержит 0–3,3 В, а пользователь **прямо утвердил стендовую шкалу ±6 В**. В данной программе используется **±6 В**. Текст исходного ТУ сохраняем как источник для трассировки, но не заменяем им согласованную рабочую конфигурацию. Не объявлять измерение ±6 В формальным подтверждением всей иной методики без отдельной приёмки.

**Про M8:** приём и декодирование M8 — существующая диагностическая способность «Орбиты». Для выбранной программы БРП не установлена информативная карта M8; **не включать M8 в обязательный маршрут ТУ**, но сохранять возможность в ручной трассировке.

## 3. User Stories

1. Как оператор, хочу открыть отдельную программу БРП, чтобы не запускать MilTechStation.
2. Как оператор, хочу видеть готовность нужных приборов до старта, чтобы не начинать испытание с неподключённым стендом.
3. Как оператор, хочу выполнять один последовательный маршрут без переходов в ручную диагностику, чтобы пройти проверки быстрее.
4. Как оператор, хочу, чтобы приложение само включало питание по проверенной процедуре, чтобы не повторять команды вручную.
5. Как оператор, хочу видеть реальный результат RS-485 0…1023 и ошибку последовательности, чтобы проверить канал интерфейса.
6. Как оператор, хочу проверять свежесть M16 по нескольким циклам, чтобы единичный старый отсчёт не означал НОРМА.
7. Как оператор, хочу допускать одиночные пропуски и видеть регулярные сбои, чтобы не браковать за разовый провал связи.
8. Как оператор, хочу видеть отдельные результаты ПОС1–ПОС4, чтобы находить отказавший канал.
9. Как оператор, хочу измерить ПОС в нескольких точках ±6 В с В7, чтобы не оценивать канал по одному отсчёту.
10. Как оператор, хочу, чтобы подключённый к ИСД дискретный вход переключался автоматически, чтобы не делать лишних действий.
11. Как оператор, хочу вручную переключить неподключённый вход, а программа проверила кадр, чтобы не терять этот пункт.
12. Как оператор, хочу отдельную кнопку **«ББ ПР — выдать сигнал»**, чтобы инициировать требуемое воздействие непосредственно из БРП-приложения.
13. Как оператор, хочу увидеть успешность команды ББ ПР и реакцию в телеметрии, чтобы отличать выдачу сигнала от его приёма.
14. Как оператор, хочу повторить пункт после НЕ НОРМА, чтобы проверить воспроизводимость отказа.
15. Как оператор, хочу продолжить после НЕ НОРМА, чтобы за один прогон увидеть остальные проблемы.
16. Как оператор, хочу, чтобы успешный повтор дал итог НОРМА, а первая неудачная попытка осталась в истории.
17. Как оператор, хочу использовать Ctrl+Shift+Q для принудительного ОК текущего пункта, не завершая его досрочно.
18. Как оператор, хочу видеть фактические значения при принудительном ОК, чтобы диагностические данные не пропадали.
19. Как оператор, хочу отличать сбой стенда от отказа БРП, чтобы не путать причины.
20. Как оператор, хочу восстановить оборудование после безопасной паузы и повторить текущий пункт без перезапуска пройденных.
21. Как оператор, хочу после аварийного закрытия начать новый прогон, но сохранить старые результаты и попытки.
22. Как оператор, хочу получить протокол и табличный экспорт, чтобы передать результаты.
23. Как инженер, хочу сохранить и расширять ручной экран M16/M8 и отдельные измерения, чтобы трассировать новые сигналы.
24. Как инженер, хочу включать или исключать ручную диагностику при сборке, чтобы не переписывать приложение для поставки.
25. Как оператор, хочу запустить сигнал Манчестер через PURUMK и проверить его приём в БРП, чтобы закрыть проверку ЛПИ штатным внешним инструментом.
26. Как оператор, хочу видеть причину недоступности PURUMK или аппаратной команды ББ ПР, чтобы приложение не показывало ложный успех.
27. Как инженер, хочу пройти демонстрационный прогон на имитаторе, чтобы быстро проверить сшивку до доступа к оборудованию.
28. Как инженер, хочу различать результат имитации и физической проверки, чтобы не выдавать симулятор за реальный стенд.

## 4. Implementation Decisions

### Принятые пользователем (Grill Me 1–13)

| № | Решение |
|---|---|
| 1 | Строгая последовательность; сервисная комбинация выставляет ОК текущего пункта |
| 2 | Принудительный ОК **не пропускает** и **не сокращает** ожидаемое штатное завершение |
| 3 | Принудительный ОК сохраняется при отклонениях измерений, но аппаратные ошибки обрабатываются отдельно; фактические измерения сохраняются |
| 4 | При сбое стенда — безопасная пауза, восстановление и повтор текущей проверки с начала; ранее завершённые пункты остаются |
| 5 | Наличие параметра проверяется за несколько циклов «Орбиты», не по одному кадру |
| 6 | Единичный краткий пропуск допустим, систематические пропуски — НЕ НОРМА; конкретные величины не утверждались |
| 7 | Питание уже реализовано в `tu_minimal`; повторно используем процедуру и приборный код, а не обсуждаем заново |
| 8 | Управляемые дискретные входы переключаем автоматически через ИСД |
| 9 | Если вход не подключён к ИСД — оператор переключает вручную, станция проверяет кадр |
| 10 | ПОС1–ПОС4: несколько измерительных точек на канал |
| 11 | После аварийного закрытия — новый прогон, предыдущие результаты сохраняются |
| 12 | При НЕ НОРМА предложить «Повторить» или «Продолжить», сохранить все попытки |
| 13 | Успешный повтор устанавливает итог НОРМА, не стирая предыдущую НЕ НОРМА |

### Дополнительные подтверждённые требования

- Для ПОС принят диапазон **±6 В**; ТУ в данном проекте — исходный документ для трассировки, а не основание переписать действующую стендовую шкалу по инициативе агента.
- **ББ ПР:** присутствует отдельная кнопка выдачи сигнала (активная команда).
- **Манчестер:** применяем внешнюю программу **PURUMK**; проверка остаётся в объёме с меньшим приоритетом.
- **Ручной режим:** оставляем и при необходимости расширяем для трассировки; исключение из сборки предусмотрено, но в данный момент его не выключаем.
- **Темп:** рабочие, локальные, иногда временные изменения; не создавать платформенных подсистем ради архитектурной чистоты.
- **Изоляция:** нет зависимостей от Issues MilTechStation `R-*`/`INT-*`/`UI-*`.

### Обоснованные решения реализации

- Использовать **существующие** приём «Орбиты», парсер адресов, ЯФК/RS-485, ЯСМ, АКИП, ИСД, В7 и Qt UI как единый прикладной код.
- Переиспользовать из `master` **приёмы** контроля свежести, учёта возможных активных воздействий и промежуточной записи, но не переносить `ScenarioEngine`, платформенные плагины, `RunStore`, реестр или другие универсальные менеджеры целиком.
- Сохранять попытки и признак операторского вмешательства в локальной модели результатов, используя существующие форматы экспорта.
- Для ручной трассировки опираться на существующую опцию сборки `BRP_ENABLE_MANUAL_TESTS`, проверить оба значения флага. При `OFF` исключать только инженерный UI и его ненужные связи, не общий код прогона и приборов.
- Кнопку ББ ПР не связывать с неподтверждённым адресом ИСД по совпадению названий; критерий — реально отправленная команда, её подтверждение и наблюдаемая реакция.
- Для PURUMK сначала обследовать установленную программу и имеющийся способ запуска теста; ручное внешнее действие — допустимая экспресс-реализация. Автоматическое управление только если установлен и подтверждён её интерфейс.

## 5. Testing Decisions

**Главный тестовый шов:** существующий сквозной `brp.scenario` (`Qt -platform offscreen`) через UI, состояние этапов и фактический экспорт. Дополнять его сценариями, а не делать новую инфраструктуру тестирования. **Вспомогательный:** `brp.frame_checks` для M16 и геометрии адресов; `orbita.m8` остаётся регрессионным тестом библиотеки, но не обязательным испытанием изделия.

- [ ] Демонстрационный прогон проверок, порядок шагов, безопасное завершение, результат и экспорт.
- [ ] ПОС ±6 В — несколько точек и отдельный результат на каждый канал; корректный и ошибочный отсчёты.
Стендовые критерии EXP-01…EXP-07 собраны в [EXP-FIN · #79](https://github.com/Anatolichka2202/KPA-YALK_MODULE/issues/79). Программные критерии и известные ограничения остаются в исходных задачах. Пункт PURUMK относится к P1.

- [x] Аварийное завершение имитатора до экспорта — история показывает завершённую попытку прерванного прогона. Новый запуск сохраняется отдельно.
- [x] M16 на имитаторе — свежие кадры с постоянным значением проходят, одиночный краткий разрыв допускается, повторяющиеся пропуски и устаревшие группы отвергаются.
- [ ] Дискретные сигналы — автоматическое воздействие и ручной резерв, проверка `0`/`1`, очистка.
- [ ] ББ ПР — кнопка доступна, отправляет **реальное подтверждённое действие** либо показывает недоступность; событие и проверка отклика различимы.
- [ ] Повтор/продолжение, успешный второй результат, наличие в протоколе всех попыток.
- [ ] Ctrl+Shift+Q — ОК только после обычного завершения, реальные измерения не стираются, аппаратная ошибка остаётся отдельной.
- [ ] Питание БРП на стенде — подтвердить штатное включение, замер и отключение АКИП с утверждёнными уставками БРП. Программный сценарий сохраняет итог после завершения отключения.
- [ ] Ошибка ИСД/В7/АКИП — безопасная пауза; невыясненное состояние оборудования блокирует повтор.
- [ ] Аварийное завершение процесса — старые завершённые результаты сохранены; новый запуск не продолжает старый.
- [ ] ЯСМ — проверка с внешним сигналом PURUMK при доступной программе, отдельная имитация в CTest без ложного аппаратного ОК.
- [ ] Сборка с `BRP_ENABLE_MANUAL_TESTS=ON` и `OFF`: при `OFF` основной прогон не пропадает.
- [ ] На реальном стенде отдельная проверка физической выдачи ББ ПР, наличия сигнала PURUMK, электрических цепей и безопасного снятия. **Сборка/CTest не равны стендовой приёмке.**

## 6. Out of Scope

- Разработка MilTechStation, R/INT/UI Issue-очередь, перенос её архитектуры и рефакторинг общего ядра.
- Новый универсальный TU Builder, MES/ERP, общая HMI-платформа, плагины и абстрактные сервисы оборудования.
- Переписывание работающих драйверов и декодера без конкретного дефекта.
- Обязательный M8-сценарий при отсутствии полезных для БРП адресов.
- Автоматизация внешней PURUMK при отсутствии проверенного протокола управления.
- Полный объём аппаратуры ПУ (раздел 3.2.2); СТИР1/СТИР2 — отдельный более поздний объём, не основание задерживать текущий экспресс-прогон.

## 7. Further Notes — факты, ограничения и точки входа

**Проверено в исходниках, но не на физическом стенде:**

- `tu_brp_minimal`: `BrpTuWindow::startScenario()` формирует сейчас начальный RS-485/ЯСМ-гейт, адресную подготовку ИСД, затем одноточечные сравнения В7 для ББ СУ/ББ ПР/Ептм. Работающие ручные проверки не встроены в полный маршрут.
- Для ББ ПР в конфигурации указан M16-адрес `M16P1A10B60C21T01` — он описывает **приём/наблюдение**, а не доказанный путь выдачи сигнала.
- Имеются файлы кадровых проверок, приём `M16/M8`, RS-485, тест ЯСМ `.bcfrm`, встроенный график, адресные профили, проба ИСД/В7/АКИП/E20-10, HTML/TXT/CSV.
- Модель результатов приложения хранит один результат шага; историю попыток и сохранение до создания отчёта нужно дополнить.
- `BRP_ENABLE_MANUAL_TESTS=ON` уже существует; надо проверить реальное поведение сборки `OFF`.
- `master` содержит работающее управление приборами и механизмы `parameter.wait`, безопасного обращения с ИСД, записи промежуточных результатов; переносим только нужную логику.
- **PURUMK не обнаружена в проверенном репозитории.** Существование её внешней программы подтверждено пользовательским требованием; контракт запуска/формат команд пока не известен.
- По исходному PDF ТУ для ПОС есть текст 0–3,3 В, а по принятому решению для стенда ±6 В. В рамках этой задачи не менять выбранный диапазон.
- На момент подготовки нет проведённых в этом сеансе Windows-сборки, CTest и аппаратного теста; результаты не объявляются успешными.

Техническая очередь оформлена отдельно.
