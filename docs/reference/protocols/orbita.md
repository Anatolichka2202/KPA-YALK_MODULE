# Протокол «Орбита»

## Роль в системе

Протокол «Орбита» и ROKT — разные вещи.

```text
«Орбита»
    =
формат телеметрических данных,
который декодирует liborbita

ROKT
    =
протокол управления конкретным
Ethernet/RS-485 адаптером КТМА
```

Не объединять их в один протокол.

---

# Реализация

Библиотека:

```text
orbita/
```

Публичный API:

```text
orbita/include/orbita.h
```

Основной decoder pipeline:

```text
источник отсчётов
    ↓
восстановление битового потока
    ↓
frame decoder
    ↓
адрес канала
    ↓
сырой код
    ↓
Snapshot
```

---

# Текущая поддерживаемая модель

Текущая реализация публичного API ориентирована на адреса семейства:

```text
M16...
```

Адрес передаётся в liborbita уже нормализованным.

Пример формы:

```text
M16P1A70B12C10D10T01
```

Точная семантика конкретного адреса определяется парсером адресов и
типом канала.

---

# Типы значений

В текущем коде присутствуют типы:

```text
ANALOG_10BIT
CONTACT
FAST_1
FAST_2
FAST_3
FAST_4
BUS
TEMPERATURE
ANALOG_9BIT
```

На выходе liborbita отдаёт декодированный сырой код.

Это принципиально:

```text
liborbita:
    protocol bits
        ↓
    raw channel value

прикладной слой:
    raw channel value
        ↓
    физическая величина
```

Например перевод кода в вольты не должен автоматически считаться частью
wire-протокола «Орбита».

---

# Граница библиотеки

liborbita не отвечает за:

- ROKT;
- IP-адрес адаптера КТМА;
- HTTP ИСД;
- SCPI;
- ТУ;
- допуски;
- UI;
- базы данных;
- verdict изделия.

---

# Что пока не объявляем отдельной формальной спецификацией

В текущей новой документации не воспроизводится вручную полное побитовое
описание всех кадров «Орбита», если оно не подтверждено отдельным
исходным документом.

Источником текущей реализации decoder остаётся код `orbita/`.

Если понадобится независимая wire-spec, она должна быть восстановлена
отдельно и подтверждена тестовыми векторами.
