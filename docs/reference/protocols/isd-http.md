# HTTP-протокол ИСД

## Область и источник истины

Этот документ описывает host-side работу с ИСД текущего стенда КТМА.

Живой endpoint стенда сейчас:

```text
http://192.168.0.101
```

В предоставленном исходном коде firmware (`LPC1788/src/tcpip.h`) указан
`192.168.0.102`. Поэтому архив исходников не считается доказательством того,
что реально прошитый бинарник побитно ему соответствует.

Семантика активных команд в host-коде принимается только там, где она
подтверждается исходником firmware и/или живым испытанием.

Это не общий API MilTechStation.

---

## Подтверждение команды

Живой стенд подтверждает успешную HTTP-команду коротким:

```text
OK
```

Для совместимости host также принимает старый текстовый ответ, содержащий
`успешно`.

`OK` является только подтверждением HTTP/firmware обработчика. Оно не является
полным физическим readback состояния реле, шин или внутренних UART-модулей.

---

## Probe

```text
GET /
```

Probe подтверждает только HTTP connectivity/alive.

Он **не** подтверждает:

- состояние коммутации;
- состояние всех внутренних UART-модулей;
- отсутствие ранее оставшихся активных выходов;
- глобальную готовность аппаратуры к испытанию.

---

## Service full reset / all-channels-off

Команда firmware:

```text
/type=4num=1
```

По предоставленному `easyweb.c` это не обычный reset контроллера. Обработчик
синхронно выполняет последовательное отключение таблиц:

- 96 `AnalogReset`;
- 64 `KMReset`;
- 96 `KMGlobalBusReset`.

Всего выполняется 256 внутренних UART-операций. При отказе/тайм-ауте одного из
внутренних модулей HTTP-запрос может завершиться ошибкой после частично
выполненной последовательности.

Поэтому `type=4` разрешён только как явная сервисная операция
`service_full_reset`:

- одна HTTP-попытка;
- отдельный увеличенный timeout;
- без автоматического retry;
- не используется в `safeStop`, destructor, обычном cleanup, после probe,
  после ошибки или как подготовка ЯЛК/ЯТП;
- при timeout/error результат считается неопределённым.

---

## Type 7

В предоставленном `easyweb.c` полезное содержимое `case 7` закомментировано.
Фактически ветка не выполняет подтверждённой коммутации.

Поэтому:

```text
/type=7num=1
```

не является подтверждённой командой `YALK prepare`, а последовательность
`type=4 -> пауза 400 ms -> type=7` удалена из production-семантики.

Также нельзя считать подтверждённой старую трактовку `type=7` как коммутацию
ЯТП 3/9/12/17 только на основании Delphi/KPA комментариев. До отдельного
живого подтверждения production host такую команду не выдаёт.

---

## Задание напряжения ЯЛК

Подтверждённый host-side формат:

```text
/type=5num=<channel>val=<volts>work=1bus=1
```

Пример:

```text
/type=5num=47val=3.10work=1bus=1
```

Рабочий диапазон текущего host adapter:

```text
0.00 ... 6.20 В
```

Значение задаётся в вольтах. Старую трактовку `val=4095` не использовать как
канонический способ задания точки ЯЛК.

Отдельной команды `prepare` перед `type=5` host больше не посылает.

---

## Отключение выхода ЯЛК

Адресное выключение выполняется двумя командами:

1. отключить bus:

```text
/type=1num=<channel>val=0work=1bus=0
```

2. после примерно 100 ms выключить output:

```text
/type=1num=<channel>val=0work=0
```

Если одна из команд не получила ACK, маршрут остаётся в host driver как
`possibly-active`, а сессия становится `indeterminate`. Автоматически повторять
неопределённую активную команду нельзя.

---

## Общая коммутация

Низкоуровневая форма:

```text
/type=<type>num=<channel>val=<0|1>
```

Конкретные `type/channel` должны приходить только из подтверждённой карты
стенда. Неизвестные маршруты запрещено угадывать или подбирать перебором.

---

## Raw analog

Низкоуровневая форма:

```text
/type=1num=<channel>val=<value>work=<0|1>
```

Для штатных аналоговых точек ЯЛК используется специализированный `type=5`
flow, а `type=1` применяется там, где он явно нужен подтверждённому маршруту.

---

## HTTP transport

Один вызов активной команды host = одна физическая HTTP-попытка.

Transport:

- использует HTTP GET;
- проверяет HTTP status 2xx;
- для команд проверяет ACK в body;
- **не выполняет автоматический retry** после timeout, connection close или
  другой ошибки;
- для `service_full_reset` использует отдельный увеличенный timeout, но всё
  равно только одну попытку.

Причина: после сетевой ошибки host не может доказать, что физическая операция
не была выполнена до потери ответа.

---

## Stateful host driver

Driver сериализует все команды ИСД: одновременно выполняется не более одной
HTTP/UART операции.

Driver хранит две разные сущности:

1. `session_state` — есть ли у текущего процесса неразрешённая неопределённая
   операция (`operational` / `indeterminate`);
2. owned resources — только маршруты, которые текущий процесс сам пытался
   активировать, с owner/session id.

`operational` **не означает**, что глобальное физическое состояние всего ИСД
известно. Firmware не предоставляет надёжного полного readback.

Перед отправкой ON-маршрут сразу записывается как `possibly_active`. Только
после ACK он становится `acknowledged_active`. Поэтому потерянный ACK не
приводит к забыванию потенциально включённого выхода.

---

## Cleanup и безопасность

Обычный cleanup выполняется адресно:

```text
releaseOwner(owner)
```

Driver выключает owned/possibly-active маршруты этого owner в обратном порядке.
`safeStop` плагина использует тот же targeted cleanup для всех ресурсов,
которыми владеет текущий процесс.

`safeStop` никогда не вызывает `type=4`.

После ошибки активной команды новые ON/active mutations блокируются до
явного разрешения неопределённости. Targeted OFF/release при этом разрешён.

Ошибка HTTP/ИСД является ошибкой стенда, а не автоматически дефектом
проверяемого изделия.
