# HTTP-протокол ИСД

## Область и источник истины

Документ описывает host-side работу с ИСД текущего стенда КТМА.

Живой endpoint стенда сейчас: `http://192.168.0.101`.
В предоставленном исходном коде firmware (`LPC1788/src/tcpip.h`) указан
`192.168.0.102`, поэтому архив исходников не доказывает побитовое соответствие
реально прошитому бинарнику. Семантика активных команд принимается только там,
где она подтверждена исходником firmware и/или живым испытанием.

## ACK и probe

Живой стенд подтверждает успешную HTTP-команду коротким `OK`. Для совместимости
host также принимает старый текстовый ответ, содержащий `успешно`.

ACK подтверждает завершение обработчика команды, но не является полным
физическим readback реле, шин или внутренних UART-модулей.

`GET /` используется только как HTTP connectivity/alive. Probe не подтверждает
состояние коммутации, внутренних UART-модулей или отсутствие ранее оставшихся
активных выходов.

## Service full reset / production baseline

Firmware-команда `/type=4num=1` — не reboot контроллера. По предоставленному
`easyweb.c` она синхронно выполняет all-off sweep:

- 96 `AnalogReset`;
- 64 `KMReset`;
- 96 `KMGlobalBusReset`.

Итого — 256 внутренних UART-операций. При ошибке одного внутреннего модуля
операция может завершиться после частично выполненного сброса.

Host предоставляет её только как `service_full_reset`:

- одна HTTP-попытка;
- отдельный `service_timeout_ms`;
- без автоматического retry;
- timeout/error переводит ISD session в `indeterminate`.

В production `service_full_reset` вызывается ровно один раз в начале нового
самостоятельного run как `ubsi.isd_baseline`. После ACK host проверяет
`session_state=operational` и `owned_count=0`. Это означает подтверждённый
стартовый all-off baseline текущей сессии, но не означает, что глобальное
физическое состояние ИСД можно прочитать: `global_hardware_state=not_readable`.

Внутри уже начатого run между ЯЛК, ЯТП и ЯВП глобальный reset не выполняется.
При штатном завершении и при ошибках используются только tracked targeted OFF.

## Firmware case 7

В предоставленном `easyweb.c` полезное содержимое `case 7` закомментировано.
Поэтому host не использует эту ветку как рабочую команду коммутации.

Старые последовательности подготовки, в которых рядом с ЯЛК/ЯТП встречалась
эта команда, удалены из production flow. ЯТП при этом не блокируется: его
рабочий тракт является adapter/ROKT flow `prepare_ytp_rokt ->
start_prepared_ytp_rokt -> await_ytp_rokt` с кадрами 68 байт и не требует
активных команд ИСД.

## Задание напряжения ЯЛК

Подтверждённый host-side формат:

```text
/type=5num=<channel>val=<volts>work=1bus=1
```

Рабочий диапазон текущего host adapter: `0.00 ... 6.20 В`.
Отдельной команды prepare перед `type=5` production host не посылает.

## Адресное отключение выхода ЯЛК

Отключение выполняется двумя командами:

```text
/type=1num=<channel>val=0work=1bus=0
/type=1num=<channel>val=0work=0
```

Между ними host выдерживает короткую паузу. Если ACK потерян, ресурс остаётся
в driver как `possibly_active`, а session становится `indeterminate`.

## Общая коммутация

Низкоуровневая форма:

```text
/type=<type>num=<channel>val=<0|1>
```

Конкретные `type/channel` должны приходить только из подтверждённой карты
стенда. Неизвестные маршруты запрещено угадывать или подбирать перебором.

Raw analog использует форму:

```text
/type=1num=<channel>val=<value>work=<0|1>
```

Для штатных аналоговых точек ЯЛК используется специализированный `type=5`
flow; `type=1` применяется только там, где это требуется подтверждённому
маршруту.

## HTTP transport

Один вызов активной команды host = одна физическая HTTP-попытка. Transport:

- использует HTTP GET;
- проверяет HTTP status 2xx;
- для активных команд проверяет ACK в body;
- не выполняет автоматический retry после timeout/connection close;
- для `service_full_reset` использует отдельный увеличенный timeout, но всё
  равно одну попытку.

Причина: после сетевой ошибки host не может доказать, что физическая операция
не была выполнена до потери ответа.

## Stateful host driver

Driver сериализует команды ИСД и хранит две разные сущности:

1. `session_state` — `operational` или `indeterminate` для текущего процесса;
2. owned resources — маршруты, которые текущий процесс пытался активировать,
   вместе с owner/session id и степенью уверенности.

`operational` не означает, что глобальное физическое состояние всего ИСД
известно. Firmware не предоставляет надёжного полного readback.

Перед отправкой ON ресурс записывается как `possibly_active`. После ACK он
становится `acknowledged_active`. Поэтому потерянный ACK не приводит к
забыванию потенциально включённого выхода.

## Cleanup и безопасность

Обычный cleanup выполняется адресно через `releaseOwner(owner)`. Driver
выключает owned/possibly-active ресурсы в обратном порядке. `safeStop` плагина
делает тот же targeted cleanup для всех ресурсов текущего процесса.

`safeStop` никогда не вызывает глобальный reset.

После ошибки активной команды новые ON/active mutations блокируются до
разрешения неопределённости. Targeted OFF/release при этом разрешён. Если
cleanup не возвращает session в `operational`, production run завершается
ошибкой стенда; автоматический глобальный reset в середине run не запускается.
