# Администрирование и жизненный цикл КТМА

Этот раздел описывает не измерительный алгоритм, а учёт изделия и
производственный документооборот.

Реализация регистратора:

```text
registrar/
```

---

# Что должен различать регистратор

```text
ИЗДЕЛИЕ
    конкретный экземпляр КТМА/объекта

КОМПОНЕНТ
    конкретная установленная ячейка/узел со своим SN

УСТАНОВКА
    связь компонента с изделием во времени

ПОПЫТКА ЭТАПА
    конкретное прохождение production stage

RUN
    подробное измерительное выполнение ScenarioEngine
```

---

# Product

Хранится:

```text
id
product_type
serial_number
```

Серийный номер изделия уникален в registrar.

---

# Component

Хранится:

```text
id
component_type
serial_number
```

Экземпляр компонента существует отдельно от факта его установки в
изделие.

---

# Установка и замена компонента

Таблица `product_components` хранит историю:

```text
product_id
component_id
installed_at
removed_at
removal_reason
active
```

Поэтому снятый компонент не должен исчезать из истории после замены.

Жизненный цикл выглядит так:

```text
component A установлен
    ↓
испытания
    ↓
component A снят с причиной
    ↓
component B установлен
    ↓
новые испытания
```

Нельзя переписывать старый run так, будто в нём уже стоял component B.

---

# StageAttempt

Попытка этапа хранит:

```text
product_id
component_id (может отсутствовать у агрегатной попытки)
stage
verdict
opened_at
finished_at
```

Текущая enum-модель содержит production stages:

```text
Primary

ClimateNormal
ClimateMinus
ClimatePlus

PottingClimateNormal
PottingClimatePlus
PottingClimateMinus
```

В модели также остаются legacy stage values для чтения старых данных.

Наличие legacy значения не означает, что оно должно использоваться новым
production flow.

---

# Связь с измерением

`stage_runs` связывает:

```text
stage_attempt_id
    ↕
run_id
```

Один stand `run_id` не должен быть привязан как независимый результат к
нескольким stage attempts.

Для завершения attempt результатом `Ok` или `Fail` текущий registrar
требует связанный stand run.

Это защищает от ручного "поставить НОРМА" без измерительного следа.

---

# Агрегатный итог изделия

На текущем коде:

```text
Registrar::productVerdict(productId)
    ↓
Incomplete
```

Это сделано сознательно.

Причина: старая схема автоматического вывода итогового verdict из прежних
электрических этапов больше не считается достаточной нормативной policy.

Следовательно:

- не показывать старый агрегатный `OK` как канонический итог;
- не восстанавливать "четыре обязательных этапа" из старой документации;
- не придумывать новую policy в registrar самостоятельно.

Финальная policy должна быть отдельным подтверждённым решением уровня
поставки/текущего объекта.

---

# Документооборот

Минимальная трассировка production-документа должна позволять пройти:

```text
изделие / SN
    ↓
состав на момент работы
    ↓
этап / пакет
    ↓
run_id
    ↓
измерения
    ↓
generated report
```

Документооборот не должен заставлять пользователя вручную переписывать
измеренные значения из одного экрана в другой.

---

# Что относится к администрированию, а не к испытанию

Например:

- создание карточки изделия;
- регистрация серийного номера;
- регистрация компонента;
- установка компонента;
- снятие / замена с причиной;
- выбор этапа;
- просмотр истории;
- открытие связанного run;
- формирование журнала.

А вот:

```text
подать 27 В
измерить канал
проверить допуск
```

— это испытательная логика, а не registrar.
