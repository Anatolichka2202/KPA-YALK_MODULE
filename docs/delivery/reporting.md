# Отчётность КТМА

Отчётность разделяется по уровню.

```text
run
  ↓
отчёт конкретного запуска

production run / stage
  ↓
производственный отчёт

product lifecycle
  ↓
журнал изделия
```

Эти документы не должны подменять друг друга.

---

# 1. Отчёт ScenarioEngine run

Реализация:

```text
stand/src/report_writer.cpp
```

Текущий writer формирует:

```text
Ведомость_каналов_<run_id>.html
Ведомость_каналов_<run_id>.csv
Протокол_ТУ_<run_id>.html
```

Для части ЯЛК-сценариев дополнительно создаётся совместимый файл:

```text
channels.csv
```

## Что должно быть привязано к run

Отчёт использует данные:

```text
run_id
scenario_id
scenario_version
catalog_version
profile_version
object_serial
started_at
finished_at
verdict
measurements
```

То есть отчёт должен позволять понять, какой именно запуск он отображает.

---

# 2. Ведомость измерений

Ведомость показывает измерения конкретного run.

Состав колонок может различаться по типу данных.

Например текущий writer отдельно форматирует:

- ЯЛК;
- ЯТП;
- смешанный ЯЛК/ЯТП run.

Это presentation-layer.

Исходные измерения остаются в `runs.db`.

---

# 3. Протокол ТУ

`Протокол_ТУ_<run_id>.html` — краткое представление результата формального
TU-сценария.

Наличие файла с таким именем само по себе не доказывает полноту покрытия
ТУ.

Полнота определяется рабочей картой требований и фактически выполненным
сценарием.

Поэтому:

```text
красивый протокол
!=
доказанное полное покрытие ТУ
```

---

# 4. Производственный отчёт УБСИ

Task-specific реализация:

```text
ktma/ubsi/src/production_report.cpp
```

Формирует:

```text
Производственный_отчет_<run_id>.html
Производственный_отчет_<run_id>.csv
```

В текущий production report включаются:

- изделие;
- этап;
- пакет проверки;
- сценарий и версия;
- время;
- итог;
- snapshot состава изделия на момент запуска;
- измерения;
- `run_id`.

Это важно: состав фиксируется на момент начала production run и не должен
"переехать" задним числом после замены компонента.

Подробно:

[../task/ubsi/production-data.md](../task/ubsi/production-data.md)

---

# 5. Журнал КТМА / Registrar report

Реализация:

```text
registrar/src/report.cpp
```

Журнал показывает:

- изделие;
- состав;
- активные и снятые компоненты;
- причины снятия;
- stage attempts;
- связанный `run_id`.

Подробные измерения туда не копируются.

Сам документ прямо указывает, что подробные измерения находятся в
`runs.db`.

---

# 6. Verdict

На уровне ScenarioEngine существуют разные результаты:

```text
НОРМА
НЕ НОРМА
НЕПОЛНАЯ
ОШИБКА
ОСТАНОВЛЕНО
НЕ ВЫПОЛНЯЛОСЬ
```

Производственный слой УБСИ отображает соответствующие статусы:

```text
NORM
NOT_NORM
STAND_ERROR
INCOMPLETE
STOPPED
```

Критическое правило:

```text
ошибка стенда
!=
дефект изделия
```

---

# 7. Что сейчас НЕ утверждаем

Текущий `Registrar::productVerdict()` сознательно возвращает:

```text
Incomplete
```

пока не подключена каноническая production verification policy.

Поэтому новый канон НЕ повторяет старое утверждение:

```text
"четыре этапа OK автоматически дают итог изделия OK"
```

Это устаревшая модель и текущему коду не соответствует.

Итог уровня всего изделия нельзя выводить из старой четырёхэтапной схемы
до явного подключения актуальной policy.

---

# 8. Документ не должен быть единственным доказательством

Generated report является представлением.

Для технической трассировки должен сохраняться путь:

```text
документ
  ↓
run_id
  ↓
runs.db
  ↓
исходные step / measurement / event
```
