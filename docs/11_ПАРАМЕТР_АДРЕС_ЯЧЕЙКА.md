# Параметр, адрес, ячейка и вид испытания

## Самое короткое объяснение

Это не четыре названия одного и того же:

| Понятие | Что это на самом деле |
|---|---|
| объект испытаний | физический блок целиком: например, УБСИ № 7 или БСИ |
| ячейка | физический модуль внутри блока: ЯЛК-96, ЯВП-8, ЯТП и другие |
| вход/выход | электрическая точка ячейки и контакт разъёма |
| параметр | смысловой сигнал, который нужно показать, записать или проверить |
| адрес «Орбиты» | координаты сырого кода этого параметра в кадре M16 |
| канал ИСД | команда, которая подключает нужное воздействие к физической точке |
| поле адаптера | место данных ячейки в UDP-пакете выбранного режима УБСИ |
| VISA resource | техническое имя вольтметра в Windows |
| вид испытания | последовательность действий и правило получения `ОК/НЕ ОК` |

Одна ячейка содержит много входов и параметров. Один параметр может иметь
основной и альтернативный адрес `ЗУ` в «Орбите». Сам адрес M16 не является ни
номером ячейки, ни IP-адресом, ни номером канала ИСД.

## Пример из приложения 1

Для строки `Параметр А1` документ отдельно указывает:

```text
смысловое имя:       Параметр А1
физический источник: Вх.2
контакт:             X1/2
адрес в документе:   П1 A70 B12 C20 D10 T01
адрес для liborbita: M16P1A70B12C20D10T01
```

Это одна строка телеметрической карты. Она уже позволяет найти сырой код в
потоке, но ещё не отвечает на вопросы:

- в каком экземпляре ячейки находится этот вход;
- какой выход ИСД нужно включить;
- где в этот момент подключён В7-78/1;
- какая формула переводит сырой код в физическую величину;
- какая погрешность допустима;
- где лежит соответствующее значение в пакете адаптера УБСИ.

Эти связи должны быть добавлены из схем, ТУ и референсных программ. Их нельзя
угадывать по строке адреса.

## Что хранится для одного проверяемого параметра

Вместо одного перегруженного поля `address` нужна запись-привязка:

```text
объект:                 УБСИ № 7 или БСИ
ячейка:                 тип + экземпляр/позиция
параметр:               стабильный идентификатор и имя оператора
физическая точка:       разъём + контакт + вход/выход
телеметрия «Орбита»:    один или несколько адресов M16
ИСД:                    канал/маршрут переключения
вольтметр:              роль и настройки измерения
адаптер УБСИ:           режим + тип пакета + поле данных, если требуется
преобразование:         сырой код → физическая величина
правило допуска:        формула разрешённой ошибки
```

Пока какая-либо связь не подтверждена документом или проверкой на стенде, она
должна иметь состояние `не определено`, а не выдуманное число.

## Как выполняется автономная проверка ЯЛК

1. Оператор выбирает ЯЛК и проверку аналоговых каналов.
2. Движок загружает все привязки выбранных параметров.
3. ИСД переключает требуемый вход и выход.
4. В7-78/1 измеряет реальное опорное напряжение.
5. Ethernet-адаптер получает коды ЯЛК по внутренней RS-485.
6. Движок переводит данные адаптера в ту же физическую величину.
7. От показания вольтметра и нормативной формулы вычисляются границы.
8. На экран выводятся графики, результат параметра, ячейки и всего блока.

Это проверка отдельной ячейки, а не доказательство отсутствия «Орбиты» у
УБСИ. УБСИ имеет адресованные параметры в приложении 1. Интегрированный вид
испытания блока может читать их через `liborbita`, а диагностический —
сопоставлять их с прямыми данными адаптера.

## Как выполняется проверка БСИ

1. Оператор выбирает БСИ, ячейку/группу и вид испытания.
2. ИСД переключает требуемый вход и выход.
3. В7-78/1 измеряет опорное значение.
4. E20-10 и `liborbita` получают сырой код параметра по его адресу M16.
5. `TelemetryService` переводит код в физическую величину.
6. Движок сравнивает её с интервалом, вычисленным от показания вольтметра.
7. На экран выводятся графики и итог `ОК/НЕ ОК`.

Ethernet-адаптер RS-485 в проверке БСИ не используется.

## Что такое процедура в программе

В интерфейсе оператору нужен термин **вид испытания**. Внутри программы его
исполняемое описание можно называть процедурой или картой испытания. Это не
текстовая инструкция и не произвольный скрипт, а проверенная структура:

```text
какие параметры проверяем
→ что переключает ИСД
→ какое оборудование обязательно
→ сколько ждём установления
→ откуда берём опорное и проверяемое значения
→ как считаем границы
→ когда ставим ОК/НЕ ОК
→ какие ряды кладём на график и в отчёт
```

Именно эта структура связывает документы приложений 1 и 2 с физическим
стендом. База SQLite служит индексом для приложения; нормативными источниками
остаются проверенные карты и нормализованные данные репозитория.
