# Ethernet-адаптер RS-485 КТМА

## Что было исследовано

Источник: локальный архив
`L:\Проекты\Адаптер_485_КТМА\Адаптер 485 для КТМА.rar`.

SHA-256 архива:

```text
E625F59EA718125ED9744B0018BC7A2AAD3627DF90EC7E298F9512F090FFDC83
```

В архиве находится проект прошивки Keil для LPC2378/LPC2478:
`easyweb.c`, `tcpip.c`, `udp.c`, таблицы опроса `YALKPOLL.h` и `YATPPOLL.h`,
собранный `easyweb.hex` и артефакты сборки.

Отдельной операторской программы Windows в архиве нет. `WebConverter.exe` —
служебный конвертер HTML-страницы в C-заголовок для прошивки, а не программа
обмена с адаптером.

Исходные PDF в той же папке являются сканами/чертежами и не дают извлекаемого
текстового описания протокола. Ни архив, ни PDF в Git не копируются.

## Главный вывод

Это не прозрачный Ethernet↔COM преобразователь. Микроконтроллер адаптера сам:

- формирует запросы к ячейкам по трём UART/RS-485;
- проверяет CRC8 ответов;
- раскладывает быстрые, медленные, контактные и температурные параметры по
  внутренним буферам;
- передаёт буферы в компьютер по UDP;
- принимает по UDP команды выбора режима и отдельные технологические команды.

Следовательно, для приложения нужен специализированный
`UbsiEthernetUdpAdapter`, а не открытие COM-порта.

## Сетевые параметры из архивной прошивки

| Параметр | Значение |
|---|---|
| IP адаптера в исследованной сборке | `192.168.0.101` |
| MAC исследованной сборки | `00-35-65-03-74-01` |
| Маска | `255.255.255.0` |
| Шлюз | `192.168.0.1` |
| Назначение исходящих UDP | `192.168.0.255`, широковещательно |
| Команды и основные данные | UDP `1001` |
| Подтверждения команд | UDP `1101` |
| Режим сырого транзита UART1 | UDP `999` |

Проверка реального стенда 26.08.2026 уточнила картину. HTTP на `.101` вернул
типичную ошибку ИСД с примером `type=1num=2val=3work=1`; следовательно, на
текущем стенде `.101` — **ИСД**, а не адаптер. Устройство `.115` отвечает по
Ethernet и имеет MAC `00-35-65-03-74-06`, то есть ту же серию, что и MAC
архивной сборки. `.115` — кандидат на адаптер, но его нельзя закреплять в
рабочем профиле до записи реального UDP-обмена. Плагин не должен жёстко
зашивать ни IP, ни MAC архивной сборки.

В комментариях прошивки оставлены варианты адресов `.103`, `.104`, `.105` и
портов `1003…1005`/`1103…1105`, но исследованная сборка скомпилирована для
`.101`, `1001`, `1101`. Фактическую прошивку конкретного адаптера нужно
подтвердить на стенде.

UDP checksum в прошивке не рассчитывается, а полезная нагрузка отправляется
на broadcast. Плагин должен принимать только ожидаемый источник и проверять
длины/содержимое сам, иначе пакет другого прибора в той же сети может быть
ошибочно принят за данные ячейки.

## Команды

Основная команда имеет три байта и приходит на UDP `1001`:

```text
byte 0 = 68 (0x44)
byte 1 = флаги; для выбора режима установлен bit 0
byte 2 = номер режима
```

Подтверждение повторяет три байта на UDP `1101`. Установленный `bit 1` второго
байта включает флаг одиночной работы.

Подтверждённые комментариями режимы:

| Режим | Назначение в исходниках |
|---:|---|
| `0` | ЯЛК, БСУ ФТК, ответ RS-485 14 байт |
| `1` | ЯВП |
| `2` | ЯТП |
| `3` | технологическая проверка ЯЛК |
| `6` | ЯЛК, УЛК |
| `7` | вариант опроса ЯТП на 16 каналов |
| `8` | вариант опроса ЯЛК по таблице `YALK3PollTable` |
| `9` | сбор 8-байтовых ответов в медленный буфер |
| `11` | ЯЛК с 18-байтовым ответом |
| `12…18` | совмещённый опрос ЯЛК и транзит ЯТП |

Назначение режимов `4`, `5`, `8`, `9` и вариантов `12…18` нельзя превращать в
операторские названия только по коду: его нужно сверить с референсной
программой проверки и реальным подключением.

Также прошивка принимает:

- `68, 168, N` — выбор канала ЯВП;
- `69, 169, N` — выбор режима каналов ЯТП;
- 6-байтовые команды для ЯП-А, одноразово или циклически 128 Гц;
- 92-байтовую загрузку калибровок ЯТП;
- технологические команды ЯФК и ЯК-40;
- произвольный транзит через UDP `999` в UART1.

Эти команды способны менять режим работы ячеек. Диагностический скрипт их не
посылает. В производственном плагине они должны быть типизированными
операциями, разрешёнными конкретным видом испытания, с журналированием и
безопасным завершением.

## Выходные UDP-пакеты

Формат зависит от выбранного режима. Из исходников подтверждены, среди прочих:

| Режим | Полезная нагрузка UDP `1001` |
|---:|---|
| `0` | 120 байт быстрых данных (`12 × 10`) и отдельно 200 байт медленных |
| `1` | блок 128 байт ЯВП |
| `2` | 64 байта значений 32 каналов ЯТП + байт режима |
| `6` | 120 байт быстрых и 200 байт медленных данных ЯЛК |
| `7` | 32 байта значений 16 каналов ЯТП + байт режима |
| `8` | 120 байт быстрых и 200 байт медленных данных ЯЛК |
| `9` | 200-байтовый медленный буфер |
| `10` | 4 байта ответа через UDP `999` |
| `11…18` | быстрые, медленные и температурные буферы, зависящие от подрежима |

В этих пакетах нет универсального заголовка с типом пакета, версией и длиной.
Одна длина может встречаться в разных режимах. Поэтому плагин обязан хранить
текущее подтверждённое состояние режима и декодировать пакет в его контексте.

## Требования к плагину

Первый вариант плагина должен:

1. проверить наличие подходящего IPv4-интерфейса `192.168.0.0/24`;
2. проверить доступность адаптера и отсутствие конфликта IP;
3. привязать UDP `1001` и `1101` к выбранному интерфейсу;
4. фильтровать источник по IP и проверять длину пакета;
5. записывать исходные UDP-пакеты с временем до их декодирования;
6. послать команду режима только по запросу стендового движка;
7. дождаться совпадающего подтверждения на `1101`;
8. выдавать типизированные выборки ячеек без знания о графиках и `ОК/НЕ ОК`;
9. иметь replay/mock-реализацию на сохранённых пакетах;
10. при остановке выполнять только подтверждённую безопасную последовательность.

Первое подключение должно начинаться с пассивной записи трафика и сверки
реальных пакетов с исходниками. До этого автоматическую отправку команд в
общем диагностическом режиме включать нельзя.
