# SUPER SPEC

## Следующая минимальная поставка КТМА / УБСИ

Статус: каноническая спецификация реализации
Область: ближайшая версия КТМА для стенда
Цель документа: дать агенту достаточно контекста и конкретики, чтобы он мог реализовывать задачу без повторного допроса пользователя и без возвращения к уже закрытым решениям.

---

# 0. Главное правило для агента

**Открытых продуктовых или методических вопросов по текущей поставке УБСИ нет.**

Не задавать пользователю повторно вопросы:

* входит ли ЯВП;
* как проверяется ЯТП;
* нужны ли ±12 В;
* какие контактные точки;
* измеряется ли входной ток ≤2 мкА;
* нужна ли линия 50 м;
* нужна ли изоляция;
* нужен ли автоматический 350/450 мА;
* сколько режимов приложения;
* как ведётся регистратор;
* какой должен быть ТУ-протокол;
* что делать после замены ЯЛК/ЯТП/ЯВП;
* кто подтверждает Р4831;
* что делать с напечатанным протоколом.

Все эти решения ниже зафиксированы.

Если при реализации отсутствует **технический факт** — например, конкретная команда ИСД ЯВП или физический масштаб тракта, — это не новый вопрос к пользователю.

Порядок действий:

1. проверить текущий код;
2. проверить журнал стенда;
3. проверить capture/reference KPA;
4. проверить схему/каталог/профиль;
5. проверить живой стенд, если доступен;
6. не выдумывать команду;
7. при невозможности подтвердить оставить опасное воздействие безопасно заблокированным и явно описать технический blocker.

Не превращать технический commissioning в продуктовый допрос.

# 5. Общая модель результатов

## Результат отдельной нормативной проверки

```text
НОРМА
НЕ НОРМА
ОШИБКА СТЕНДА
```

`НЕ НОРМА`:

достоверное измерение изделия выполнено и вышло за допустимую границу.

`ОШИБКА СТЕНДА`:

получить достоверное измерение не удалось из-за оборудования, транспорта или состояния стенда.

Не превращать:

```text
timeout
ошибку адаптера
ошибку ИСД
ошибку VISA
невалидный кадр
```

в `НЕ НОРМА` изделия.

---

## Общий результат запуска

Дополнительно разрешён:

```text
НЕПОЛНАЯ ПРОВЕРКА
```

Только как агрегатный итог, когда из-за технической ошибки нельзя получить полный нормативный ответ.

`ОСТАНОВЛЕНО` — состояние выполнения, а не нормативный verdict.

---

# 6. Повторы

При технически несостоявшемся измерении:

* автоматически повторить тот же безопасный шаг;
* допускается не более **трёх повторных попыток**;
* исходная попытка и все повторы сохраняются;
* после исчерпания повторов:
  `ОШИБКА СТЕНДА`;
* независимые части сценария продолжаются, если это безопасно.

Реальный `НЕ НОРМА` изделия не маскировать техническими retry.

# 7. Приёмо-сдаточный режим — TU MVP

## 7.1. Назначение

Самостоятельный полный нормативный прогон текущей автоматизированной методики.

Не зависит от производственного lifecycle.

Но имеет связь с БД, если изделие уже зарегистрировано.

---

# 7.2. Вход в режим

При открытии режима ПО **само** выполняет техническую подготовку оборудования.

Оператор НЕ видит:

```text
RS485 готов
ИСД готов
В7 готов
АКИП готов
Rigol готов
```

и не нажимает отдельную штатную кнопку `Проверить оборудование`.

Он видит только:

```text
ПОДГОТОВКА СТЕНДА...
```

затем:

```text
СТЕНД ГОТОВ
```

или:

```text
СТЕНД НЕ ГОТОВ

Проверка не может быть запущена.

[ ПОВТОРИТЬ ПОДГОТОВКУ ]
```

Низкоуровневая причина доступна через F12.

---

# 7.3. Номер блока

Оператор вводит номер:

```text
Блок / УБСИ № [________________]
```

Далее:

* если `Registrar` находит объект с таким номером — `run_id` связывается с существующим изделием;
* если объекта нет — проверка всё равно разрешена;
* новая карточка автоматически НЕ создаётся;
* производственный lifecycle НЕ меняется;
* производственный этап НЕ закрывается.

TU-run может иметь nullable `product_id`.

---

# 7.4. Состав полного TU-прогона

Текущий полный маршрут должен включать:

## Питание и готовность

* готовность после включения — не более 30 секунд;
* рабочие напряжения:
  `24 / 27 / 35 В`;
* выдержка:
  `19 В / 5 мин`;
* выдержка:
  `37 В / 1 мин`;
* после 19/37 В восстановить рабочий режим и продолжить функциональную проверку;
* ток потребления УБСИ:
  `≤400 мА` в рабочем диапазоне;
* сохранять временной ряд тока и напряжения.

---

## ЯЛК-96

Проверяются только реальные рабочие адреса ЯЛК.

Калибровка:

```text
97
99
```

Аналоговые точки:

```text
0 В
3,1 В
6,2 В
```

В7 измеряет фактическое значение воздействия.

Уставка ИСД без показания В7 эталоном не является.

Для каждого измерения сохраняются:

```text

code99
raw
analog code
signal
показание В7
пересчитанное значение ЯЛК
абсолютная погрешность
приведённая погрешность
```

---

## Контактные входы

Приняты точки:

```text
0 В   → 0
0,9 В → 0
2,5 В → 1
```

Не возвращать `1,0 / 2,4 В`.

Не вводить в этот сценарий проверки `5 кОм / 100 кОм`.

---

## Обрыв

Проверять все соответствующие аналоговые входы.

Методика считается принятой.

Точный raw/bit-критерий — техническая часть реализации.

Не спрашивать пользователя повторно.

Использовать подтверждённые стендовые наблюдения/текущий код и валидировать на живом стенде.

---

## Перегрузка ±12 В

Проверяется.

Каждый вход последовательно:

```text
+12 В
-12 В
```

Длительность:

```text
10 с по умолчанию
```

Параметр конфигурируемый.

Во время воздействия остальные незатронутые каналы должны продолжать выдавать рабочие данные.

Не писать в UI:

```text
нужна карта
нужна опция
нужно подтвердить безопасный уровень
```

как продуктовый blocker.

Методика уже принята.

# 7.5. ЯТП

ЯТП — ручной Р4831.

Физическая схема:

```text
Р4831
→ общий X123
→ ЯТП
→ адаптер
→ 68-byte stream
```

Оператор устанавливает:

```text
0 Ом
120 Ом
240 Ом
```

Все 30 каналов проверяются в каждой точке.

Не использовать:

```text
0 / 100 / 240
```

Р4831 не изображать автоматическим COM-прибором.

# 7.6. ЯВП

ЯВП входит в текущую проверку.

Не считать его external evidence.

## Генератор

```text
Rigol DG-1022Z = ДГ10.2
```

Это одно устройство/название.

Плагин:

```text
stand/plugins/rigol_generator_plugin.cpp
orbita.rigol_generator
signal.generator
```

---

## Физический тракт

```text
Rigol DG-1022Z
→ C = 1000 пФ
→ выбранный вход ЯВП
→ ЯВП
→ ЯЛК
→ UDP 204 байта
→ ScenarioEngine
```

ИСД:

```text

```

```text

измеряет фактическое напряжение
```

Уставка Rigol не является эталоном без измерения В7.

---

## Выходы

На УБСИ выходы ЯВП связаны с областью ЯЛК:

```text

```

Фактическое соответствие адресов закрепить в catalog/profile после технической проверки.

Не возвращать `orbita.parameter_source` / E20 как целевой источник результата УБСИ ЯВП.

Результат читается через ЯЛК из UDP-потока адаптера.

## Амплитуды

Принято:


## Заряд

```text
Q[pC] = C[pF] × Uin[V]
```

при:

```text
C = 1000 пФ
```

---

## Измеренный коэффициент

```text
Kmeas[mV/pC] =
1000 × Uout[V] / Q[pC]
```

---

## Погрешность коэффициента

```text
δK[%] =
(Kmeas - Kset) / Kset × 100
```

Критерий быстроменяющегося параметра:

```text
±7 %
```

---

## АЧХ

На технически выбранной/подтверждённой опорной частоте сохранить `Aref`.

Для остальных точек:

```text
ΔAFC[%] =
(A(f) / Aref - 1) × 100
```

Применить таблицу ТУ.

Не сохранять старый алгоритм, который сравнивает каждую точку напрямую без нормирования.

---

## Затухание

На `4000 Гц = 2Fв`:

```text
D[dB] =
20 × log10(Aref / A(f))
```

Порог/verdict должен браться из актуального текста ТУ/config.

Не прятать неоднозначный текст за выдуманной формулой.

Техническое значение хранить отдельно в конфигурации сценария.

## Питание датчиков 6,2 В / 350–450 мА

Проверка принята как ручная.

Для **текущей поставки форма отсутствует**.

То есть:

```text
manual_sensor_supply_check = disabled
```

# 24. Definition of Done — TU MVP

TU считается готовым, когда оператор может:

1. открыть `Приёмо-сдаточная проверка по ТУ`;
2. дождаться автоматической подготовки стенда;
3. ввести любой номер блока;
4. если запись есть — run связывается с ней;
5. если записи нет — ничего автоматически не создаётся;
6. запустить полный current TU scenario;
7. выполнить ручные точки Р4831;
8. выполнить ЯЛК;
9. выполнить ЯТП;
10. выполнить ЯВП;
11. пройти питание/19/37/потребление;
12. получить нормативный итог;
13. сохранить полный run в `runs.db`;
14. распечатать чёрно-белый протокол:

```text
Дата
Блок
Оператор
НОРМА / НЕ НОРМА
```

И при этом обычный оператор не увидит low-level оборудование.

# 25. Definition of Done — Production MVP

Production считается готовым, когда испытатель может:

1. найти изделие;
2. зарегистрировать новое;
3. внести:

   * ЯЛК SN;
   * ЯТП SN;
   * ЯВП SN;
   * ЯП-П SN;
4. выбрать production stage;
5. запустить:

   * полный прогон;
   * питание/потребление;
   * ЯЛК;
   * ЯТП;
   * ЯВП;
6. видеть все каналы одновременно;
7. видеть отклонение в `%`;
8. видеть измеренное значение над столбцом;
9. выбрать канал;
10. видеть его живые колебания;
11. видеть фоновый noise indicator;
12. видеть график потребления;
13. получить подробную ведомость;
14. заменить ячейку;
15. сохранить старую SN;
16. получить правильное предложение повторной проверки;
17. выполнить повтор;
18. увидеть историю после перезапуска приложения.
