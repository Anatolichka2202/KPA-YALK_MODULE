# MilTech Station Enterprise — требования к фронтенду v0.1

Дата: 2026-11-23. Статус: проектное ТЗ; UI Enterprise ещё не реализован.
Основание: enterprice/miltech_server, enterprice/miltech_delivery, enterprice/contracts и существующие docs/ui/UI_SPEC_V0.md, PLATFORM_COMPOSITION.md, HMI_PRESENTATION.md, DELIVERY_UX_SCOPE.md.

## 1. Три разных интерфейса

| Контур | Платформа | Область ответственности |
|---|---|---|
| Enterprise Web | React + TypeScript (рекомендуемый стек, ещё не утверждён) | Производство, качество, изделия, парк стендов, программные поставки, аудит |
| MilTech Station HMI | Действующий Qt 6.8 / C++17 Widgets | Локальный инженерный HMI, телеметрия, оборудование, сценарии и протоколы |
| ТУ-сборка | Отдельный ограниченный Qt EXE, ещё не реализован | Подготовка → Проверка → Результат по фиксированной версии методики |

Enterprise Web не управляет физическими приборами и не подменяет Qt HMI. Локальная станция продолжает разрешённые испытания без Enterprise. Существующий apps/ui_preview и docs/ui являются исходной спецификацией локального HMI; нельзя создавать второй параллельный HMI shell.

## 2. Роли и границы

- Оператор: работа с ТУ в Qt, доступ к подготовке, текущему шагу, измерению, протоколу.
- Инженер: полная станция, HMI-представления, диагностика, утверждённые инженерные операции.
- Диспетчер производства: заказы, маршруты, экземпляры, состояния операций.
- ОТК: просмотр доказательств, отклонения, решения по операциям и выпуску.
- Администратор: регистрация стендов, конфигурации, версии ПО, доступы, аудит.

Это целевые роли. Текущий backend использует пилотный X-Admin-Key и station bearer, не OIDC/SSO/RBAC. Нельзя помещать X-Admin-Key, station bearer или приватные ключи подписи в браузер, JS bundle, localStorage. Для работающего web write UI нужен защищённый BFF/session и серверная проверка полномочий.

## 3. Навигация Enterprise

Основные разделы — Обзор, Производство, Качество, Стенды, Поставки. Администрирование отдельно, только при разрешении.

| Web route (предлагаемый, НЕ backend endpoint) | Содержание |
|---|---|
| /overview | задачи и проблемы, состояние производства и синхронизации |
| /production/orders | заказы, фильтры, статусы, маршрут |
| /production/orders/:id | карточка заказа и история исполнения |
| /production/units/:id | паспорт серийного изделия, версии, состав, замены, испытания |
| /quality | несоответствия и решения |
| /quality/units/:id | доказательства, нормативные требования, итоговая приёмка |
| /stations | парк автономных станций |
| /stations/:id | профиль, оборудование, статус, версии, runs, синхронизация |
| /releases | реестр подписанных программных поставок |
| /releases/:id | состав, назначения, ход применения и откаты |
| /administration | пользователи, доступ, конфигурации, аудит |

В интерфейсе приоритет — отклонения и действия, а не декоративные KPI. Сквозная навигация: проект → производственный заказ → серийное изделие → состав → производственная операция → run_id → протокол → отдельное решение ОТК. Проект, заказ и программа ТУ — разные сущности.

## 4. Требования к страницам

### Производство
Реестр заказов; карточка заказа с утверждённым маршрутом/ревизией; экземпляры; операции и повторные попытки. Карточка изделия показывает историю установок/замен компонентов во времени, состояние каждой обязательной проверки и привязанные runs. Повторная ТУ-проверка является новым фактом; старый результат не переписывается.

### Качество
Три независимых уровня:
- результат run: NORM / NOT_NORM / STAND_ERROR / INCOMPLETE / STOPPED / NOT_EXECUTED;
- решение по операции: ACCEPTED / REJECTED / HOLD / REWORK_REQUIRED (целевая модель);
- выпуск изделия: PENDING / APPROVED / BLOCKED (целевая модель).

Результат NORM не равен приёмке изделия; STAND_ERROR не означает дефект изделия. Поступивший RUN_COMPLETED в evidence.imported_runs — входящий технический факт, не решение ОТК и не полный измерительный протокол.

### Стенды
Площадка, ID, состояние подключения, наблюдение heartbeat и его время, состояние часов, версия агента, согласованная конфигурация, версия ПО, ошибки синхронизации. Статус online/offline возможен только по утверждённому порогу с backend; до этого показывать «Последний обмен» со временем. Карточка — read-only сравнение desired/observed: NIC, VLAN, IPv4/CIDR, route, IP:port/protocol/direction/owner, COM/USB/VISA и диагностические расхождения. Ни одна кнопка браузера не меняет IP/VLAN/firewall ОС без отдельного административного backend сервиса.

### Поставки
Реестр подписанных .mtbundle: release_id, версия, платформа, key id, SHA-256, компоненты и размеры. Назначение конкретной версии станции с pilot/stable каналом — отдельно от фактических состояний STAGED / PENDING_REBOOT / ACTIVE / FAILED / ROLLED_BACK. Загрузка файла не означает его активацию; назначение не означает успешный запуск. Не создавать прямую браузерную кнопку обхода maintenance guard.

### Обзор
Динамические показатели, основанные только на реальном backend read model. Для каждой цифры — источник и переход к исходным данным. Нет данных означает «Нет данных», а не 0.

## 5. Локальный HMI: не дублировать, а интегрировать

Соблюдать существующую docs/ui спецификацию:
- Полная станция — сборная оболочка по поставке, гибридная навигация + инженерные dock-панели.
- HMI-представление — отдельный документ с элементами label, numeric, status, bar, trend, command; текущий apps/ui_preview демонстрирует только UI, не физические команды.
- Для реального binding обязательны key, type, unit, source, measuredAtUtc, quality: Missing / Invalid / Stale / Simulated / Valid.
- Симулятор помечается явно; отсутствие значения не превращается в ноль и не рисуется «Норма».
- Будущая команда идёт только через Core dispatcher с правом, причиной блокировки и состояниями requested / acknowledged / verified / failed. Изменение layout не инициирует команду.
- Отдельный ТУ EXE содержит только Подготовка, Испытание, Результат; в нём нет редактора, произвольного управления или настройки критериев ТУ.
- От локального Enterprise-модуля нужны лишь назначение, статус соединения, синхронизация и информация о поставках; разрешённые автономные испытания от сети не зависят.

## 6. UI/UX, данные и эксплуатация

Industrial Precision: нейтральная тёмная тема из docs/ui/UI_SPEC_V0.md, минимум верхних вкладок, отчётливая типографика и таблицы; статус нельзя показывать только цветом. Принимаемые web viewport: 1366×768, 1600×900, 1920×1080; браузерное масштабирование 125% и 150%; проверка клавиатуры, фокуса и контрастности с ориентиром WCAG 2.2 AA.

У каждой загрузки: loading, empty, error/retry, forbidden, offline, stale, partial data, success. Различать observed_at, received_at, запланированное и фактически активированное. При восстановлении соединения не выдавать прошлый timestamp за новый. RU — базовая локаль; статусы сценария, качества и поставок имеют независимые словари.

Для больших списков требовать серверную пагинацию/фильтрацию. Сырая телеметрия и её высокочастотный график остаются в локальном Qt до появления отдельного read-only streaming API. Web не подключается к OT и не читает PostgreSQL напрямую.

Стек-кандидат: React + TypeScript strict + Vite, Router, TanStack Query, client generation по enterprice/contracts/openapi.v1.json, Vitest/Testing Library и Playwright. Web моки допустимы только с видимой меткой DEMO и гарантированным исключением тестовых секретов из production.

## 7. Реально существующие backend endpoints (на 23.11.2026)

- GET /health/live; GET /health/ready.
- POST /api/v1/admin/sites.
- POST /api/v1/admin/stations; POST /api/v1/admin/stations/{station_id}/rotate-token; POST /api/v1/admin/stations/{station_id}/disable.
- PUT /api/v1/admin/stations/{station_id}/profile.
- GET /api/v1/admin/stations/{station_id}/runs — последние 100, без пагинации.
- POST /api/v1/admin/delivery/releases; PUT /api/v1/admin/delivery/stations/{station_id}/target; GET /api/v1/admin/delivery/stations/{station_id}/reports.
- GET /api/v1/stations/me/profile; POST /api/v1/stations/me/heartbeat; GET /api/v1/stations/me/sync-state; POST /api/v1/sync/events.
- GET /api/v1/stations/me/delivery/desired; GET /api/v1/stations/me/delivery/bundles/{release_id}; POST /api/v1/stations/me/delivery/reports.

Первые административные endpoints защищены пока только пилотным X-Admin-Key. Пути /stations/me предназначены авторизованной станции, не web оператору. Нет endpoint списка стендов/заказов/изделий, нормализованных измерений, решений ОТК, списка релизов и их деталей. Фронт не должен выдумывать ответ. Backend gaps описаны в FRONTEND_BACKLOG.md.

## 8. Приёмка

1. Сценарий заказ → изделие → состав → операция → run → решение ОТК трассируется по реальным IDs, когда backend будет готов.
2. При NOT_NORM, STAND_ERROR, INCOMPLETE, не полученных данных и просроченном heartbeat отображаются принципиально разные состояния.
3. При остановке Enterprise локальная станция сохраняет функциональность, а web показывает stale/offline.
4. Front не скрывает проблему из-за свёрнутой панели и не позволяет обойти backend permission/maintenance guard.
5. Загрузка/назначение релиза не показываются как ACTIVE до отчёта подтверждения.
6. Любой demo экран маркирован; миграции PostgreSQL, корпоративная авторизация и Qt hardware integration не объявляются готовыми без реальной проверки.
