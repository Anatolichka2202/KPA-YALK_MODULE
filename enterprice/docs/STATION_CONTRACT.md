# Контракт автономной станции и интеграции ТУ EXE

## Функциональные роли и границы

**Core** (C++/Qt): единственный владелец hardware transport, ScenarioEngine/RunStore, локальных измерений и событий. Компонуемые TU EXE — отдельно версионированные исполняемые продукты с ограниченным UI и утверждённым capability manifest. Они не должны иметь возможность произвольно перехватывать аппаратные ресурсы другого TU пакета.

**Station Agent** (Python proof of concept в Pilot, может быть перенесён на Qt/C++): локальная очередь и доставка в Enterprise. Не получает права изменять пользовательские отчёты и нормативную оценку.

**Enterprise**: назначает версии профилей, сохраняет информацию об установке, получает результаты и обеспечивает поиск. Не является обязательным dependency для аппаратного сценария.

## Нормативный контракт профиля

См. `examples/station-01.example.yaml` и pydantic `miltech_server.contracts.Profile`.

Каждый профиль содержит:

- уникальный `station_code`;
- интерфейсы (`role`, `alias`, `vlan_id`, `ipv4/prefix`, `gateway`, `default_route`, `skip_as_source`);
- сеть сокетов (`name`, `protocol`, `direction`, `address`, `port`, `interface_role`, `owner`);
- аппаратные ресурсы (`id`, `kind`, `owner`, `exclusive`);
- `required_capabilities` установленного Core.

Ограничения Pilot: IPv4 и одиночный profile целиком; интерфейсная топология сообщается как DECLARATIVE configuration, а не машинная процедура. Для реальной системы добавить device identity (PNP DeviceID/MAC+PCI path, если стабилен), DHCP/static policy, trust roots, ASLR-safe named pipes, manifest signing и per-package permissions.

## Ресурсы

`IStationResourceBroker` (предлагаемый C++ контракт в `include/miltech/station_runtime_contract.hpp`):

- `acquireResource` — эксклюзивное владение аппаратным ресурсом с RAII lease;
- `bindEndpoint` — bind конкретного сокета по утверждённому `listen` манифесту, возвращает **тот же** открытый handle его владельцу;
- `release` — автоматический при выходе из scope/при сбое;
- конфликт по отдельному device/port должен быть диагностирован до запуска проверки.

Пример `miltech_edge/resources.py` демонстрирует удержание сокета и кросс-процессную файловую блокировку, но **не подключён к реальному Qt Core**.

## Договор обмена завершённым run (минимум)

Сразу после атомарного сохранения `run` в локальной `runs.db`, Core публикует в local outbox событие `RUN_COMPLETED` (`examples/run-completed.example.json`). У события UUID и монотонная station-level sequence, хеш, версия формата, UTC времена с tz, source_run_id, серийный номер/модель, контекст версий, итог и snapshot состава. Изменение уже опубликованного события запрещено. Исправление — отдельный последующий тип событий в следующем slice.

В Pilot событие содержит **только метаданные** и manifest артефактов, не само двоичное содержимое. Приём полного результата в `evidence.test_runs` ждёт сопоставления изделия и загрузки подтверждённых артефактов; пока запись располагается в `evidence.imported_runs` (staging).

Жизненный цикл:

`Core finished run → SQLite runs.db commit → create immutable outbox row → background station sync → 200 ACK / duplicate → outbox ACKED`

Невозможно восстановить RUN_COMPLETED после повреждения обеих БД без бэкапа. Требуется согласованный восстановительный процесс/чекпоинты с source_run_id. В Pilot нет read-only импорта фактической runs.db: схемы и код текущего HEAD не доступны для сверки.

## Сценарии без Enterprise

1. Нет связи: запуск разрешённых автономных проверок не блокируется.
2. Нет свежего профиля: разрешается последний локально подтверждённый профиль только при неистёкшем утверждённом сроке действия (в Pilot expiry ещё не реализован).
3. Неизвестные полномочия/новая ТУ: fail closed для нового запуска — до установки подписанной поставки/профиля.
4. Нет прибора или он не прошёл поверку: не искажать это в `NOT_NORM`; регистрировать `STAND_ERROR`/`INCOMPLETE` по политике поставки.
5. Не хватает места: не завершать RUN как сохранённый; прервать/безопасно завершить испытание в соответствии с методикой и сообщить явную ошибку хранения.

## Интеграционные ограничения этого пакета

- Не внедрён production-migration действующих `parameters.db`, `runs.db`, `registrar.db`.
- Нет компиляции и выполнения отдельных TU EXE; C++ интерфейс — только контракт на обсуждение.
- Нет аппаратного управления RS-485/USB/VISA и нет редактирования HMI.
- Нет RBAC / SSO / mTLS / PKI issuance, это пилотный backend с временным admin enrollment key. Не разворачивать в производственной сети в текущем виде.
- Нет утверждённой verification policy. `NOT_NORM` ≠ автоматическое решение о выпуске/браке изделия.
