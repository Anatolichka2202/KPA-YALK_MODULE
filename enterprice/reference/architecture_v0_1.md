# MilTech Station Enterprise — архитектура производственного контура

**Версия:** Draft 0.1 · 23.11.2026
**Статус:** проектная модель, не утверждённая производственная методика и не миграция действующего ПО.

## 1. Назначение и границы

MilTech Station Enterprise — on-premise платформа уровня MES/MOM для учёта жизненного цикла серийных изделий, технологических операций, испытаний, технических свидетельств, несоответствий и решений о выпуске.

- **MilTech Station Core (C++/Qt, desktop):** связь с КПА/MCU, измерения, исполнение сценариев, формирование протоколов и локальный учёт. Продолжает работать без сервера.
- **Приложения конкретных поставок (КТМА/УБСИ, ППБ и пр.):** правила ТУ, процедуры, специализированные интерпретации.
- **Enterprise Server:** регистрация изделий, версии технологических маршрутов, производственные задания, история сборки, централизованное хранение, quality decision, аудит и аналитика.
- **Внешние ERP/PLM/PDM:** владельцы собственных данных; обмен через версионированные API и адаптеры. Enterprise не заменяет ERP/PLM.

Планируемый стандарт моделирования — ISA-95 / IEC 62264 (как ориентир, без заявления о сертификации). Для OT/IT сегментации использовать принципы NIST SP 800-82.

## 2. Соответствие существующему ПО

Историческая документация MilTech указывает на локальные `parameters.db` (каталоги и адреса), `runs.db` (фактические измерительные запуски), `registrar.db` (жизненный цикл КТМА), таблицы `products`, `components`, `product_components`, `stage_attempts`, `stage_runs`, `ubsi_production_runs` и `ubsi_production_run_components`. Связь измерения с производственным этапом: `run_id`.

**Текущее состояние HEAD проекта в настоящем сеансе не проверено**: эти структуры подтверждены сохранённой проектной документацией, не живым исходным репозиторием. Перед интеграцией нужен отдельный аудит исходников и миграций.

Существующая `Registrar::productVerdict()` в описанной версии намеренно возвращает `Incomplete` до введения утверждённой verification policy. Не восстанавливать старую модель «четыре этапа OK = итог OK».

## 3. Идентичности и источники истины

| Объект | Ключ | Владелец/источник |
|---|---|---|
| Модель/ревизия изделия | `model_id`, `model_revision_id` | Enterprise/PLM adapter |
| Физическое изделие или серийный компонент | `unit_id` (UUID), производственный SN | Enterprise registry |
| Установка компонента | `installation_id`, период установки | Enterprise/Registrar adapter |
| Заказ/партия | `work_order_id` | Enterprise или ERP adapter |
| Технологический маршрут и этап | `route_version_id`, `route_operation_id` | Enterprise, утверждённая ревизия |
| Попытка операции | `operation_attempt_id` | Enterprise с локальным fallback |
| Измерительный прогон | `run_id` (UUID, никогда не переиспользуется) | MilTech Core, затем проверенная реплика в Enterprise |
| Файл доказательства | `sha256`, `object_key` | Иммутабельное файловое хранилище |
| Решение отдела качества | `quality_decision_id` | Enterprise/QMS |
| Событие доставки | `(station_id, event_id)` | Edge Outbox/Server Inbox |

Не использовать один серийный номер без типа/пространства номеров как глобальный ID. Для компонентов и изделий вести также таблицу `legacy_id_map` (source_system + entity_type + local_id → global UUID).

## 4. Шесть предметных контекстов

1. **Product Registry:** `product_models`, `model_revisions`, `units`, `unit_installations`, `legacy_id_map`. История состава через интервалы времени, без перезаписи после замены.
2. **Manufacturing:** `route_versions`, `route_operations`, `route_dependencies`, `work_orders`, `work_order_units`, `operation_attempts`, `operation_runs`.
3. **Test & Evidence:** `method_revisions`, `test_runs`, `run_measurements`, `run_artifacts`, `run_equipment`. Run append-only; версия ПО/прошивки/сценария/каталога/профиля и snapshot состава.
4. **Quality:** `nonconformities`, `quality_decisions`, `acceptance_records` с указанием подписанта, утверждённой policy и конкретных оснований.
5. **Infrastructure:** `sites`, `stations`, `equipment`, `calibration_records`, `software_releases`.
6. **Governance / Integration:** `users`, `roles`, `audit_events`, `sync_inbox`, `sync_outbox`, external mappings.

## 5. Состояния (разные смысловые слои)

- **Run verdict:** `NORM`, `NOT_NORM`, `STAND_ERROR`, `INCOMPLETE`, `STOPPED`, `NOT_EXECUTED`.
- **Operation lifecycle:** `PLANNED`, `IN_PROGRESS`, `COMPLETED`, `CANCELLED`; конкретное заключение хранится отдельно.
- **Quality disposition:** `ACCEPTED`, `REJECTED`, `HOLD`, `REWORK_REQUIRED`.
- **Release/acceptance:** `PENDING`, `APPROVED`, `BLOCKED`, `REVOKED`.

Ошибка стенда не равна дефекту изделия. Нормативный итог не формируется автоматически без версионированной утверждённой policy. Повторное испытание — новая попытка; исторические неудачи сохраняются.

## 6. Цикл одного серийного изделия

1. Утверждённые модель, ревизия и маршрут; создаётся производственный заказ, регистрируется SN.
2. Комплектация и сборка: установки компонентов и их SN, кто/когда/почему.
3. Enterprise выдаёт производственное задание на локальную станцию с версией метода и политикой доступа; локальная станция сохраняет полученную задачу.
4. Перед запуском фиксируются SN, состав изделия, экземпляр стенда, используемые приборы, валидность поверок, оператор, версии ПО/прошивок/методик.
5. MilTech Core проводит испытания автономно; `run_id`, measurements, events и artifacts попадают в локальное хранилище и outbox.
6. Клиент передаёт событие и артефакты с контрольными суммами; Enterprise идемпотентно принимает, валидирует, присоединяет к попытке операции.
7. Контролёр качества анализирует результат, при необходимости оформляет несоответствие, ремонт, новую попытку.
8. Утверждённая verification policy оценивает полноту необходимых этапов и оснований; уполномоченное лицо принимает решение о выпуске и подписывает протокол/паспорт (если предусмотрено).
9. История продолжает пополняться ремонтом, обслуживанием, диагностикой и повторными проверками.

## 7. Локальный и центральный контуры хранения

**На стенде:** существующие SQLite-базы с явными миграциями и раздельным временем жизни от release, локальный каталог файлов артефактов, `outbox`/`inbox`. Хранилище в `C:\ProgramData\MilTech\Station\`, не внутри каталога EXE.

**Enterprise:** PostgreSQL для транзакционных сущностей и индексов; файловое S3-совместимое on-prem хранилище или защищённый сетевой файловый архив для сырых пакетов, телеметрии, протоколов и снимков. Не помещать гигабайты потоковой телеметрии в основную OLTP БД.

**Репликация:** событийная синхронизация через HTTPS/mTLS, исходящий push станции, idempotency key `(station_id, event_id)`, sequence для диагностики пропусков, hash объектов и подтверждение приёма после записи. Ошибки/конфликты отдельно видны операторам. При нестабильной сети не терять данные и не прекращать безопасные автономные измерения. Не использовать физическую репликацию SQLite↔PostgreSQL.

**Политика владения:** на момент измерения локальный run — первичный факт; после подтверждённого приёма Enterprise хранит каноническую архивную копию для межстендовых сценариев. Исправления — отдельными версиями/событиями, не UPDATE исторических измерений.

## 8. Безопасность и права

- On-prem по умолчанию, явное разделение IT и OT; сервер БД не имеет прямого доступа к шинам управления КПА/MCU.
- Роли минимум: оператор, технолог, контролёр ОТК, метролог, руководитель производства, администратор, аудитор.
- Раздельные права на исполнение испытания, изменение нормативной методики, повторную попытку, закрытие несоответствия и приёмку.
- Аудит: кто, что, когда, из какого экземпляра ПО, основания, предыдущая/новая версия, корреляционный ID.
- Файлы свидетельств по SHA-256, контроль целостности при копировании, резервное копирование и проверка восстановления; при юридической необходимости — квалифицированная подпись и WORM-хранилище по отдельному ТЗ.
- Политика времени: UTC внутри, исходное время станции и статус синхронизации часов записывать; серверное время приёма хранить отдельно.
- Enterprise не должен без отдельного проектирования безопасности отправлять произвольные команды управления аппаратурой.

## 9. Версионирование и контракты

- API `/api/v1/` с OpenAPI; производственные приложения поставляются отдельно от Enterprise.
- `GET /work-orders`, `GET /stations/{id}/assignments`, `POST /sync/events`, `POST /runs/{id}/artifacts`, `GET /units/{id}/history`, `POST /quality/decisions` — **проектные** эндпоинты, ещё не реализованы.
- Версионируются: схема БД, API, формат события, методика ТУ, сценарий, каталог, профиль, software release, verification policy.
- Для каждой выполненной проверки хранится snapshot применённой версии метода и нормативных пределов; обновление справочника не переписывает историю.

## 10. Итерации внедрения

**Slice 0 — аудит:** актуальный HEAD, фактическая схема SQLite и таблицы, существующие данные, миграции, контракты UI. Зафиксировать идентификаторы и ограничения миграции.

**Slice 1 — изделие и прослеживаемость:** центральный Product Registry, прототип Postgres-схемы, API идентичностей, карта legacy↔Enterprise, подключение Read Only к существующим регистратору и RunStore.

**Slice 2 — независимая синхронизация:** локальный outbox, серверный inbox, импорт запусков и артефактов, повторы, сбои, восстановление после разрыва связи.

**Slice 3 — маршруты:** задания, версии маршрутов, журнал попыток, подготовка стендов, расписание.

**Slice 4 — качество/выпуск:** управляемые несоответствия, подтверждения, утверждаемые verification policies, документы.

**Slice 5 — аналитика/интеграции:** поиск по SN, traceability, повторные испытания, отказность, использование стендов, ERP/PLM adapter, мониторинг парка стендов.

## 11. Что требуется утвердить до production migration

1. Место мастер-данных (ERP/PLM или Enterprise); формат идентификации SN, партии и ревизии.
2. Обязательные операции для каждого типа изделия и юридически значимый порядок приёмки.
3. Требования к автономности: сколько времени допустимо работать без сети, когда запрещается/разрешается приёмка.
4. Перечень обязательных полей run и объём/ретенция сырых измерений.
5. Допустимые модели удостоверения операторов, подписи, разграничения доступа и эксплуатационные режимы защищённой сети.

## 12. Критерии приемки ранней реализации

- Сбой сервера не прерывает безопасно выполняемый локальный сценарий.
- Один и тот же sync-event, переданный 10 раз, создаёт одну принятую запись.
- Замена компонента не меняет snapshot старого run.
- `STAND_ERROR` не формирует дефект изделия автоматически.
- Старый тест с неподходящей версией ТУ не становится автоматически текущим допуском.
- Итог `APPROVED` не может возникнуть без версии policy и основания.
- Отсутствующая поверка по применимым правилам блокирует именно требуемую операцию, но не скрывает уже зарегистрированные факты.
- Отчёт воспроизводим по зафиксированным исходным данным, версиям и артефактам.
- После переустановки ПО локальная БД и outbox сохраняются.

**Сопутствующий файл:** `postgres_schema_v0_1.sql` — черновой DDL основных таблиц, не production migration.
