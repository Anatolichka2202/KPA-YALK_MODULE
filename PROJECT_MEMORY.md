## 1. Цель проекта

Текущий целевой объём УБСИ:

```text
УБСИ / УЛК
├── ЯЛК-96
└── ЯТП
```

По терминологии проекта **УЛК == УБСИ**. Исторические имена классов и capability с `ulk` не переименовывать массово.

Цель выпуска:

1. прогнать полноценную проверку ЯЛК-96;
2. прогнать полноценную проверку ЯТП;
3. уметь выполнить последовательный combined-прогон ЯЛК + ЯТП;
4. получить нормальный отчёт по ТУ и технические артефакты прогона;
5. дать оператору простой тёмный интерфейс, инженерные детали скрыть в инженерный режим.

**Не расширять production scope на ЯП-П, ЯВП-8, климат, питание и прочие узлы без прямого требования пользователя.** Если вспомогательная логика питания нужна для включения стенда, это инфраструктура готовности/cleanup, а не автоматическое расширение предмета приёмочных испытаний.

## 3. Проверенный тракт ЯЛК-96

### 3.1. Живой ROKT-протокол адаптера

Адаптер: `192.168.0.115`, UDP `1113`.

Подтверждённая последовательность:

```text
ROKT 16                 reset
ROKT 14 01 2B 01 00     address YALK
ROKT 15 01 01 01 00     address YTP
ROKT 0A 00 00 01 00     START YALK
```

Каждая команда — 128 байт, неуказанный хвост заполнен нулями.

После запуска ЯЛК ожидается свежий кадр:

```text
len = 204
header = 02 00 2B 00
payload = 4-byte header + 100 x little-endian uint16_t
```

Декодирование слова:

```cpp
analog = raw & 0x03FF;
signal = (raw & 0x0400) != 0;
```

Архивный `44 01 06` / WorkMode 6 и старые 120/200-byte кадры существуют как отдельная историческая ветка. Не удалять её, но не подменять ею подтверждённый production ROKT/204 путь.

### 3.2. Адреса и калибровка

Валидные адреса ЯЛК:

```text
1–28, 32–43, 45–70, 74–87
```

Итого 80 каналов. Не тестировать «дырки» как реальные каналы.

Калибровка production-пути:

```text
addr 97 ≈ 125
addr 99 ≈ 922
```

Адрес 98 не является заменой 99.

### 3.3. ИСД для ЯЛК

ИСД: `192.168.0.101`, HTTP/80.

Подготовка:

```text
GET /type=4num=1
GET /type=7num=1
```

Воздействие задаётся в вольтах через `type=5`, `bus=1`:

```text
GET /type=5num=Nval=0.00work=1bus=1
GET /type=5num=Nval=3.10work=1bus=1
GET /type=5num=Nval=6.20work=1bus=1
```

Выключение:

```text
GET /type=1num=Nval=0work=1bus=0
GET /type=1num=Nval=0work=0
```

Не использовать для этой задачи `type=2` и не задавать `val=4095`.

### 3.4. Подтверждённый результат

На живом стенде 02.09.2026 полный проход ЯЛК завершился:

```text
80 / 80 каналов
240 / 240 точек
failed_channels = 0
failed_points = 0
RESULT DIAGNOSTIC_OK
```

Отдельный канал после исправления ISD HTTP также прошёл 0 / 3.1 / 6.2 В в допуске 0.5 %FS.

ЯЛК как базовый тракт не исследовать заново без нового симптома.

## 4. Проверенный тракт ЯТП

### 4.1. Главный вывод

**`ROKT 17 01` НЕ является подтверждённой командой запуска ЯТП.** Старые успешные пробы были загрязнены остаточным состоянием после KPA.

Свежий успешный захват `KPA_Rokot` 02.09.2026 подтвердил фактический switch/start:

```text
52 4F 4B 54 0A 02 00 01 00 ...
```

То есть:

```text
ROKT 0A 02 00 01 00     START YTP
```

Production-builder обязан выдавать 128-байтный пакет именно с этим началом.

### 4.2. Формат ЯТП

После switch/start ожидается свежий кадр:

```text
len = 68
header = 01 00 34 00
payload = header + 32 x little-endian uint16_t
```

Слова:

```text
1..30  = каналы ЯТП
31     = верхняя калибровка, raw ≈ 4000
32     = нижняя калибровка, raw ≈ 330
```

Двухточечный пересчёт: диапазон `0..240 Ом`.

`0x8000` — sentinel «нет измерения».

### 4.3. Коммутация ИСД для ЯТП

Подтверждённые маршруты KPA:

```text
type = 7
channels = 3, 9, 12, 17
```

Их включают для ЯТП и выключают при cleanup.

Важно разделять:

```text
ISD type=7 3/9/12/17  -> физическая коммутация тракта
ROKT 0A 02 00 01 00   -> переключение/запуск YTP stream адаптера
```

Одна только коммутация ИСД не переводит поток 204 -> 68.

### 4.4. Р4831

Р4831 — ручной механический магазин. Подключён к общему X123. Компьютер им не управляет.

Production ЯТП: оператор вручную ставит:

```text
0 Ом
120 Ом
240 Ом
```

При общем 120 Ом на живом стенде уже получено примерно:

```text
120.26 ... 120.39 Ом
```

по 30 каналам.

## 5. Как выполнять combined ЯЛК + ЯТП

Не пытаться держать два потока одновременно. Подтверждённая модель — последовательная машина состояний:

```text
YALK PREPARE
-> YALK START (ROKT 0A 00)
-> verify fresh 204
-> calibration
-> 80 channels x 0/3.1/6.2 V
-> YALK cleanup

-> transition

YTP PREPARE
-> required ISD routing
-> YTP START (ROKT 0A 02)
-> verify fresh 68 + header 01 00 34 00
-> calibration 32/31
-> 30 channels x 0/120/240 Ohm
-> YTP cleanup
```

UI может показывать результаты обеих частей одновременно, но физически live-поток в каждый момент один.

## 6. Семантика результата

Строго разделять:

```text
FAIL / НЕ НОРМА
= изделие реально измерено и вышло за допуск

ERROR / ОШИБКА
= стенд, оборудование или транспорт не позволили выполнить достоверное измерение
```

Ошибка ИСД, адаптера, сети, V7 и т.п. не должна превращаться в FAIL изделия.

`Incomplete` остаётся защитным verdict движка для неполной конфигурации/диагностических запусков, но штатный опубликованный production-сценарий при исправном стенде не должен завершаться `Incomplete` из-за оставшихся commissioning-флагов.

Каждый переход режима внешнего оборудования должен быть `command + verification`:

```text
YALK requested -> require fresh 204
YTP requested  -> require fresh 68 with 01 00 34 00
```

При mode mismatch — bounded retry только известной явной последовательности, затем ERROR и safe cleanup. Не угадывать opcodes.

## 7. Отчётность и регистратор

Канонический результат прогона — `ScenarioRunResult` и вложенные `StepRunResult`, `MeasurementResult`, `RunEvent`.

SQLite `RunStore` хранит:

```text
test_runs
run_steps
run_measurements
run_events
```

Текущий `report_writer.cpp` уже определяет тип измерения по данным самого `MeasurementResult`:

```text
ytp_channel  -> YTP
a ulk_address -> YALK
```

и поддерживает mixed/combined-отчёт, а не выбирает весь формат только по `scenarioId`.

Формируются как минимум:

```text
Ведомость_каналов_<runId>.html
Ведомость_каналов_<runId>.csv
Протокол_ТУ_<runId>.html
```

Для combined отчёт должен содержать отдельные ЯЛК и ЯТП данные и общий итог по ТУ.

Рекомендуемая структура run-каталога:

```text
runs/<runId>/
├── report / protocol HTML
├── channel CSV
├── events / technical log
└── diagnostics/
    ├── adapter.raw
    └── transport.log
```

Сырые высокочастотные данные хранить файлами, не SQLite.

## 8. UI / UX — зафиксированное направление

Тёмная тема — приоритет.

Figma-макет операторского экрана:

https://www.figma.com/design/aPFXJTEv9XaI80W4BPguzz

Целевая структура operator UI:

```text
верх:      заводской номер + ЯЛК-96 / ЯТП / ЯЛК-96+ЯТП
центр:     график + компактная таблица результатов
справа:    этапы проверки + текущее измерение + состояние стенда
низ:       прогресс + итог + Отчёт + Безопасно остановить + Запустить
```

Оператору показывать:

- что сейчас проверяется;
- номер канала/адреса;
- задано / измерено / погрешность / допуск;
- ход этапов;
- итог НОРМА / НЕ НОРМА / ОШИБКА;
- кнопку отчёта.

Не показывать в основном операторском режиме:

- IP/ports;
- raw ROKT bytes;
- sequence numbers;
- HTTP paths;
- внутренние capability/locator/mask;
- инженерные 12+ колонок одновременно.

Это остаётся в F12/engineering mode.

Для графиков:

- ЯЛК: по каналам показывать приведённую погрешность и границы допуска, плюс динамику 16 свежих кадров выбранного канала;
- ЯТП: каналы 1..30, измеренное сопротивление и границы допуска / максимальная погрешность;
- combined: не смешивать ЯЛК и ЯТП в одну бессмысленную условную шкалу, переключать представление по секциям.

Последний `test_page.cpp` уже перешёл на тёмный фон графика и содержит динамику выбранного канала + обзор отклонений по каналам. Сверять дальнейший перенос с Figma, а не делать очередное свободное переосмысление.

## 10. Эксплуатационные правила

1. Один процесс владеет адаптером/ИСД. Не запускать одновременно OrbitaDesktop + KPA + probes.
2. После чистого старта ЯТП не запускать сначала ЯЛК, если цель — проверить cold-start YTP state machine.
3. Не использовать `ROKT 17 01` как YTP start.
4. Не fuzz-ить ROKT байты и не угадывать маршруты.
5. Не автоматизировать Р4831.
6. Не использовать type2 или `val=4095` для production ЯЛК.
7. Не тестировать несуществующие адреса в дырах YALK map.
8. Не массово переименовывать ULK -> UBSI в API/классах.
9. Не переписывать старый `orbita/` без отдельной задачи.
10. Не открывать широкий рефакторинг перед физическим acceptance-прогоном.

## 11. Ближайший правильный маршрут до выпуска

1. Убрать из опубликованных acceptance-сценариев всё неподтверждённое (`TODO/TBD/commissioning/mapping_confirmed:false`) либо физически подтвердить это отдельной задачей. Не угадывать опасные воздействия.
2. Собрать текущий HEAD и прогнать все автоматические тесты.
3. На чистом состоянии стенда прогнать standalone ЯТП и подтвердить:
   - `ROKT 0A 02`;
   - свежий 68-byte кадр;
   - header `01 00 34 00`;
   - cal31 ≈ 4000 / cal32 ≈ 330;
   - 30 каналов в точках 0 / 120 / 240 Ом.
4. Прогнать полный ЯЛК 80 каналов × 0 / 3.1 / 6.2 В.
5. Прогнать combined последовательно ЯЛК -> ЯТП.
6. Проверить, что итоговый `Протокол_ТУ_<runId>.html` и ведомость каналов корректно разделяют ЯЛК/ЯТП, содержат серийный номер, версии, время, измерения, допуски и общий verdict.
7. Только после этого заниматься косметикой и второстепенными функциями.
