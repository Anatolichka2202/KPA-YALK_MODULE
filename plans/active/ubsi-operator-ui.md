## Зафиксированные правила

Не менять без отдельного решения:

- один persistent испытательный workspace;
- dark industrial style проекта;
- Preparation является состоянием того же workspace;
- открытие Production/TU само по себе не должно активировать оборудование;
- production scopes: Full UBSI / ЯЛК-96 / ЯТП / ЯВП-8;
- отдельный пользовательский scope питания не нужен;
- отдельный пользовательский scope ЯП-П не нужен;
- ЯП-П остаётся частью четырёхкомпонентного состава УБСИ;
- В7 — независимый физический reference для воздействия ИСД, не источник 80 столбцов ЯЛК;
- ЯТП использует ручной R4831 и единственный backend modal `operator.manual_input`;
- ЯВП не получает `НОРМА` до подтверждённого decoder/criterion;
- UI не придумывает scenario IDs для красивых под-проверок;
- старые UI-прототипы не являются источником дизайна.

Текущий commissioning ЯВП дополнительно зафиксирован как исключение:

- Rigol CH1 физически подключён к выводу «З» ЯВП 8-2;
- Rigol должен быть доступен по VISA;
- 1 В и OUTPUT сейчас выставляются оператором вручную;
- автоматические `set_sine/output` остаются запрещены до подтверждения трактовки амплитуды.

# Несостыковки и обязательные работы

## 1. ЯП-П внутри полной УБСИ

Статус: **BLOCKER / REQUIREMENTS-BACKEND MISMATCH**

Подтверждено кодом:

```text
FullUbsi -> YALK-96, YTP, YVP, YP-P
PowerConsumption -> YP-P
```

При этом `data/scenarios/ubsi_production_full.yaml` не содержит отдельного узла `YP-P`; в нём есть `readiness` и `supply_range`.

Нельзя просто написать в UI, что ЯП-П «проверена».

Нужно сделать одно из двух и подтвердить источником требований:

1. доказать, что существующий power-flow действительно полностью закрывает требования ЯП-П;
2. добавить недостающую backend-процедуру/узел и связать его с full run.

До решения UI не должен создавать отдельную кнопку ЯП-П, но документация должна помечать coverage как открытое.

---

## 2. Production session на несколько УБСИ

Статус: **PARTIAL**

Целевая модель:

```text
оператор
  ↓
выбрать несколько уже зарегистрированных УБСИ
  ↓
очередь текущей сессии
  ↓
прогон изделия 1
  ↓
прогон изделия 2
  ↓
...
```

Текущая реализация загружает зарегистрированные изделия и выбирает active serial, но необходимо проверить, что оператор действительно формирует явную очередь выбранных изделий, а не просто видит общий список registrar.db.

Критерий закрытия:

- отдельный набор selected-for-session;
- понятный current/next state;
- переход к следующему изделию после verdict;
- запись operator/serial/scenario/status/run_id без подмены production ledger.

---

## 3. Перегрузка ЯЛК 1..88

Статус: **PARTIAL UI**

Backend выполняет перегрузку и имеет критерий:

```text
abs(delta_code) <= 2
```

Текущий UI показывает локальные значения текущего воздействия, но финальное HMI должно позволять видеть состояние остальных наблюдаемых каналов относительно baseline в процессе проверки.

Критерий закрытия:

- текущий физический канал;
- текущая полярность;
- 88-канальный обзор/матрица состояния или эквивалентное компактное представление;
- явная индикация каналов, вышедших за `delta_code` criterion;
- без отдельного второго measurement backend.

---

## 4. Время

Статус: **MISMATCH**

Текущий код считает:

```text
estimatedTotal = elapsed * 100 / progress_percent
remaining = estimatedTotal - elapsed
```

и показывает `≈` total/remaining.

Это не является утверждённым правилом операторского HMI.

До отдельного решения:

- elapsed time — допустимо и достоверно;
- progress-based total/remaining не считать каноническим;
- либо убрать эти значения, либо оставить явно вторичными до согласования алгоритма.

Критерий закрытия: отдельное подтверждённое правило времени или явное решение показывать только elapsed/progress.

---

## 5. ЯВП — decoder и acceptance

Статус: **COMMISSIONING**

Подтверждено:

```text
Rigol DG-1022Z CH1 -> вывод «З» ЯВП 8-2 -> ЯВП-8 -> adapter
ROKT 0A 01
ROKT 0A 03 channel 1..8
fresh UDP after command
```

Текущая ручная методика:

```text
оператор: CH1 = 1 В, OUTPUT
```

Не подтверждено:

- payload layout;
- физическая величина;
- Uout;
- коэффициент усиления;
- АЧХ;
- HTTP type/num штатной коммутации входов;
- код КУ1..КУ4;
- трактовка программной амплитуды Vpp/peak/RMS;
- acceptance criterion.

Критерий закрытия:

1. живой capture для режима и каждого канала на собранном тракте;
2. доказанный decoder;
3. подтверждённые HTTP type/num входов и КУ;
4. подтверждённая единица амплитуды Rigol;
5. критерии из нормативного источника;
6. полный живой run;
7. только после этого `NORM/NOT_NORM`.

До этого UI показывает `INCOMPLETE`, а не выдумывает измерения.

## 6. ЯВП — safe-off ручного Rigol

Статус: **OPEN SAFETY/PROCESS GAP**

Сейчас оператор вручную включает `Rigol OUTPUT`, потому что автоматические active commands запрещены.

Одновременно текущие `yvp_cleanup` nodes требуют только `ulk.parameter_source` и не содержат явной автоматической команды выключения Rigol.

Нужно подтвердить и зафиксировать одно из решений:

1. явный операторский шаг `Rigol OUTPUT OFF` перед/во время cleanup;
2. либо после подтверждения active-command policy — безопасный backend `output_off`.

До этого нельзя считать safe completion ЯВП полностью закрытым.

Критерий закрытия:

- сценарий/методика однозначно определяет момент снятия сигнала;
- Stop/timeout также имеют понятный безопасный путь;
- UI показывает оператору требуемое действие, если оно остаётся ручным.

---

## 7. Финальное состояние run

Статус: **PARTIAL UI**

Backend verdict и run lifecycle есть.

Нужно довести операторское состояние в том же workspace:

- итог run;
- статусы основных блоков;
- safe cleanup / power off, если подтверждены событиями;
- run_id / отчёт;
- понятное действие «следующее изделие» или возврат.

Не создавать отдельный result-application или новый wizard.

---

## 8. Визуальная доводка ЯТП

Статус: **POLISH**

Функциональные данные уже подключены.

Нужно проверить визуально на runtime:

- читаемость 30 каналов;
- выбранный канал;
- min/max fluctuations;
- положение 0 / 120 / 240 Ом;
- отсутствие дублирующего modal UI.

Не менять backend-контракт ради визуальной доводки.
