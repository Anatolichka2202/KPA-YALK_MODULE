# Content Language v1 — МилТех Станция / КТМА

Область: тексты интерфейса прототипов и будущая UX-проекция. Термины измерительной методики и ТУ не переименовываются без подтверждённого основания.

## 1. Основное правило

Текст отвечает на три вопроса в этом порядке:

1. **Что происходит?**
2. **Что это значит для текущей задачи?**
3. **Что оператор может сделать дальше?**

Не начинать операторское сообщение с названия backend-модуля, класса, таблицы БД или исключения.

## 2. Утверждённые верхнеуровневые названия

- `МИЛТЕХ СТАНЦИЯ` — общий shell.
- `КТМА` — продукт.
- `ПРОИЗВОДСТВО` — рабочая задача.
- `ПРИЁМО-СДАТОЧНАЯ ПРОВЕРКА ПО ТУ` — рабочая задача.
- `АДМИНИСТРИРОВАНИЕ` — рабочая задача.
- `ИНЖЕНЕРНЫЙ РЕЖИМ` — дополнительный слой F12, не рабочая задача.

Не использовать `режим приёмки / режим производства` как глобальный переключатель продукта.

## 3. Статусы

Использовать словарь из `design-system-v1.md` без случайных синонимов:

- ГОТОВО;
- ВЫПОЛНЯЕТСЯ;
- ТРЕБУЕТСЯ ДЕЙСТВИЕ;
- НОРМА;
- НЕ НОРМА;
- ОШИБКА;
- НЕПОЛНАЯ;
- ОСТАНОВЛЕНО;
- НЕДОСТУПНО;
- ЗАНЯТО.

Дополнительная предметная причина пишется рядом, например:

`ЗАНЯТО · ресурс используется сеансом RUN-…`

а не заменяет semantic status словом `ЗАХВАЧЕНО`, `LOCKED` и т. п.

## 4. Отличие результата изделия от технической ошибки

### НЕ НОРМА

Использовать только когда выполненная предметная проверка дала результат вне допустимого критерия.

Шаблон:

```text
НЕ НОРМА
Канал 57: отклонение +0,63 % при допустимом ±0,50 %.
Доступно: повторить измерение по методике / открыть ведомость.
```

Числа в реальном UI должны приходить из подтверждённого измерительного источника. Пример выше — только шаблон языка.

### ОШИБКА

Использовать при технической невозможности получить/доверять результату: связь, ресурс, устаревшие данные, стенд, ПО.

Шаблон:

```text
ОШИБКА
Нет свежих данных от измерительного источника.
Результат текущего шага не определён.
Доступно: проверить соединение / повторить чтение / безопасно остановить.
```

Нельзя автоматически преобразовывать ОШИБКУ в НЕ НОРМА.

## 5. Manual Action

Глагол должен описывать физическое действие:

- `Установите 120 Ω на Р4831`;
- `Подключите ...`;
- `Переключите ...`.

После инструкции обязательно указать, что подтверждает кнопка.

Хорошо:

`ПОДТВЕРДИТЬ ДЕЙСТВИЕ` — подтверждает, что оператор физически выполнил действие.

Не использовать:

`ОК`, `ДА`, `ПРОДОЛЖИТЬ` без контекста для критической ручной операции.

## 6. Safe Stop

Основная надпись:

`БЕЗОПАСНО ОСТАНОВИТЬ`

После выполнения:

```text
ОСТАНОВЛЕНО
Воздействующие выходы приведены в безопасное состояние.
Сеанс сохранён как незавершённый.
```

Последнее утверждение показывается только если это фактически гарантируется production-логикой; в React-прототипе оно должно быть помечено как intended behavior, а не подтверждённый backend-факт.

## 7. Занятое оборудование

Структура сообщения:

```text
ЗАНЯТО
Адаптер УБСИ используется сеансом <ID>.
Текущий запуск пока недоступен.
```

Если интерфейс знает владельца/оператора и это разрешено политикой продукта, можно показать его как вторичный контекст.

Не предлагать `освободить принудительно`, пока не спроектирована и не подтверждена безопасная процедура.

## 8. Неполный нормативный итог

Если выполнена только часть обязательного состава:

```text
НЕПОЛНАЯ
Выполненные проверки не покрывают весь обязательный состав утверждённой методики.
Полный итог по ТУ не сформирован.
```

Нельзя писать `НОРМА по ТУ`, если источники подтверждают только отдельные подмаршруты.

## 9. Demo-data

Любой экран прототипа с вымышленными значениями должен иметь видимую маркировку:

`ПРОТОТИП · ДЕМО-ДАННЫЕ`

Числа внутри экранов не должны переноситься в production requirement как нормативные только потому, что они присутствуют в макете.

## 10. Buttons

### Primary

Глагол + объект/результат:

- `ОТКРЫТЬ СЕАНС`;
- `СЛЕДУЮЩИЙ ШАГ`;
- `ПОДТВЕРДИТЬ ДЕЙСТВИЕ`;
- `ОТКРЫТЬ ПРОТОКОЛ`.

### Secondary

- `НАЗАД`;
- `ПАУЗА`;
- `ОТМЕНА`.

### Danger / safety

- `БЕЗОПАСНО ОСТАНОВИТЬ`.

Не использовать несколько одинаково сильных primary buttons в одной зоне.

## 11. Error message grammar

Формат:

```text
<SEMANTIC STATUS>
<краткая причина на языке оператора>
<влияние на текущий шаг/итог>
<доступные действия>
Технический код: <code>   [только как вторичная строка]
```

Stack trace, exception text и внутренние имена модулей доступны только в инженерном режиме/журнале.
