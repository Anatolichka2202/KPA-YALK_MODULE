# КТМА / УБСИ — интерактивный операторский прототип

Статус: активный design-prototype текущей поставки после предметной корректировки 2026-09-08.

## 1. Модель

УБСИ — изделие и верхнеуровневый объект проверки.

ЯЛК, ЯТП, ЯВП и питание не являются отдельными верхнеуровневыми пользовательскими сценариями. Они входят в состав полной проверки УБСИ и могут выбираться как части неполной производственной проверки.

Активный entry:

```text
КТМА / УБСИ
├── ПРОИЗВОДСТВО
├── ПРИЁМО-СДАТОЧНАЯ ПРОВЕРКА ПО ТУ
├── АДМИНИСТРИРОВАНИЕ
└── F12 · инженерный слой
```

Общая Station-концепция и прежние экраны остаются в репозитории как архитектурный задел, но не являются текущим предметным flow.

## 2. Production

После выбора УБСИ оператор выбирает production stage и состав проверки:

```text
ПОЛНАЯ ПРОВЕРКА УБСИ
```

или

```text
НЕПОЛНАЯ ПРОВЕРКА
├── Питание / потребление
├── ЯЛК · аналоговые
├── ЯЛК · контактные
├── ЯЛК · обрыв
├── ЯЛК · перегрузка ±12 В
├── ЯТП
└── ЯВП-8
```

Служебные prerequisite измерительной процедуры не превращаются в отдельные пользовательские сценарии. Для любой выбранной ЯЛК-проверки прототип автоматически включает калибровку 97/99 до измерительных шагов.

## 3. Порядок полной проверки ЯЛК

Интерактивный маршрут отражает подтверждённую последовательность предметных проверок:

```text
калибровка 97 / 99
→ аналоговые 0 В
→ аналоговые 3,1 В
→ аналоговые 6,2 В
→ контакты 0 В → 0
→ контакты 0,9 В → 0
→ контакты 2,5 В → 1
→ обрыв
→ перегрузка +12 В
→ перегрузка −12 В
→ эталон 6,2 ±0,03 В
```

Далее полный УБСИ-маршрут продолжает ЯТП, ЯВП и безопасное завершение.

## 4. Живой поток ЯЛК

Ключевое производственное требование прототипа:

**во время каждой ЯЛК-проверки оператор постоянно видит колебания всех каналов из сырого потока, пересчитанные в вольты.**

Это не отдельная «динамика выбранного адреса» и не декоративная heatmap.

Экран содержит:

1. обычный временной график всех каналов одновременно;
2. текущие численные значения каналов;
3. выбранный канал только подсвечивается, остальные не скрываются;
4. результат текущей точки/процедуры показывается отдельно от live-потока;
5. сохранённый all-channel trace доступен в производственном отчёте после завершения проверки.

В операторском UI не используется термин `УЛК`. Внутренние locator/source-названия допускаются только в F12-инженерном слое.

## 5. Количество каналов ЯЛК

Для штатной аналоговой/контактной части используются 80 подтверждённых рабочих каналов из текущего каталога:

```text
1–28, 32–43, 45–70, 74–87
```

Для overload применяется отдельная физическая модель:

```text
88 физических каналов
+12 В / −12 В
критерий остальных каналов: |Δcode| <= 2
```

Не смешивать эти две модели и не выводить 96 одинаковых каналов только из имени `ЯЛК-96`.

## 6. DEMO telemetry

Browser-prototype использует синтетические детерминированные значения только для UX-проверки. Они не являются измерениями стенда.

В production реализации источником live traces, результатов и отчёта должны быть существующие ScenarioEngine / RunStore / equipment events и подтверждённые пересчёты.

## 7. TU

TU использует полный маршрут без выбора production stage и без выбора неполного состава. Во время выполнения измерительная информация может быть показана оператору; итоговый TU-протокол остаётся коротким и без производственных графиков.

## 8. Prototype-only scenarios

Панель `СЦЕНАРИИ` позволяет вручную воспроизвести:

- НОРМА;
- НЕ НОРМА;
- stale data;
- ОШИБКА СТЕНДА;
- overload fail;
- переходы к ручным действиям.

Эта панель не является частью целевого операторского UI.
