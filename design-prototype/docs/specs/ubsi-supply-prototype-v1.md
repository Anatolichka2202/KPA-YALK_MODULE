# КТМА / УБСИ — интерактивный прототип поставки v1

Статус: активный design-prototype текущей поставки.

## 1. Область

Этот прототип сужает штатный UX до текущего предметного контура УБСИ, но не отменяет общую архитектурную концепцию Station/Product Launcher, сохранённую в старых prototype-файлах.

Активный entry:

```text
КТМА / УБСИ
├── ПРОИЗВОДСТВО
├── ПРИЁМО-СДАТОЧНАЯ ПРОВЕРКА ПО ТУ
├── АДМИНИСТРИРОВАНИЕ
└── F12 · инженерный слой
```

## 2. Что можно пройти кликами

### Производство

1. Найти УБСИ по номеру.
2. Зарегистрировать новый УБСИ.
3. Выбрать одно из семи production stages.
4. Открыть один из рабочих предметных видов:
   - УБСИ;
   - ЯВП;
   - по ячейкам.
5. Запустить полную production-проверку.
6. В active run:
   - выбрать адрес ЯЛК кликом по столбцу;
   - видеть фактическое значение и отклонение;
   - видеть живой trace выбранного адреса;
   - видеть фоновую ленту колебаний всех рабочих адресов;
   - видеть потребление;
   - поставить run на паузу;
   - Safe Stop;
   - открыть прототипную панель сценариев и воспроизвести НЕ НОРМА / stale / ошибку стенда / overload fail;
   - перейти к Р4831;
   - перейти к ЯВП.
7. Завершить run и открыть производственную ведомость.
8. В ведомости сохранить визуальный контекст динамики и потребления.

### По ячейкам

Для ЯЛК-96 / ЯТП / ЯВП-8 / ЯП-П можно открыть flow замены SN. После замены прототип показывает обязательную связанную повторную проверку:

```text
ЯЛК-96 -> полный ЯЛК
ЯТП    -> полный ЯТП, все 30 каналов, 0 / 120 / 240 Ω
ЯВП-8  -> полный ЯВП + связанные каналы ЯЛК 89–96
ЯП-П    -> питание / потребление
```

### ТУ

1. Ввести номер блока.
2. Запустить автоматическую подготовку стенда.
3. Получить состояние «СТЕНД ГОТОВ».
4. Запустить единый TU run.
5. В prototype-controls воспроизвести:
   - Р4831;
   - ошибку стенда;
   - переход к следующей проверке.
6. Safe Stop.
7. Открыть короткий чёрно-белый TU-протокол.

### Администрирование

- список УБСИ;
- состав и SN;
- замена ячеек;
- entry-точки для production runs / TU runs / состояния стенда.

## 3. Канонические величины, использованные в UI

### ЯЛК

Обычные аналоговые/контактные проверки используют 80 подтверждённых рабочих адресов УЛК из `data/catalog/address_sets/ulk_yalk_reference.txt`:

```text
1–28, 32–43, 45–70, 74–87
```

Калибровка:

```text
97 / 99
0 ... 6,2 В
```

Аналоговые точки:

```text
0 / 3,1 / 6,2 В
```

Нормальный критерий аналоговой проверки в НКУ:

```text
±0,5 % шкалы 0...6,2 В
```

Контактные точки текущей методики:

```text
0,0 В -> 0
0,9 В -> 0
2,5 В -> 1
```

Overload — отдельная процедура:

```text
88 физических каналов
+12 В / -12 В
критерий остальных каналов: |Δcode| <= 2
```

Не использовать для overload `±0,5 % FS`.

### ЯТП

```text
30 каналов
0 / 120 / 240 Ω
```

### ЯВП

Подтверждённые частоты текущей методики:

```text
0,15 / 20 / 250 / 500 / 1800 / 2000 / 4000 Гц
```

Физический тракт UI отражает как методический контекст:

```text
Rigol DG-1022Z -> C = 1000 пФ -> выбранный вход ЯВП -> X1 -> ЯВП -> ЯЛК / поток
```

При этом текущий `catalog.yaml` ещё не подтверждает live-binding ЯВП к потоку адаптера. Поэтому UI ЯВП помечает числовое live-представление как commissioning/DEMO и не формирует выдуманный нормативный verdict.

### Потребление

График production должен отражать ток и напряжение, включая точки 19 / 24 / 27 / 35 / 37 В и границу 400 мА. В текущем browser-prototype временной ряд синтетический и используется только для демонстрации UX.

## 4. DEMO telemetry

`src/ubsi/demoTelemetry.js` генерирует детерминированный синтетический поток исключительно для интерактивного UX:

- значения 80 рабочих адресов ЯЛК;
- фактическое значение в В;
- отклонение % FS;
- raw/code placeholder;
- короткий trace выбранного адреса;
- фоновую историю всех адресов;
- ток/напряжение;
- отдельную модель 88 физических каналов overload.

Эти значения не являются результатом реального стенда.

В целевой реализации UI должен получать те же визуальные поля из ScenarioEngine / RunStore / live events, не сохраняя генератор DEMO как источник измерительных данных.

## 5. Prototype-only controls

Кнопка `СЦЕНАРИИ ПРОТОТИПА` в active Production run и строка prototype-controls в TU предназначены только для UX/QA. Они позволяют мгновенно увидеть нештатные состояния без ожидания физического стенда.

Они не являются частью целевого операторского интерфейса.

## 6. Граница следующего этапа

После утверждения этого прототипа следующий этап — перенос подтверждённого interaction contract в production Qt/C++ UI поверх существующих ScenarioEngine, RunStore, Registrar и equipment capabilities.

До утверждения UX этот прототип не должен менять измерительные algorithms и wire protocol.
