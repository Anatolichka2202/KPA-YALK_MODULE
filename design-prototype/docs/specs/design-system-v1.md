# MilTech Station Design System v1

Статус: рабочая UX/UI-спецификация прототипа.  
Область: `design-prototype/` и будущая визуальная проекция в Qt.  
Не является спецификацией backend, измерительных алгоритмов или C++ API.

## 1. Принципы

1. Рабочая задача важнее структуры программы и backend.
2. Состояние оборудования и активного сеанса видно постоянно.
3. Критическое действие не перемещается по экрану между состояниями.
4. Цвет не является единственным носителем смысла: статус всегда содержит текст и пиктограмму.
5. Инженерные данные не смешиваются с операторским маршрутом без явного перехода F12.
6. React-прототип описывает anatomy, states, behavior и density; production-реализация может быть Qt.
7. Будущие продукты используют общие паттерны Station, но предметные названия, маршруты и нормативы не выдумываются без входных данных.

## 2. Семантические токены

### Поверхности

- `surface.app` — фон приложения.
- `surface.topbar` — системная верхняя панель.
- `surface.panel` — базовая рабочая панель.
- `surface.panelRaised` — строка/объект внутри панели.
- `surface.selected` — выбранный объект или активная рабочая задача.
- `surface.engineering` — инженерный слой F12.

### Текст

- `text.primary` — основной операторский текст.
- `text.secondary` — пояснение и метаданные.
- `text.tertiary` — подписи осей, вторичные метки, timestamps.

### Семантика

- `accent.selection` — выбор, фокус текущего объекта.
- `status.ready` — готовность без утверждения результата измерения.
- `status.running` — процесс выполняется.
- `status.normal` — измерительный/процедурный результат НОРМА.
- `status.action` — требуется действие или итог неполный.
- `status.danger` — НЕ НОРМА или ОШИБКА.
- `status.neutral` — остановлено/недоступно.
- `status.busy` — ресурс занят.
- `focus.ring` — клавиатурный фокус.
- `engineering` — инженерный контур F12.

Цветовые значения в React-CSS — реализация прототипа, а не контракт Qt. Контрактом являются семантические имена и назначение.

## 3. Словарь статусов

| ID | Текст | Смысл | Использование |
|---|---|---|---|
| `READY` | ГОТОВО | ресурс/шаг готов | оборудование, подготовка |
| `RUNNING` | ВЫПОЛНЯЕТСЯ | активный процесс | сеанс, измерение |
| `ACTION` | ТРЕБУЕТСЯ ДЕЙСТВИЕ | нужен оператор | manual action, подтверждение |
| `NORMAL` | НОРМА | измерительный/процедурный результат принят | результат проверки |
| `NOT_NORMAL` | НЕ НОРМА | результат вне допуска | измерение/проверка |
| `ERROR` | ОШИБКА | техническая ошибка | стенд/ПО/оборудование |
| `INCOMPLETE` | НЕПОЛНАЯ | итог ещё нельзя определить | отчёт/маршрут целиком |
| `STOPPED` | ОСТАНОВЛЕНО | сеанс безопасно остановлен | активный сеанс |
| `UNAVAILABLE` | НЕДОСТУПНО | функция/контур недоступен | launcher, permission |
| `BUSY` | ЗАНЯТО | общий ресурс принадлежит другому сеансу | оборудование |

Запрещено подменять эти значения синонимами только ради визуального разнообразия. Предметный текст допускается рядом, но основной semantic status остаётся из таблицы.

## 4. Общие компоненты Station

### ProductHeader

Anatomy:

1. бренд `МИЛТЕХ СТАНЦИЯ`;
2. текущий продукт/контур;
3. название текущего экрана;
4. краткий контекст;
5. индикатор `ИНЖЕНЕРНЫЙ РЕЖИМ`, если F12 активен;
6. `Назад`;
7. кнопка/shortcut F12.

Требование: верхняя панель стабильна по высоте и расположению. Она не должна превращаться в web-navigation.

### StatusBadge

Обязательные части: пиктограмма + утверждённый текст + семантический tone. Цвет никогда не используется без текста/пиктограммы.

### Panel

Плотная HMI-панель: заголовок, optional badge/counter, содержимое. Не использовать декоративные SaaS-card эффекты, большие скругления, oversized whitespace.

### CommandButton

Варианты: default, primary, danger, quiet. В одном рабочем состоянии должна быть одна главная primary-команда; destructive/safety action визуально отделён.

### SessionCommandBar

Постоянная нижняя зона активного сеанса.

Стабильные зоны:

1. `STATUS + PROGRESS` слева;
2. навигация шага/пауза;
3. `БЕЗОПАСНО ОСТАНОВИТЬ`;
4. primary action справа.

Safe Stop не должен менять координаты от шага к шагу.

### ManualAction

Используется, когда измерительный маршрут требует физического действия оператора.

Обязательные части:

- что физически сделать;
- целевое значение;
- фактическое/введённое значение, если применимо;
- допуск, если применимо;
- явное подтверждение физического действия;
- оператор и идентификатор запуска;
- `Отмена` и disabled-until-confirmed primary action.

Manual Action не является измерением сам по себе. Если нормативный результат требует внешнего протокола/измерения, интерфейс должен сохранять ссылку на этот источник.

### ActiveSessionRow

Показывает: объект, продукт, рабочую задачу/этап, semantic status. Переход открывает конкретный сеанс.

### EquipmentRow

Показывает: ресурс, владелец/сеанс, `READY | BUSY | ERROR | UNAVAILABLE`.

## 5. Графики и HMI

### ChannelOverview

Для многоканального контроля основной экран использует bar-overview, а не десятки независимых line charts.

Обязательные части:

- X: номер канала;
- Y: отклонение, % (если предметная методика использует процентный допуск);
- нулевая линия;
- выбранный канал;
- фактическое значение над столбцом, если плотность viewport позволяет;
- tooltip/accessible label для каждого канала;
- текстовое отображение выбранного канала справа.

Для других продуктов Y-axis определяется предметной методикой и не копируется автоматически из КТМА.

### SelectedChannelTrend

Малый временной график выбранного канала. Показывает динамику/шум и не конкурирует по площади с общим overview.

### ConsumptionTrend

Отдельный малый график потребления/питания, если этот параметр входит в текущий производственный этап.

## 6. Layout и density

Основной reference viewport: `1920×1080`.

Regression viewports:

- `1664×935` — исторический основной viewport прототипа;
- `1024×768` — компактный desktop;
- `720×900` — вертикальный fallback с прокруткой.

Правила:

- desktop/HMI first;
- важные действия не требуют горизонтальной прокрутки;
- большие канальные HMI допускают локальный горизонтальный overflow на узком viewport, но shell и command bar остаются доступными;
- верхняя и нижняя системные зоны визуально отделены от предметного контента.

## 7. Typography

- UI: Segoe UI / системный sans-serif;
- технические счётчики/каналы: Consolas/monospace;
- крупные hero-заголовки использовать умеренно;
- основной рабочий текст 10–14 px в прототипе;
- uppercase — для системных labels и команд, не для длинных абзацев.

## 8. Keyboard и accessibility

- F12: открыть/закрыть инженерный слой, не менять бизнес-задачу;
- Escape: закрыть инженерный drawer/dialog, если применимо;
- все интерактивные элементы имеют видимый `:focus-visible`;
- status не определяется только цветом;
- modal использует `role=dialog`, `aria-modal=true`;
- графики имеют текстовое состояние выбранного канала и labels;
- disabled state визуально и функционально различим.

## 9. Common vs KTMA-specific

### Common Station

`ProductHeader`, `StatusBadge`, `Panel`, `CommandButton`, `SessionCommandBar`, `ManualAction anatomy`, `ActiveSessionRow`, `EquipmentRow`, таблицы, ChannelOverview anatomy, SelectedChannelTrend, ConsumptionTrend, ReportViewer anatomy.

### KTMA-specific

УБСИ, БСИ, ЯЛК-96, ЯТП, Р4831, адреса 97/99, п. 5.6 ТУ, состав конкретных проверок, значения допусков, маршруты ИСД и другие предметные сущности.

## 10. Definition of Done для нового экрана

Перед handoff экран должен иметь:

- рабочую задачу и пользовательскую цель;
- входные состояния;
- empty/loading/error/busy/action states, если применимо;
- keyboard behavior;
- semantic statuses;
- primary/safe/destructive actions;
- источник предметных чисел/терминов либо явную маркировку `демо-данные`;
- проверку 1920×1080 и regression viewports;
- отсутствие новых backend-концепций в UI без пользовательской причины.
