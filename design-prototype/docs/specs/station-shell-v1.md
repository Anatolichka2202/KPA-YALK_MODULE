# MilTech Station Shell / КТМА IA v1

Статус: каноническая UX-структура для текущего прототипа.  
Область: только `design-prototype/` и будущая UI-проекция.  
Backend, `orbita/`, C++ и Qt production-код этой спецификацией не изменяются.

## 1. Иерархия продукта

```text
МИЛТЕХ
└── МИЛТЕХ СТАНЦИЯ
    ├── КТМА
    ├── ППБ
    ├── СУС
    ├── ВОРОНЕЖ
    └── будущие продукты
```

`МилТех Станция` — общий shell: запускает продукты, показывает активные сеансы и управляет видимостью общих ресурсов. Предметная логика остаётся внутри продуктов.

Для ППБ, СУС, ВОРОНЕЖ и будущих продуктов в текущем прототипе не придумываются предметные функции. Они могут присутствовать в launcher только как названия/неописанные контуры.

## 2. Универсальная и специализированная поставка

### Универсальная

Если установлено несколько продуктов, пользователь попадает на Station Home и выбирает продукт.

### Специализированная

Если установлен один продукт и эксплуатационный профиль разрешает быстрый вход, после системной загрузки допускается автоматический переход в Product Home. При этом пользователь всегда должен иметь доступ к Station shell для просмотра общих ресурсов и сеансов.

React-прототип v1 по умолчанию показывает универсальный Station Home, чтобы демонстрировать общий shell.

## 3. Station Home

Основные области:

1. ProductHeader;
2. список продуктов;
3. активные сеансы;
4. ресурсы станции;
5. системная строка состояния/footer.

Station Home не показывает внутренние таблицы backend, сырые драйверы и предметные шаги КТМА.

## 4. Product Home КТМА

КТМА имеет три штатные рабочие задачи верхнего уровня:

```text
КТМА
├── ПРОИЗВОДСТВО
├── ПРИЁМО-СДАТОЧНАЯ ПРОВЕРКА ПО ТУ
└── АДМИНИСТРИРОВАНИЕ
```

Это не роли пользователя и не технические режимы приложения.

Роль/уровень допуска определяет, какие действия внутри каждой задачи доступны.

## 5. F12

F12 открывает/закрывает **инженерный режим**.

Инженерный режим:

- сохраняет текущую рабочую задачу и объект;
- добавляет инженерные инструменты;
- может показывать адреса, raw, трассировку, редактор сценария и техническую телеметрию;
- не переключает `Производство ↔ ПСИ`;
- не отменяет permission checks;
- не освобождает занятый ресурс;
- не прерывает активный сеанс.

В прототипе v1 инженерный режим представлен drawer-слоем поверх текущего экрана.

## 6. Производство

### Production Home

Показывает очередь работ:

- изделие/ячейка;
- этап;
- следующее действие;
- состояние.

Ниже допускается предметная группировка КТМА: УБСИ, БСИ, отдельные ячейки, промежуточные измерения.

### Production Session

Главный HMI:

- все каналы одновременно;
- selected channel;
- отклонение относительно эталона;
- небольшой временной график выбранного канала;
- отдельный график потребления;
- состав/замены;
- постоянная command bar;
- safe stop.

## 7. Приёмо-сдаточная проверка по ТУ

### Acceptance Home

Показывает назначенные изделия и готовность к запуску:

- изделие;
- назначенная методика;
- подтверждение состава;
- готовность оборудования;
- причина блокировки, если запуск невозможен.

### Acceptance Session

Последовательный операторский маршрут. Технические адреса и инженерные параметры скрываются, кроме тех предметных значений, которые непосредственно нужны для выполнения/понимания утверждённой операции.

Постоянно доступны:

- текущий шаг;
- общий прогресс;
- semantic status;
- safe stop;
- primary action.

Для ручного Р4831 используется общий паттерн `ManualAction`.

## 8. Администрирование

Штатная рабочая задача, а не инженерный режим.

Содержит эксплуатационные сущности:

- изделия;
- состав и серийные номера;
- история замен;
- история проверок;
- профили стенда;
- архив/поиск результатов;
- уровни допуска;
- журнал изменений.

Не является frontend для схемы БД. Термины таблиц, ORM, драйверов и внутренних модулей не должны становиться primary navigation без пользовательской необходимости.

## 9. Инженерный слой

Инструменты, доступные по F12 и дополнительному уровню допуска:

- поадресная диагностика;
- raw/аналоговые значения;
- трассировка источника;
- техническая телеметрия;
- полный редактор сценария;
- технические диагностические данные.

Воздействующие команды проектируются отдельно и требуют проверки занятости ресурса, безопасного состояния и уровня допуска.

## 10. Route map прототипа v1

| Route | Экран | Parent |
|---|---|---|
| `station` | Station Home | — |
| `ktma` | КТМА Product Home | Station |
| `production` | Production Home | КТМА |
| `production-session` | Production Session | Production |
| `acceptance` | Acceptance Home | КТМА |
| `acceptance-session` | Acceptance Session | Acceptance |
| `admin` | Administration Home | КТМА |

Инженерный режим не является route и хранится отдельным UI state.

## 11. State matrix Station shell

### Products

| Состояние | UI |
|---|---|
| один доступный продукт | продукт selected; возможен быстрый вход по профилю |
| несколько продуктов | launcher с доступными продуктами |
| продукт загружается | RUNNING + disabled open |
| продукт недоступен | UNAVAILABLE + причина |
| продукт с ошибкой | ERROR + диагностический код/краткая причина |

### Active sessions

| Состояние | UI |
|---|---|
| нет сеансов | спокойный empty state, без fake rows |
| один/несколько | компактные Session rows |
| выполняется | RUNNING |
| ждёт оператора | ACTION |
| безопасно остановлен | STOPPED |
| ошибка стенда | ERROR |

### Equipment

| Состояние | UI |
|---|---|
| свободно | READY |
| занято | BUSY + владелец/сеанс |
| ошибка | ERROR + краткая причина |
| не установлено/не доступно | UNAVAILABLE |

## 12. Navigation rules

- `Назад` возвращает на parent рабочей задачи, а не в случайное предыдущее состояние браузерной истории.
- Active session можно открыть из Station Home без потери владения ресурсами.
- F12 не влияет на route.
- Safe Stop действует только на текущий активный сеанс и после выполнения должен приводить к `STOPPED`.
- Смена обычного экрана не должна сама по себе означать остановку measurement session.

## 13. Что удаляется из канонической модели

Не использовать как верхнеуровневую IA:

- `приёмо-сдаточный режим` vs `производственный режим` как глобальный toggle;
- F12 для переключения этих задач;
- `БД` как самостоятельный операторский раздел только потому, что backend хранит данные;
- `Сценарий` и `Поадресная проверка` на одном уровне с рабочими задачами оператора.

Эти сущности могут существовать ниже в соответствующем пользовательском/инженерном контексте.
