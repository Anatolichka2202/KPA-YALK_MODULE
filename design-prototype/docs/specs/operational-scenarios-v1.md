# Operational Scenarios v1

Статус: UX/prototype specification. Этот документ не определяет backend, измерительные алгоритмы, аппаратные протоколы или Qt production implementation.

## 1. Назначение

Базовый happy-path недостаточен для промышленной станции. Prototype v1 должен демонстрировать не только нормальное выполнение, но и то, как интерфейс различает причины, сохраняет безопасность и предлагает оператору следующий допустимый шаг.

Для быстрого просмотра edge-cases в React-прототип добавлен `UX SCENARIOS` dock. Он является только навигацией самого прототипа и **не является частью будущего операторского Qt UI**.

## 2. Матрица реализованных сценариев

| Сценарий | Route прототипа | Главный UX-вопрос | Реализовано |

| Specialized one-product startup | `single-product` | как убрать лишний launcher при одной надстройке, не убирая Station как shell | да |

## 3. Recovery states

### 3.1 `НЕ НОРМА`

Причина относится к результату изделия: измерение получено валидно, но критерий проверки не выполнен.

UI обязан сохранять:

- измеренное значение;
- критерий/допуск;
- номер попытки;
- статус `НЕ НОРМА`;
- предыдущие попытки при повторе.

Повтор не стирает исходный результат.

### 3.2 `ОШИБКА`

Причина относится к технической возможности выполнить проверку. Нормативный результат шага не определяется.

UI не должен автоматически переводить техническую ошибку в `НЕ НОРМА` изделия.

### 3.3 `ДАННЫЕ УСТАРЕЛИ`

Последнее значение можно показать как исторический контекст, но оно визуально и семантически перестаёт считаться текущим. Continue по stale data в прототипе запрещён.

### 3.4 `ЗАНЯТО`

Ресурс исправен, но закреплён за другим сеансом. UI показывает владельца ресурса и предлагает безопасные варианты; оператору не предлагается force-acquire.

## 4. Manual Action + safety

ManualAction блокирует обычные команды активного сеанса, но `БЕЗОПАСНО ОСТАНОВИТЬ` остаётся доступным поверх modal layer.

Подтверждение ручного действия фиксирует действие оператора, но само по себе не является измерительным результатом.

## 5. Administration destructive change

Изменение состава показывается не как обычный inline edit. Prototype требует:

1. показать `было → будет`;
2. запросить причину изменения;
3. отдельно подтвердить понимание влияния на связанные проверки;
4. визуально отделить destructive confirm;
5. показать, что это UX-прототип без записи в backend.

## 6. Reports

### Production ledger

Фиксирует конкретный производственный этап и его измерения/состав. Не использует формулировку полного приёмо-сдаточного соответствия.

### Acceptance ReportViewer

Содержит summary и детальную ведомость. Если полный обязательный состав проверки в прототипе не представлен, итог остаётся `НЕПОЛНАЯ`, а формирование полного нормативного PDF недоступно.

## 7. Demo-data policy

Числа и идентификаторы, которые введены только для демонстрации поведения UI, маркируются `DEMO` или сопровождаются явным указанием на демонстрационный характер экрана.

Нельзя использовать prototype placeholder как подтверждение реального измерительного факта, реального состояния стенда или нормативного результата.

## 8. Открытые сценарии следующего slice

- restart/reopen активного сеанса;
- permission denied / elevation request;
- multi-product launcher loading/error states;
- `НЕ НОРМА` непосредственно в 96-channel overview;
- telemetry/stand-error overlay непосредственно в активном HMI;
- focus trap и focus return для modal interactions;
- visual/browser QA на целевых viewport.
